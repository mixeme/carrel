# Changelog

All notable changes to this project are documented in this file.

## [Unreleased]

### Added

- **Desktop wrapper phase 4 — sidecar download:** `internal/desktop/sidecar` downloads `carrel_{version}_{goos}_{goarch}` from GitHub releases, verifies SHA256 via `checksums.txt`, extracts to the install dir, and writes `version.json`. Local mode calls `Ensure` lazily when the sidecar is missing or version mismatches; `-sidecar` skips download for development.

- **Desktop wrapper phase 3 — local supervisor:** `PickFreePort` on loopback, `Supervisor` starts `carrel` with `CARREL_DATA_DIR`, `CARREL_PORT`, `CARREL_BIND=127.0.0.1`, polls `/healthz`, writes `instance.lock` with dynamic port, stops sidecar with 15s grace (SIGTERM / interrupt). `LocalApp` and `-local`/`-sidecar` flags; Wails `SingleInstanceLock` focuses an existing window on second launch.

- **Desktop wrapper phase 2 — Wails Remote webview:** `cmd/carrel-desktop` (Wails v2) opens a window and navigates to a configured or `-remote-url` Carrel instance; persistent webview profile under the OS-user Carrel directory; instance lock on startup. Minimal `frontend/` shell embed; full UI and fan-out SSE/poll run in the remote webview like a browser. Local mode returns a clear not-implemented error until phase 3.

- **Wave 2.1 — full-screen note.** A note opens in read mode on its own URL: prose column, meta column (tags, related, attachments, source), neighbour notes in the rail, **Full width / Reading width** (remembered in `localStorage`), **Focus** and **Esc**, markup toolbar and unsaved-draft warning in edit mode (`?edit=1`), **Copy link**, and **Source** toggling the raw text. The details panel links **Open** instead of **Edit**. Save stays explicit; ETag conflicts unchanged.

- **Wave 2.2 — Markdown in read mode.** Note bodies render as GitHub Flavored Markdown through `goldmark` (headers, lists, tasks, emphasis, links, code, quotes, tables); raw HTML stays escaped. Storage and edit mode still use the exact typed text; **Source** shows the same string. Dependency recorded in `THIRD_PARTY.md`.

- **Wave 2.3 — Related to typeahead.** The note editor replaces the comma-separated UID field with a search-as-you-type picker over the same selected calendar and contact sources as global search. Matches appear as removable chips; **Enter UID by hand…** is always the last menu item.

- **Wave 2.4 — file manager foundation.** `/app/files` is **All collections** — every storage as a top-level folder with server, access and attachments badge. Inside a collection: row checkboxes, an operations bar (download and batch delete with a per-item report), **Filter this folder** on the loaded listing, type icons in the name column, and a properties panel for a single selection (closes manually and remembers). Breadcrumbs navigate as before.

- **Wave 2.5 — rename and move.** The provider gains `Move` and `Rename` over WebDAV `MOVE`. The operations bar and a shared folder-picker dialog (all storages in one tree) wire **Rename** (one item) and **Move…** (batch). Same-server moves use `MOVE`; cross-storage moves stream through Carrel with download and upload.

### Changed

- **Wave 1 close-out — the narrow screen keeps the promise §13 made.** The slide-out panel of 1.17 moved the wrong rail. What slid out was the list of *sections*, which the bottom bar already carries; what got `display: none` was the *source* rail — the stack of checkboxes that §13 and section 10 of the mockups both name as the thing to move out of the way. A phone therefore could not choose which collections to poll at all. The panel now takes the whole screen, holds the source rail with its own **Apply** button and the section links below it, and closes on Escape, on the scrim and on its own ✕. It is assembled in the browser, so without JavaScript the rail simply stays in the flow of the page: uglier, and still usable. Tap targets follow: the toggle went from 28 px to 44, and source rows, list rows, the bottom bar and every button below 640 px are 44 px — the row-height tokens of 1.3 stop governing controls once the pointer is a finger. There is no properties panel on a phone any more: a row opens the record itself, which is where its `href` pointed all along, and the remembered-open state of 1.4 no longer restores a full-screen overlay on load. Photo cropping on a narrow screen is the centre square §13 asks for rather than pan-and-zoom by numbers — canvas, number fields and the preview button are all hidden, and the screen says so. The one item of §13's list still missing is the `⋯` row menu that was to take the panel's place for operations; it is written down in the specification and the roadmap instead of being quietly dropped.

- **The tests those steps should have carried.** `DetectTodos` and `DetectNotes` (1.15) had none, while their contact and event counterparts had four between them: tasks and notes group on a shared UID, a shared summary alone stays below the default threshold on purpose, a skipped pair is never offered again, and the kind filter keeps a task out of the notes section. Task attachments (1.14) gain the model test journals already had — `ATTACH` reaches `Todo` with its parameters and does not also turn up among the foreign properties §8 keeps untouched. `settings.go` had CRLF endings and an unaligned `const` block, so `gofmt -l .` had not been silent since 1.10.

- **Documents caught up with the code,** which is what the plan means by a wave being closed. §13 of the specification now marks the slide-out panel, the 44 px targets and the centre crop as done and the row menu as not; the roadmap's narrow-screen gap shrank to that one item; and the completeness table of 7.13 in the mockups was re-checked — 50 templates and 92 routes, `app` and `timeline` replaced by `settings_*` and `person`, the four detail panels listed as the fragments they are, and the §23.8 row no longer badged as planned.

- **Wave 1.18–1.19 — drag-to-crop photo and embedded fonts.** The contact photo crop screen gains a visual drag layer: a 256 px canvas shows the source image with a square crop frame that can be repositioned by dragging and zoomed by scrolling. The hidden form fields stay in sync so Update preview sends the right values to the server. The four number fields (Pan X, Pan Y, Zoom, Rotate) move into a `<details>` block as a keyboard fallback and remain the only option on narrow screens where CSS hides the canvas (§13 asks for a centre crop there). Literata (normal + italic, Latin + Latin-ext + Cyrillic) and Public Sans (variable weight, Latin + Latin-ext) are embedded into the binary as woff2 files under `static/fonts/` via `go:embed` and served through `@font-face` rules with `unicode-range`; no CDN appears, and the image size grows by ≈145 KB.

- **Wave 1.16–1.17 — print directory listing and narrow screen.** Print stylesheets now cover the files table (break-inside, clean borders) and every fan-out view (agenda, tasks, notes, contacts, search, duplicates) gains a print footer with the section name, number of sources polled, and a capture timestamp. The files screen adds its own print footer with the account label. Narrow screens (≤640 px) get a slide-out section rail toggled from the header, a fixed bottom navigation bar with five section shortcuts and 44 px touch targets, two-line record rows that collapse grid columns to a single content area, the detail panel as a full-screen overlay, and hidden sidebars/source rails so the content fills the viewport. `carrel.js` handles the rail open/close.

- **Wave 1.14–1.15 — task attachments and task/note duplicates.** Tasks gain the same attachment block events and notes already have: upload, detach, open through the proxy, all reusing the shared `{{template "attachments"}}` and the existing `/attach` endpoint. The `ATTACH` property is parsed into the `Todo` model instead of falling into `Other`. Duplicate detection now covers tasks (`VTODO`) and notes (`VJOURNAL`) in addition to contacts and events: the poll loads all component types from each calendar, fingerprints them on UID and summary, and groups them on the duplicates screen under their own sections. Linking and ignoring work the same way; server-side merge is not offered for tasks or notes because their fields have nothing to supplement.

- **Wave 1.12–1.13 — §23.8 transparency.** Detail panels and **Settings → Connections** show a **Source** block with when the collection was last read, when the server last changed it (from `getctag` when it encodes a time), and object count. Event times carry the stored `TZID` as a muted label when it differs from your settings timezone; the event form shows a read-only **Time zone** field in that case.

- **Wave 1.11 — column picker.** Lists and tables in contacts, tasks, notes, files, admin users, and the audit log gain a **Columns** control in the toolbar. A checkbox shows or hides a column, the drag handle reorders, and the first data column cannot be turned off. Choices are stored per section in `localStorage`.

- **Wave 1.10 — settings and administration shell.** Profile moves into **Settings** with its own rail: Account, Connections, Attachments, and Appearance. `/app/` redirects to Connections; the header login link becomes a menu (connections, account, appearance, theme switcher, administration, sign out). **Appearance** keeps theme and row density in `localStorage` only. Administration pages use the same top bar and a vertical rail instead of horizontal tabs.

- **Wave 1.9 — import, merge, and conflict dialogs.** Import screens are a three-step wizard (file or source → preview → report) in a centred dialog without the section rail. Merge confirmation and ETag conflict resolution use the same dialog frame: merge shows kept/deleted/gains with a solid danger confirm button; conflict shows a wide property table with value colours by diff kind. Handlers and form fields are unchanged.

- **Wave 1.8 — cross-source search and person view.** The header search field submits to `/app/search` from any screen (`/` focuses it); the search page shows results and kind tabs only. `/app/contacts/{account}/{col}/{uid}` is the full-width person screen: calendar source rail, fan-out of meetings, tasks, notes and file attachments from the same poll, a «why it matched» column (exact `mailto:` attendee vs text hit), kind tabs including Files, and Write a note / New event with a pre-filled link or attendee. The edit form moves to `/edit`; `/timeline` redirects here. Duplicates gains the same kind filter tabs; `timeline.html` is removed.

- **Wave 1.7 — unified view inside sections.** `/app/calendar`, `/app/contacts`, `/app/tasks`, and `/app/notes` open on an «All …» merged view with fan-out polling; each section rail lists collections with tri-state selection, and merged rows show a source column. Calendar range forms add Events / Tasks due / Notes kind checkboxes. `/app/unified` redirects to the matching section; `unified.html` is removed.

- **Wave 1.6 — forms.** Record cards, settings, auth, and admin screens use a shared multi-column form layout: `.form` / `.form-field` with content-width tokens (`w-xs`–`w-xl`), grouped fieldsets, and a `.form-foot` action bar. Field names and handler tests are unchanged.

- **Wave 1.5 — quick note sheet.** «New note» opens a sheet over the current screen via htmx; `/app/notes/quick` still works as a full page without JavaScript. The caret lists other create actions in rail order (contact, event, task, file upload). Keys: `N` opens the sheet, `/` focuses search, `Enter` opens the selected row, `Esc` closes the sheet or details panel, `Ctrl+Enter` saves the quick note.

- **Wave 1.4 — details panel.** Contacts, calendar, tasks, and notes load a read-only card into the right-hand `#app-details` column via htmx when a list row is clicked. Direct links to a record still open the full edit page. The panel closes with ✕ and does not reopen by itself; which row was open is remembered per section in `localStorage` until the user closes it.

- **Wave 1.3 — list row components.** Shared list grid (`.list` / `.list-row`), 3 px collection bar, rubricator headers, square 28 px avatars, and badge styling from the mockups. Row-height tokens (`--row-lg` / `--row-md` / `--row-sm`) drive control sizes; inputs and adjacent buttons share the 28 px height. Contacts, agenda, tasks, and notes use per-section column layouts; collection dots in the sidebar are vertical bars.

- **Wave 1.2 — application shell in `base.html`.** Signed-in app pages use a 52 px top bar, section rail, full-width content area, and a hidden details zone for later htmx use. `View.Shell()` and `View.NavSection()` drive the frame; admin and public pages keep the old top bar. Responsive layout collapses rail and side widths at ≤1279 px and hides the details column at ≤1023 px.

- **Wave 1.1 — design tokens in `carrel.css`.** Palette and layout variables from the UI mockups (§5): font stacks, `--rail` / `--side` / `--top` / `--pad`, `--accent-lt`. One alert colour (`--alert`) replaces `--error` and `--danger`. Dark theme follows `prefers-color-scheme` and `data-theme`; `:focus-visible` uses the accent outline from the mockups.

## [0.9.0] - 2026-08-18

**Планы и спека после 0.8.0; волна 0.1 в коде.** Глобальный план, §10.1 коллекции, §23.3–§23.5 в спеке и макетах; отзыв депонированной копии — только решение владельца ключа (код). Версия в бинарнике — `0.9.0`. Не v1: тег ждёт P1, P2, P5 ([docs/manual-acceptance.md](docs/manual-acceptance.md)).

### Added

- **A global implementation plan — [docs/plans/global-plan.md](docs/plans/global-plan.md).** The roadmap says what is not built and in what order it matters; the mockups say how it looks and carry their own fourteen-step order for the redesign. Neither answers the question the two together raise: which of those orders runs first. The plan answers it in five waves and two parallel tracks, and derives the order from three rules rather than taste — no feature starts with its interface, the frame comes before what stands on it, and the collection parity rule is an acceptance criterion rather than a wish.

  Reading the mockups back against the code found work that the roadmap does not list, because it was never a decision to defer — it simply had no page in either document: the installation-check screen of 7.11.1, which answers the most common complaint there is (Carrel sits behind somebody else's reverse proxy and the proxy is what breaks) and which the specification does not describe; the column chooser for six lists and tables; the dark theme and the row-density switch, neither of which exists in `carrel.css` at all; the person screen moving out of the service «timeline» into contacts with a why-it-matched column the engine already computes and does not show; tiles with thumbnails, cross-storage copying and an upload queue with progress in files; the folder-picker tree, which three separate screens need and which the mockups say is drawn once; and the show-password sheet whose mechanics 7.10 and 7.14 share.

  Manual acceptance blocks the **tag** and not the work: P1–P4 test data compatibility, the container and the logs, and do not depend on the layout, while P5 and the live attachment pass go through exactly the screens the first two waves change and are therefore repeated after them.

- **Creating, renaming and deleting collections — §10.1 and its screens.** A hole nobody had written down: Carrel could write events and cards, and could not make the calendar or address book to put them in. Someone standing up a clean Baikal landed in an interface with nothing to work on and went to the server's own admin panel — precisely the place Carrel promises to take them away from. File collections have had `MKCOL` from the start, so the collection parity rule (§2.1) says this was an oversight rather than a decision, and the parity table now carries the row.

  The new section sits in §10 «Данные» and not in §23, because this is missing data work and not an addition on top of a finished web client. It fixes the wire operations per kind (`MKCALENDAR`, extended `MKCOL`, `PROPPATCH`, `DELETE`), the two methods the transport of §7 still lacks — `PropPatch` and a `MkCol` that can send a body — address derivation from the name and its immutability afterwards (a change of address is `MOVE`, after which the collection vanishes and reappears for every configured client), the component set as a decision that can only be made once because most servers freeze it at creation, and the fact that the right to create lives on the home-set where discovery never looks: the button is therefore not hidden in advance and the server's refusal is shown as diagnostics, method, code and body, the way a failed connection already is.

  Four screens in [7.10.1](docs/visual/carrel-ui-mockups.html): the new-collection sheet, that refusal, rename-and-colour, and deletion. **Deletion earns its own rules** — the only Carrel operation that destroys somebody else's data in bulk, and one to which §8 does not apply because there is nothing left to preserve. It lists what points at the collection (published links, backup jobs, davloom devices), offers the export before rather than after, and confirms by typing the name, because everything it would destroy cannot be listed. Entry points: buttons in the contacts and calendar rails, `New collection` on each account card in Connections, and a per-collection menu. The account's `Remove` became `Disconnect`: a button that deletes data on somebody else's server now stands next to it, and two adjacent buttons meaning «delete» with opposite consequences would eventually be confused.

- **Sending by mail — new §23.5.** Publication (§23.4) issues a link and then leaves the person to carry it to the recipient by hand. The SMTP client has worked since §5.3; what was missing was permission to use it for anything but a token. Two steps, and the second does not stand without the first: a link sent by mail, then a plain letter with things attached — contact, address book, event, calendar range, note, task, file attached; folder always a link, and anything over the ceiling becomes a §23.4 link too, which the interface says *before* sending rather than leaving the recipient to report it. One direction only: Carrel sends and never receives, and that is what makes the address work below the real content of the section.

  **The From address is an administrator's decision, not a guess.** The instance owns its domain, so the question is which form the relay will let out, and the setting beside SMTP has two positions: personal `<login>@<domain>`, or the service `noreply@<domain>` alone, which is the default. The envelope sender stays the configured relay address either way, so SPF passes on it whatever the header says. Carrel signs no DKIM and touches no DNS — the administrator knows the relay and Carrel does not, and §5.3's test-message button answers the question empirically for the chosen form. The domain comes from the setting rather than the request header, or the sender address would depend on which proxy the user arrived through. The one local part that can collide with a login becomes a **forbidden login** rather than a special case: `noreply` is the instance's service address whatever the setting says, so no such account may exist — the check joins login validation and applies always, and where such an account already exists, enabling personal addresses refuses and names it. `admin` needs no rule, the login being ordinary and the domain the instance's own.

  **`Reply-To` is the profile address only once confirmed — and «confirmed» turns out not to be a state the record can express.** There is an address, a pending address and a change token, but no flag saying this one was proved, because three of the four ways an address arrives confirm it by construction: an invitation by mail, self-registration, a change of address. The fourth — an invitation by **link** — lets the person type any address at activation and stores it unchecked. That cost an undelivered notice at worst, right up until `Reply-To` began depending on it, where it instead steers the recipient's reply at an address nobody proved. So the flag gets added, a link activation counts as unconfirmed, and it is confirmed by the same mailed link as a change. With no confirmed address the letter ends with a line saying not to reply, because Carrel parses no inbound mail at all and silence would lose the reply.

  Two consequences worth naming. The profile has a login and an address and **no display name** — «sender name from the profile» means adding that field, falling back to the login, and one field fills two places: the `From` header and the signature closing the letter. Not field economy — under the service From the header reads `noreply@domain`, leaving the signature as the only place that says who wrote. The foot of the letter has a fixed order: text, signature, then the do-not-reply line where that case applies. And a calendar attachment carries `METHOD:PUBLISH`; `REQUEST` would turn the letter into an iTIP invitation, which is on the list of things that will not happen.

  The remainder is the abuse surface, which is why the feature has a switch: off by default, ceilings on attachment size, message size, recipients per letter and letters per user per day, `CR`/`LF` stripped from subject, sender name and recipient addresses so nobody appends a `Bcc:`, and an audit line recording who sent how many with what kind of attachment — not the addresses, not the subject, not the contents. One limit is structural rather than defensive: SMTP wants the whole message and base64 inflates it by a third, making this the only place in Carrel where a file body is held whole in memory. The ceiling is the answer; a temporary file is not. Sending creates no state, so §10.1's «what points at this collection» warning gains no row. Recorded in [docs/roadmap.md](docs/roadmap.md) as item 4, ahead of davloom, and in §25.6 stage 2.

  **The recipient field completes from the connected address books** — the same fan-out search as §16, narrowed to cards that have an address. A client that holds the address books and still sends you to another screen to fetch an address would be absurd. A suggestion is an address rather than a person, so a card with two addresses makes two rows carrying their own `TYPE` labels; a card with no address is not offered at all, the iCal↔vCard bridge of §23.9 having nothing to stand on without one; typing an address by hand stays the ordinary case rather than a fallback. The list also names any book that failed to answer (§17) — otherwise a missing person reads as «you have no such contact» when the truth is that a server was down, which is the silence §23.8 exists to argue against. No history of recipients, that being content Carrel does not keep (§2), and no expansion of `CATEGORIES` groups, one keystroke turning into forty recipients deserving its own decision.

  **Which address the letter leaves from is shown before it is sent, in every sending form.** The sender is not a choice — the administrator picked the form, the person set the reply address in their account — but Carrel keeps no copy of what it sent, so *afterwards* there is nowhere to find out, while the recipient sees the address regardless. The line therefore sits beside the send button and links to where the reply address is changed; with an unconfirmed address it says replying will not be possible rather than that `Reply-To` is empty.

  **A note is the one kind with a real choice of format,** so the picker asks and defaults to `.md`. A contact has only `.vcf` and an event only `.ics`; a note exists in two forms at once because the Markdown rendering is Carrel's own and nobody else's. The choice names what each loses rather than that the formats differ: Markdown carries the text and links to attachments but not the foreign `X-` properties of §8 nor data embedded in `ATTACH` (§23.10); the source `.ics` is the faithful copy and needs a client that reads VJOURNAL. Markdown wins the default because the letter goes to a person, not to their calendar.

  **Choosing what to attach is a Carrel screen, not a system dialog** — the record lives in a collection the operating system knows nothing about. It is built from what already exists (sources left, list right, search on top) and shows, before the attach button is pressed, exactly what will land in the attachment list: format, size, and whether it goes as a file or a link. For files that column sits on every row before anything is picked. And attaching over the ceiling **publishes a secret link (§23.4), which the picker has to say**: otherwise pressing «attach» quietly creates an entry in the published-links list, with its own lifetime and its own revocation, that the owner never knew about.

  **Ten screens in [7.17](docs/visual/carrel-ui-mockups.html),** a new section that pushed davloom to 7.18 and the small-planned table to 7.19. Both menus that list record kinds now run in rail order — contacts, calendar, tasks, notes, files. The attach menu was drawn with notes ahead of tasks, and the caret menu beside **New note** had carried event ahead of contact since it was drawn, both under captions claiming rail order. A menu that reorders the sections makes the reader search a list instead of reaching a known place. The letter is a **sheet**, for the same reason the quick note is one: it is written about what is on screen, and the two ticked rows behind it are half its content. It opens from under the caret beside **New note**, last and below a rule — the only item in that menu which creates nothing in a collection, and the arrow was already described as «everything else you can create».

  What the compose window is really for is the **attached / as a link** column. It answers the question the recipient would otherwise ask — why an address arrived instead of a file — and both rules are visible without explanation: a folder always goes as a link, everything else turns into one when it does not fit the ceiling. Saying so **before** sending is the only moment it can still change anything. The admin screen turns the From decision into a two-position switch of ready-made strings rather than a field for the domain: the domain is known, the only real question is which form the relay lets out, and the test button settles the SPF argument with one message instead of documentation. Both recipient-side letters are drawn too, because the signature and the do-not-reply line are the two things nobody can check afterwards. No new primitive was needed — the claim in section 13 that five planned features stand on the same parts holds.

### Fixed

- **Two mockups had specification references in their interface copy** — `§23.4` in the file picker of 7.17 and `§2` in the external-feed message of 7.16. The rule against this was already written down («рассуждение о решении — только в подписи под макетом»), and both lines slipped past it the same way: interface strings are English, so a sentence in English voice carrying a `§` does not look like document text at a glance. The rule now says outright that a section reference is reasoning whatever language surrounds it, and names the check — search for `§` inside `.mock`. Both screens now state the consequence («the letter will carry a secret link instead», «Carrel keeps no copy of it»); the reason each is so moved into the caption, where the rest of the reasoning lives.

- **The collection stripe knew no size of its own.** `.m-bar3` was given width and height only inside `.m-src` and `.m-row`; everywhere else — screen headings, file names, subtitles, tags — it silently collapsed to zero width, and **60 of the 239 stripes in the mockups were not being drawn at all**, under captions explaining what the stripe means. It is the same mistake the row-height section of the mockups already describes: the size was known to the markup rather than to the system. A base rule now gives it 3×14 and `display:inline-block` so width applies in inline contexts too; the per-context rules stay and only override the height.

- **Docker image seeds the data volume for `nonroot`.** A fresh named volume was owned `root:root`, so the distroless user could not create `server.key` on first start. The build now ships an empty `/var/lib/carrel` owned by `nonroot` with mode `0700`, which new volumes inherit.

### Changed

- **Manual acceptance lists only what is still open.** Closed container, log and mail checks are gone from [docs/manual-acceptance.md](docs/manual-acceptance.md); P1, P2 and P5 still block the tag.

- **Manual acceptance recorded a live mail pass.** The remaining SMTP items — a successful test message with the full diagnostic, the mandatory escrow-recovery notice, and an invitation by email — were run in Docker against SelfPost as the relay and confirmed in a real mailbox. P1, P2 and P5 are still open. The checklist is [docs/manual-acceptance.md](docs/manual-acceptance.md).

- **The external backup trigger hands over the finished command, not the password (§23.3).** Whoever turns it on came for a copy taken at three in the morning, which means a line in `crontab` on the machine that holds the schedule; the password is already inside that line, and assembling the call from documentation is work that can be done for them. The password moved to a disclosure below, where it matters to the minority writing the request by hand — and is worth showing properly there, with the other endpoints and the bounds of what it opens. The line is one line and stays one: `cron` understands no continuations, and the time lives inside it rather than in a second place on the screen.

  **A destination other than WebDAV alone changes the shape of what is handed over.** A job that also gives the file back needs two steps — start it, wait, take the archive — so it gets a short script instead of a line, and the crontab entry only calls that script; a download-only job gets a single request that builds and streams the archive in one breath. Tabs for `cron`, GoSentry, Gitea and plain `curl` differ in where the schedule lives, not in what each tool is allowed to do.

  §23.3 gained the contract this requires: the run answers with the id as a bare line and the status as one word, so a `sh` script on somebody else's machine needs no `jq`; status is asked by run id and by job; `GET /api/backup/download?job=` covers the download-only case. Asynchrony is explained rather than assumed — a silent `POST` running for minutes hits the proxy timeout, a stream continuously delivering bytes does not. The password's scope is now one job and starting it, not the account. Backup as a **list of jobs** is written down, with its three destinations and what each requires of the trigger.

- **Archive encryption is on by default rather than unconditional (§23.3),** with the consequence named in the same breath: with it off, whoever holds the trigger password can pull the archive down in the clear. This is the edit the 0.8.0 mockups said §23.3 would need.

- §10 is now **[частично]**; §24.8 gained two checks (a job's trigger password starts no other job and reads no collection; one user cannot create, rename or delete another's collection). [docs/roadmap.md](docs/roadmap.md) records §10.1 among the requirements not met and no longer claims backup encryption is non-negotiable.

- **Escrow withdrawal is always the key owner's decision in code (§5.4).** Removed `Settings.Escrow.ForbidOptOut`, the «Do not let users withdraw their deposited key» checkbox on `/admin/escrow`, the disabled-withdrawal branch in the profile, `SetEscrowOptOutPolicy`, `ErrEscrowOptOutForbidden`, and tests `TestOptOutCanBeForbidden` and `TestForbiddenOptOutIsVisible`. A `forbid_opt_out` flag left in an older state file is read and ignored; withdrawal still works. `TestStoredForbidOptOutIsIgnored` covers that case. The specification and mockups were updated in 0.8.0; this release catches the code up.

- **Interface mockups grew from a redesign sketch into the reference for every screen** — [docs/visual/carrel-ui-mockups.html](docs/visual/carrel-ui-mockups.html), 100 mockups drawn as live HTML on the classes meant for `carrel.css`. What changed since the first pass, in the order it matters:

  **The unified view moved into the sections.** «Everything» and `/app/unified` are dropped: the first row of every source list is now **All calendars**, **All address books**, **All lists**, **All notebooks**, and the mixed chronology survives as *Tasks due* and *Notes* ticks in the calendar range bar — the one place where mixing kinds on a date axis is meaningful. Contacts, not Calendar, is the first section.

  **Everything known about one person, in one place.** The timeline of §23.9 was there and hidden behind a button; it is now the contact screen itself — the card on the right, meetings, tasks, notes and their attachments from every server on the left, each row saying *why* it matched (attendee by `mailto:` versus a mention in the text). That is the product's own argument for keeping four sections side by side, and it was the hardest thing to find in the old mockups.

  **Files became a file manager**, not a table with two forms under it: selection, group operations, rename and move (one `Move` over the `MOVE` the transport already has), an upload queue that asks about a taken name instead of refusing silently, a details panel with a stated rule for when it is open, grid view, and the collections root as the section's own unified view.

  **Collection parity became a rule with a table** (§2.1): a feature meaningful for several kinds of collection is built for all of them at once, and each cell says *doing*, *not applicable* (with the reason) or *later* (with the place it is written down). It immediately paid: davloom now proxies WebDAV folders, and backup copies files as files.

  **Backup is a list of jobs**, each with its own sources — including file collections — destination (WebDAV, download, or both), trigger and retention; restore now starts from a screen that asks *which archive* — from a job, from a file, or uploaded — and asks for the archive password before anything else.

  **Planned features are drawn, not described:** new device (Apple profile, DAVx5 QR, copy rows), backup and restore, publication by secret link in all five kinds — calendar, address book, note, file, folder — with a `webcal://` subscription line for what can be subscribed to, external feed subscription with its own screen, and davloom with per-device app passwords and two levels of read-only. Section 12 covers the desktop wrapper against the plan above: Remote/Local onboarding, tray, global quick note, notifications, and the local-run screen that states plainly that running locally moves the *server*, not the data, and marks with a `local` badge what needs reachability from the internet.

  **New screens for operating the thing:** an installation check that asks Carrel about itself from outside — external reachability, certificate, proxy headers, SSE buffering, body-size ceiling, clock, data directory — with what to do for each failure, because most «it does not work» reports are the reverse proxy.

  **Answers to the questions the mockups raised, folded back in.** Markdown in a note is rendered — the decision, not another hedge, and it costs `goldmark` with raw HTML off. Restore lives beside backup, in the Backup header, and starts by asking which archive; the archive password became a checkbox (§23.3 says encryption is non-negotiable and will need the same edit); the app password for an external run appears on a button press with the `curl` line beside it. Operations in the file manager left the details panel: they appear from the first selected object and are repeated in every row's menu, so closing the panel takes nothing away. A published folder carries a read-only WebDAV address that Windows, macOS and Linux mount as a drive; a published calendar carries a `webcal://` line. Account, Appearance and the header menu are drawn; the square with initials is gone, because an account has no photograph to show. In davloom the device list leads with what each device can see, and that scope is editable without re-issuing its password.

  **Completeness is checked against a list, not by eye.** Every template and route now sits in a table beside the mockup that shows it, and the six pages that fall out of every such list are drawn: changing a password (ordinary and forced), cropping a contact photo, key escrow from the administrator's side, importing notes from a WebDAV folder, the two one-time-link pages and About. What has no mockup are htmx fragments, which are part of the screen they are swapped into. The settings menu was reordered to follow one question — who you are, where the data comes from, how to take it to a device, where to keep a copy, what to hand out, how it looks — because Account had been standing second to last, which is to say nowhere. The parity table gained a legend that answers what its verdicts mean: **делаем** is a screen without code, drawn so the feature is not designed twice; **позже** is neither, with the place it is written down.

  **Width discipline was corrected twice, and the second time systemically.** Helper classes each carried a character cap — 88ch on a banner, 74ch on a hint — which at 11–13 px lands around 400–550 pixels whatever the column is doing, so banners wrapped halfway across a wide screen. Caps are gone from banners, hints and empty states; what keeps a measure is what is read as prose: the note body at 72ch with its Full width / Reading width switch, and the pages that are nothing but text.

  **The brand guide now says how to build screens, not just how they look.** It gained three sections: how the mark and the logotype are applied (where each goes, the 88 px floor below which the logotype gives way to the mark, clear space, the forbidden things — recolouring into a collection colour, the mark beside the logotype, the lamp used as a feature icon); how icons are chosen and placed (Tabler outline, sizes by row, when an icon may stand without a label, and the rule that a new feature takes an icon from the forty already in use or admits it needs a word); and **how to design a screen** — the frame's four zones, width, the three row heights and the label-line alignment, colour, density, what a screen must say out loud, when a dialogue may ask a question, when a setting is not a setting, collection parity, and language. It closes with a ten-point check to run before drawing anything new.

  **Final sweep for Russian left in the mockups.** The interface strings had been cleaned earlier; this pass caught what a text scan misses. Dates were still rendered in Russian in about forty places — «Понедельник · 10 августа» — while the product formats them in English (`Monday, 2 January 2006`); six tooltips lived in `title` attributes, which no visible-text scan sees; and two explanations sat inside a mock instead of below it. What stayed Russian is what should be: the user's own names, collections, notes and file names. Two §23.8 details that had no mockup at all were drawn: a collection's sync state (read, changed, count) in Connections, and an event's original time zone beside the time when it differs.

  **Installing offers a portable copy (§12.1).** The installer asks one question — whose copy this is — in consequences rather than paths: just for me, for everyone on this computer, or **portable**, a folder that is unpacked and never installed: app, server binary and encrypted state inside it, nothing in the registry, nothing in the profile, moved by moving the folder. It is the answer for a work computer without administrator rights, somebody else's machine, or a stick — and the price is stated on the same screen: no start-up entry, updates only while the folder is writable, and a lost stick is a lost state file, encrypted but in someone else's hands. Linux gets this for free from the tarball.

  **The desktop app got the parts that were missing or invented.** «Instances» — switching between several Carrel servers — is gone: it was never discussed, contradicts the wrapper plan (one instance per OS user) and nobody could have said how it works. In its place is what the app actually has: the address it is a window onto, and signing out to change the mode. The **dynamic port** the plan calls for is finally visible: the local run does not ask for a port, it says the system picked one at this start and why — nothing to collide with a busy 8080 — and pins it only when access from the network is switched on, because a phone and DAVx5 remember an address. **Updating** is drawn for the first time (§12.1): an update downloads in the background, is checked by signature and waits — «applied when the app closes, or now» — and the case everybody forgets is drawn too: the app is newer than the server it is a window onto, which it says plainly and does not offer to fix, because it cannot reach into somebody else's machine.

  **Publish dialogues stopped asking what is being published.** They publish what was selected, and their heading says which object it is: the «This file / This folder» and «This card / The whole book» switches are gone. Two more false choices went with them — subfolders are included in a published folder by definition, and «allow mounting as read-only» decided nothing, because a link is read-only either way, so the mountable address is simply stated. «List attachments by name» became a real option instead: publish the attachments too, each getting its own link that expires and is revoked with the note — naming files nobody can open was a taunt. Tags never appear on a public page (the author's own labels), the date always does, and the calendar dialogue is no longer drawn twice: it lives in the panel of the screen that owns it. `.vcf` now offers download **and subscription**, the way `.ics` always did.

  **Answers to things that were wrong on the mockups themselves.** The photo crop states what it saves (512 px square, JPEG, ~90 KB) and why the size is the card's size. The `local` badge became a real chip — 16 px, tinted, centred against the heading — instead of an outlined word sitting a pixel low. «One address for every device instead of five accounts» lost the invented number. `Measure` became `Reading width`, because a typographic term on a button explains nothing. The public Markdown page renders its Markdown instead of showing hashes and dashes under a caption claiming it is parsed. Every details panel now has the ✕ its own rule promised — seven of ten did not.

  **A form row aligns from the top, on the label line.** Rows used to align on their bottom edge, which held only while cells were the same shape. The moment the port field gained the hint explaining the dynamic port, its cell grew by twenty pixels and the checkbox beside it — honestly pinned to the bottom of the row — slid down against the explanation. Cells now align from the top, and a cell without a label has an empty label line, so its control always sits level with the field next to it however much text hangs underneath. The checker gained a second pass for the same reason: the first compares controls already on one line and is therefore blind to a control that has drifted far enough to look like a line of its own; the second decides what a line is from the cells, not from the controls. Turned back on the old rule, it finds the drift on six rows.

  **A form row now has one height, and a checker that says so.** The checkbox beside «Port» on the local-run screen sat nine pixels below the field, because a field had a height and a checkbox took its own from the text. That is not a typo on one screen: it was true of every checkbox standing beside a field, and four screens had been propped up by hand to hide it. Field, button, segmented switch and lone checkbox are now 28 px in the primitives, a cell holding only a checkbox sits on the row's baseline by itself, and dense checkbox lists are left alone — two in a cell is a list, not a row. The file carries the proof: open it with `#check` and it walks every form row, compares the vertical centres and outlines whatever drifts by more than 1.5 px. It also found the rest — a small button standing among fields, a subscription address that could not wrap and pushed its table under the details panel, and dense administrative tables that overflowed their pane, which now drop a second-tier column below 700 px and scroll below 620.

  **Interface strings were brought back to the product's language and voice.** A pass over the whole document replaced ~200 Russian chrome strings with the English the templates use, restored the wording that already exists in the templates instead of inventing new, moved design rationale out of the screens and into the captions, and removed the one emoji glyph that had crept onto a button. The rule is now stated where it can be checked: interface strings in English, data in Russian, reasoning only under the mockup.

**Основной объём v1 закрыт (§19).** Этапы 2–7 — транспорт и discovery, контакты, календарь, задачи и заметки с единым видом и поиском, дубликаты, WebDAV-файлы и вложения — реализованы; **v0.7.0**. Остаётся ручная приёмка: [docs/manual-acceptance.md](docs/manual-acceptance.md). Что не сделано и что делаться не будет: [docs/roadmap.md](docs/roadmap.md).

### Added

- **Stage 6 — `internal/merge`, detection that costs no extra requests (§15):** a record is folded once into the handful of values it is compared on — UID, the normalised name, addresses, the significant tail of each telephone number, the birthday, an event's start — and everything else is scored on that. Scoring is points rather than a probability, because the threshold is a setting an administrator can raise or lower and a number is easier to reason about than a model nobody can inspect: a shared address, telephone number or UID identifies a person on its own (60 and past the default), a name is a hint (30, or less as it gets further from an exact match) and a birthday only strengthens a match that already exists. A shared name and a shared birthday reach 50 and stay a near miss until somebody lowers the threshold on purpose, which is the conservative default §15 asks for — a false positive is a suggestion a person has to reject, and one of those is worse than a duplicate that goes unnoticed. Numbers are compared by their significant tail rather than a guessed country code, so `+7 495 123-45-67`, `8 495 123-45-67` and `495 123-45-67` are one number; names are compared with the words sorted, so «Ivan Petrov» and «Petrov, Ivan» are two clients and not two people. Only records that share a bucket — an address, a number, a UID, the opening letters of a name, an exact start — are scored against each other, so a book of thousands is not compared with itself card by card, and the pairs that do score are joined into groups, so a card sharing an address with one and a number with another is one person rather than two overlapping pairs.
- **Stage 6 — the duplicates screen (§15):** `/app/duplicates` polls every ticked address book and calendar over the fan-out of stage 5, with the same per-source progress, retry and cancel, and scores what arrives. A group is offered with the reason it was proposed — «same address», «same phone» — beside the score, because a reason is something a person can check. Each group offers exactly the three doors §15 fixes: **link** them, mark them **not duplicates**, or, for a group already decided about, put it back on the list. Linking writes to no server at all: the records stay where they are and are shown as one, which is the whole difference between it and merging. Events are polled over a window around today rather than every event a calendar has ever held, because loading a decade to find a double invitation is a cost nobody asked for.
- **Stage 6 — merged fields and remembered choices (§15):** a linked group shows one set of fields: a field only one record carries is taken as it is, a repeatable field — numbers, addresses, mail addresses, links — is the union with the exact duplicates removed rather than one record's winning, and a single-value field the records disagree about is the one case the person is asked. The answer is remembered with the group, and a remembered value that no record offers any more falls back to the merge order instead of being invented.
- **Stage 6 — decisions on the volume, sealed (§15, §21):** a verdict is stored in the same DEK-sealed blob as the DAV credentials, because an account paired with a collection and a UID is a list of what is in somebody's collections and not something a stolen volume should give away. These are the only data about the contents of a person's collections that Carrel keeps on disk, and they are metadata only: an account, a collection path, a UID, and which value won a field. A group marked «not duplicates» stays marked after a restart, and a record belongs to one group at a time — deciding about it again moves it and dissolves a group left with one member. The key of a member was never stable: a record another client deleted or moved is dropped from its group silently, and only a collection that actually answered the poll can say something is missing from it — treating a failed or unticked source's silence as a deletion would dissolve groups because one server was briefly down (§17).
- **Stage 6 — badges and collapsed rows (§15):** the merged directory shows a group as one row with the union of its numbers and addresses, a badge saying how many records it stands for, and the collections they live in; the badge leads to the screen where the decision is made. The badge is on a single address book's list too, where the record is. A pair the person rejected is never collapsed, which is what makes «not duplicates» outlast the session it was clicked in.
- **Stage 6 — merging on the server, the destructive one (§15):** for contacts, a group can be merged into one card on one server. It is confirmed first, and the confirmation names what will be written, what will be deleted and what the kept card will gain. The order is the whole of the safety: the merged card is written first, conditionally on the version it was just read at, and a source is deleted only after that write has been confirmed — a failed PUT deletes nothing at all. The merged card only ever gains: repeatable properties become the union, a property the cards disagree about stays as the target has it, and every participant's X- properties are carried over precisely because this build does not know what they mean. A delete that fails stops the rest; what has gone and what has not is said plainly and nothing is rolled back, because undoing the write would lose what was merged into it. A collection without write access is offered as unavailable rather than tried, and a submitted object path that is not inside the collection it claims is refused rather than sent to somebody's server.
- **Stage 6 — configuration:** `duplicates.threshold` in the file and `CARREL_DUPLICATES_THRESHOLD` in the environment, defaulting to 60. What counts as the same person differs between one person's address books and another's: a shared family telephone number is one person in one and two people in the other.
- **Stage 6 — tests:** the scoring table of §15 (one strong signal reaches the threshold, name and birthday together do not, different kinds never score, a card with nothing to score on matches nothing), phone and name normalisation including `tel:` URIs and short codes, partial birthdays, clustering through shared signals and the rejected pair that is never grouped, the threshold changing what is offered, field merge with a conflict and a stale preference, and a merged patch that adds without overwriting; decisions moving a record between groups, dissolving a group of one, pruning a member that has gone, and surviving both sealing and a restart of the store; over HTTP against two address books on a fake server: candidates offered with their reason, linking storing the choice and writing nothing to the server, a linked group collapsing to one badged row in the merged list and in the address book's own list, a rejected pair not being offered or collapsed again, a foreign collection in a submitted form being refused, the merge confirming before it writes, then writing once and deleting the source, keeping every source when the write fails, reporting a partial cleanup without rolling back, and a group dissolving when another client deletes one of its records.

- **Stage 5 (block A) — tasks (VTODO):** `/app/tasks` lists one collection's tasks with open/done/all filters, counts and an overdue marker, ordered by what still needs doing and soonest due first. A tick on a row is a three-property edit (`STATUS`, `COMPLETED`, `PERCENT-COMPLETE`) rather than a rebuilt object, so everything else on the task — including properties written by another client — stays byte for byte (§8). Create, edit and delete go through the same conditional-write and §9 conflict path as events.
- **Stage 5 (block B) — notes (VJOURNAL, §23.9 in full):** `/app/notes` lists a collection newest first with an excerpt and tag filter; the card edits title, body, date, tags and links. A **New note** button sits in the navigation bar on every screen and leads to a one-field form that files into the collection last written to — a note that costs a form is a note nobody writes. `RELATED-TO` links notes, tasks and events both ways: the note card and the event card show what they are attached to, and an event offers to write the minutes it will be linked to. A contact card opens a **timeline** of everything that person appears in across every ticked calendar, matched on their addresses first and their display name second.
- **Stage 5 (block C) — Markdown import/export of notes (§23.9):** one note downloads as Markdown with YAML front matter (title, date, tags, uid, related, account, collection) and a `carrel_properties` block that carries whatever had no field of its own, so an export loses nothing §8 keeps. A collection downloads as a zip streamed straight to the response, with names built from the date and a transliterated title and never silently reused. Import reads a `.md` file or a zip of them, with or without front matter, previews titles, dates, tags, parse errors and UID collisions against the target collection, and writes only on confirmation; import always creates, and a UID that is already there gets a fresh one and a line in the report rather than overwriting the note it collides with.
- **Stage 5 (blocks D, F) — unified view and cross-source search (§14, §16):** `/app/unified` polls every ticked calendar over one date range, optionally narrowed to events, tasks or notes, and merges the answers into one list by time — a slow source lands in its place rather than at the end. `/app/search` searches calendars and address books at once through `calendar-query` text matches and one `addressbook-query` per book. Which collections a screen polls is a per-view choice stored encrypted in the account blob, so it outlives the session and a restart; an empty choice is honoured as an empty choice rather than reset to everything.
- **Stage 5 (block E) — `internal/fanout` and per-source progress (§16, §17):** a task owns one goroutine per source behind a parallelism gate, reports each source as waiting, querying, done, empty, timed out, cancelled or unavailable, and says which answers came from the session cache. A source timeout and an overall ceiling both mark whatever is outstanding instead of leaving an indicator that never stops; a failed source has a Retry that polls it alone; cancelling keeps the partial results on screen with the interrupted source marked. Tasks belong to the session that started them, are capped per session, swept when nobody asks about them, and cancelled when the session ends, so a person clicking through searches cannot accumulate live polls. Progress reaches the browser over one event-source connection that closes itself when the poll ends, with an automatic fallback to polling when the stream will not open (§13); `CARREL_PROGRESS_MODE=poll` turns streaming off for a proxy that buffers.
- **Stage 5 — `internal/model` generalised beyond VEVENT:** `NewTodo`, `NewJournal` and a primary-component lookup that treats VEVENT, VTODO and VJOURNAL alike, so patching, UID assignment and property-loss checking work the same for all three; `Todo` and `Note` display views; `Relation` parsing and rendering for `RELATED-TO` (the default `RELTYPE=PARENT` is not written out); email normalisation shared by vCard and iCalendar for the timeline.
- **Stage 5 — tests:** fan-out merge order, per-source and overall timeouts, retry, cancellation keeping partial results, a cancelled task opening no further connections, and concurrent snapshots against retries and subscribers (the goroutine-leak and race gate of §21 — `-race` needs a machine with a C compiler); component queries returning only the component asked for even when the server answers with everything, cached component sets, calendar search across components without duplicates, and `addressbook-query` any-of matching; over HTTP against a fake calendar: the task list separating open from done, a tick keeping an unknown property, task create writing a conditional VTODO, the notes list and tag filter, the quick note filing into the remembered collection, Markdown export front matter and the zip, an import previewing a UID collision then creating under a fresh UID, the unified view and search following a poll to completion through the results fragment and the event stream, an unknown poll answering 410 so the poller stops, and an empty source selection being honoured.

- **Stage 4 (phases 0–11) — calendar agenda, CRUD, import/export, print:** CalDAV VEVENT over `calendar-query` / `calendar-multiget`; RRULE expansion with `rrule-go` (whole series only); agenda UI grouped by day with a date range; event create/edit/delete with a structured RRULE editor; §9 conflict screen; session body and range caches; import/export of standard `.ics`; `@media print` for the agenda. Dependencies `github.com/emersion/go-ical` and `github.com/teambition/rrule-go` in `THIRD_PARTY.md`.
- **Stage 4 — `internal/model` iCal:** `KindICal`, `ParseICal` / `NewEvent` / `Event` / `ExpandOccurrences`, Patch/Apply on the primary VEVENT so unknown properties survive, and `.ics` import splitting.
- **Stage 4 — `internal/provider/calendar`:** listing, query-by-range, multiget, conditional PUT/DELETE, property-loss verification, and 412 conflicts carrying both versions.
- **Stage 4 — tests:** CalDAV report bodies; RRULE weekly expansion in range; If-Match 412 → conflict; unknown iCal properties kept after Apply; agenda empty state, import UID collision, and print chrome on the agenda.

- **Stage 3 (phase 8) — thumbnail cache (§12):** photo thumbnails sit in the per-session cache keyed by account, object path and ETag, so a changed card is a miss rather than a stale hit. A stricter byte ceiling (default 16 MiB) and entry cap (512) evict LRU thumbnails; wipe on logout/expiry clears them with the rest of the session cache. `GET …/photo?size=thumb` serves from the cache after the first decode.
- **Stage 3 (phase 9) — import `.vcf`:** upload a standard vCard file or a `.zip` of `.vcf` files, preview counts and parse errors against the target address book, then confirm. Import always creates; a UID that already exists gets a fresh UID and a line in the report. Cyrillic and multi-card files are accepted; Takeout-specific layouts stay out of scope (§23.7).
- **Stage 3 (phase 10) — export `.vcf`:** download the current address book as a single `.vcf` attachment (`Content-Disposition`), bodies taken through the same multiget path as the list.
- **Stage 3 (phase 11) — print (§23.6):** `@media print` hides nav, sidebar, forms and buttons; source labels are text as well as colour; black on white; `break-inside: avoid` on rows; a capture-date footer; optional photos via a checkbox that toggles `print-with-photos` before `window.print()`.
- **Stage 3 (phase 12) — tests:** thumbnail hit/miss/LRU/wipe; multi-card and Cyrillic parse; zip import; AssignUID; handler coverage for import preview (UID collision), confirm, export headers/body, and print chrome on the list.
- **Stage 3 (phase 4) — conflicts 412 (§9):** a refused precondition no longer ends as an error page. The refused edit is kept in the session, the server version is shown beside it as a property-level diff (PHOTO base64 truncated), and the person chooses keep server, apply mine, or cancel — never an automatic overwrite. Applying mine re-reads the current ETag and writes conditionally again; another 412 reopens the same screen.
- **Stage 3 (phase 5) — contact list:** address books in the sidebar and under `/app/contacts`; bodies arrive through `addressbook-multiget` in batches of 50 while the list is scrolled (`hx-trigger="revealed"`). Reopening an unchanged collection still uses the session cache from phases 2–3. Read-only books list contacts without a New button.
- **Stage 3 (phase 6) — card form via Apply:** create, edit and delete go through `Get` → `Patch` → `Apply` → conditional PUT. The form never rebuilds an object from its fields alone, so X- properties and other unknowns stay on the card (shown read-only). A first-time property loss after save is surfaced as a notice; empties remove properties rather than writing blank ones.
- **Stage 3 (phase 7) — photos (§11):** `GET /c/{account}/{collection}/{uid}/photo` serves inline JPEG/PNG/GIF/WebP (or proxies a URI photo through the SSRF guard), uses the object ETag, and falls back to a deterministic SVG of initials when there is none. Upload streams to a temp file, checks dimensions before decode, applies EXIF orientation, strips metadata by re-encoding, and offers htmx pan/zoom/rotate crop before `Apply` writes PHOTO in the card's own vCard version. Delete removes PHOTO entirely. Config defaults: max side 512, JPEG quality 85, 100 MP pixel ceiling.
- **Stage 3 (phase 0) — dependency:** `github.com/emersion/go-vcard` for vCard parsing and serialisation, recorded in `THIRD_PARTY.md`.
- **Stage 3 (phase 1) — `internal/model`, the object that cannot be rebuilt from a form:** an `Object` carries its path, its ETag and its parsed payload, and the payload is unexported (§8). Reading goes out through `Contact`, a deliberately lossy display view, or through `Properties`; writing goes in through `Patch`, which names the properties it touches and leaves every other one exactly as the server sent it. There is no way to hand back a whole object assembled from the fields a form happens to know about, which is how X- properties, groups, categories and attachments written by other clients disappear from a card without anyone noticing. A patch is checked in full before any of it is carried out, so a rejected patch changes nothing; `VERSION` and `UID` are refused outright — the first is the format the object is written back in (§11) and the second is its identity. Deleting a property is `Remove` rather than an empty value, because those are different things to every other client (§11). Serialisation folds content lines at 75 octets on rune boundaries, which the encoder underneath does not do and which an inline photo needs.
- **Stage 3 (phase 2) — `internal/provider/contacts`:** the read path is the collection tag first, then the path→ETag map, then bodies through `addressbook-multiget` in batches (§12, §13). An unchanged collection tag keeps the cached map instead of re-reading every ETag, and a collection reopened inside the soft TTL costs no requests at all. Bodies are cached under path *and* ETag together, so a body cached at an older version is a miss rather than a stale hit. One card this build cannot parse costs that card and not the whole address book. Writes carry a precondition without exception: a create is conditional on nothing being there yet, an update on the version it was read at, and an update without one is refused rather than sent as an unconditional overwrite (§9). A refused precondition comes back as a conflict carrying both versions for the diff of phase 4 — never as an automatic overwrite in either direction. `Get` goes through a multiget because a plain GET carries the body but not the version, with a PROPFIND-and-GET fallback for servers that will not answer the report.
- **Stage 3 (phase 3) — property loss on write (§8):** after a successful PUT the stored object is read back and compared with what was sent, per property and per instance, ignoring the parameter order and the `REV`/`PRODID` a server is expected to stamp itself. What the server dropped, shortened or rewrote is reported to the person who saved — a notification, never a block, because the write already happened and the decision is theirs. Losses are aggregated per account: the first time a property goes it is said inline, and after that it belongs in the account's details, because a server that drops X- properties drops them from everything and saying so after every save only teaches people to dismiss the message. A property lost by more than one write is marked as a trait of that server rather than an accident.
- **Stage 3 — tests for the phases above:** the §21 criteria of the stage that can be checked without a server — a contact with X- properties keeping every original property after its name is edited, compared property by property; a vCard 3.0 still being 3.0 after its photo is replaced; a photo held as a link being shown but not offered for editing — plus a card written and read back serialising identically, so a difference after a PUT is the server's doing and not the encoder's. The two rewrites a round trip does make are named and pinned rather than left to be found: property names are upper-cased and a `TYPE` list becomes repeated parameters, both equivalent by RFC 6350. Over a fake address book: reopening an unchanged collection making no requests at all, an unchanged collection tag sparing the deep `PROPFIND` after the TTL has passed, multiget batching and keeping the order asked for, a body cached at an older version being a miss, a malformed card costing only itself, a second create at the same path being refused instead of overwriting, an edit made elsewhere first producing a conflict with both versions and no write, and a dropped X- property being reported once and aggregated afterwards. Handler coverage for the conflict screen on 412, the contact list and SVG photo placeholder, and a save that leaves X-CUSTOM on the card.

- **Stage 2 (phases 5–9) — cache, UI, and integration tests:** per-session collection cache with ETag maps, LRU eviction, TTL/`getctag` invalidation, and wipe on logout/SIGTERM; signed-in UI with sidebar (accounts, collections, connect/remove forms) and admin «Test DAV server» discovery validator; `compose.test.yaml` Baikal stack for local integration runs; unit tests for cache, discovery, and account handlers; `go test -tags=integration` Baikal discovery gate (`CARREL_TEST_DAV_*`, skips when unset). Admin user list shows real `DAVAccountCount` without decrypting secrets.

- **Stage 2 (phases 1–4) — transport and account storage:** `internal/config` DAV timeouts, SSRF allowlist, and session cache limits; `internal/dav` SSRF guard (§24.2), DAV transport with Multi-Status parsing, and discovery with step-by-step `DiscoveryTrace` (§6); `internal/account` secrets blob sealed under the user DEK; `store` API to add, list, update and delete DAV accounts in `User.Secrets`. Dependency `github.com/emersion/go-webdav` v0.7.0 recorded in `THIRD_PARTY.md`.
- **Public self-registration (§5.2).** The form at `/register` is off until an administrator publishes it (and only if SMTP is configured, because confirmation has to go out). The visitor chooses login, email and password; the account cannot sign in until they follow the link from the mailbox. A second attempt with the same login and address, while still unconfirmed, rotates the token and the password so a missed message can be retried. The login page carries the link only while the form is actually open; a closed instance answers 404 rather than advertising a form that will refuse every submission.
- **Local build and run scripts (Windows):** `scripts/build.bat` compiles `dist/carrel.exe` with version and commit from git (`CGO_ENABLED=0`, `-ldflags -X`). `scripts/run.bat` stops an already-running instance (same binary or the configured port), starts Carrel with `CARREL_DATA_DIR=dev/data`, waits for `/healthz`, and opens the service in the default browser. Layout matches [dev/local-testing.md](dev/local-testing.md): state in `dev/data/`, binary in `dist/`.
- **Stage 7 (block A) — file collections discover themselves (§6):** a plain collection under the account's root — one with neither the calendar nor the address book marker — is a file collection, and the Files section appears because one was found. There is no setting to turn it on, which is what §6 asks for. The containers the protocol's own trees live in are skipped rather than offered as folders: Baikal answers its root with `calendars/`, `addressbooks/` and `principals/`, none of them marked as anything at that depth, so a container that holds one of the discovered homes is left alone. A server with no calendars and no address books at all now connects instead of being refused, because a separate account for files is the arrangement §23.10 expects.
- **Stage 7 (block A) — `internal/provider/files`, the one provider that never buffers (§7):** §7 fixes `Get` at an `io.ReadCloser` rather than `[]byte` precisely so a file can go from the DAV server to the browser without landing on the heap, and this is the provider that spends that. A download is a copy between two streams: a 200 MB file costs a copy buffer per reader rather than 200 MB of resident memory, and it starts arriving before the server has finished sending it. An upload is the same in reverse. (Spending it took two goes: the response ceiling meant for XML was capping downloads at 10 MiB, which only a live server revealed — see **Fixed**.) `Range` is passed through, so a partial request is answered with the part rather than the whole. Listings are cached and bodies are not: a file section that kept what it served would turn the per-session ceiling of §12 into a suggestion, and a file is not reparsed on every view the way a vCard is. A directory is a DAV collection, so it is cached as one — the key is the directory, which gives it the soft TTL and the per-folder invalidation of §12 without inventing a second scheme.
- **Stage 7 (block A) — paths that cannot leave the collection (§24.4):** a relative path from a URL is refused segment by segment — `..` is rejected rather than normalised away, so an attempt to escape is refused on its own terms and shows up as one — and the joined result is then required to still sit under the collection root. Either check alone would do; both mean a mistake has to be made twice to matter. A backslash and any control byte are refused outright, because a backslash is legal in a DAV name and is a separator on one of the platforms this runs on, and that ambiguity is not something a path check should have to reason about. A name asked for as a name — an uploaded file, a new folder — is refused when it turns out to be a path. `Relative` is the inverse and is what checks a link that arrived from someone else's `ATTACH` against the collection it claims to be in.
- **Stage 7 (block A) — the Files screen:** one folder at a time, folders before files and both by name, with a breadcrumb back to the root and a way up. Size, type and modification time come from the `PROPFIND` that listed the folder, so a listing is one request. Upload is a create and never a replace: a name that is already taken is refused and said so, rather than overwriting a file the person did not know was there. A folder can be made and anything can be deleted, with the interface stating plainly that deleting removes the file from the server and that Carrel keeps no index of what linked to it. A read-only collection is browsable and offers no forms. A folder with more members than the configured ceiling says the list is not all of it, rather than growing a page and a `PROPFIND` response without limit.
- **Stage 7 (block A) — serving somebody else's files (§24.4):** a download carries `nosniff` and a `Content-Disposition` that names the file explicitly, in both the ASCII form every browser reads and the UTF-8 form that carries a name transliteration would lose. A picture and plain text are shown in place because that is the point of an attachment; everything else is offered as a file, which is also what keeps somebody's HTML from rendering on this origin. `application/pdf` is deliberately not on that list: a PDF viewer is a scripting surface and §23.10 puts previews out of scope anyway.
- **Stage 7 (block B) — `ATTACH`, a link and not a payload (§23.10):** the file goes on the person's own WebDAV and the entry carries a reference to it, so a screenshot in a note does not become half a megabyte of base64 that every client then syncs. The property is plain RFC 5545, which is the point — a link expressible only through an invention of ours would be readable by Carrel alone. `ATTACH` is now modelled on events and notes with its parameters read (`FMTTYPE`, `FILENAME` including the `X-FILENAME` older clients wrote, `SIZE`), and the size and type shown are what the writing client said rather than something Carrel went and measured, because checking would cost one request per attachment on every page that lists them. An attachment another client embedded as base64 is shown as it is and never rewritten into a link; each property is kept exactly as it arrived, so an edit that changes the set of attachments puts the others back byte for byte.
- **Stage 7 (block B) — attaching is one action (§23.10):** the folder is named once on the profile page, created if it is not there yet, and never asked for again — a folder chosen every time is what would make the feature dead on arrival. A picture pasted into a note with Ctrl+V, or dropped onto the card, goes straight up; both hand the file to the form that is already there, so they travel the same route, the same token and the same checks as choosing a file by hand. Names are built from the date and the entry's title rather than `image-1.png`, so the folder stays readable outside Carrel. The order is the safety: the file is written first and the property second, so a failed upload leaves the entry untouched — and when the upload succeeds but the entry has changed on the server meanwhile, that is said plainly and nothing is rolled back, because deleting the upload could delete a file another entry already points at.
- **Stage 7 (block B) — opening an attachment is a proxy, not a fetcher (§23.10, §24.2):** the URI never comes from the request. The object is read, the attachment at that index is looked at, and the link is resolved against the file collections this user actually holds credentials for; a link to anywhere else is shown with the reason it cannot be opened rather than fetched. Taking a URL out of an object and following it because the SSRF guard would probably refuse the bad ones would make Carrel a fetcher of whatever anybody can write into somebody's calendar, which is the opposite of what §24.2 is for.
- **Stage 7 (block B) — detaching is not deleting (§23.10):** removing a link rewrites the `ATTACH` set and leaves the file where it is, because another entry may point at the same one. The interface says so at the moment it happens and again beside the list, and points at the Files screen for when deletion is actually meant. Carrel applies no quota, no cleanup and no garbage collection to that folder: it is the person's storage and what is in it is theirs to manage.
- **Stage 7 (block B) — degradation (§17):** an unreachable file server is a missing attachment and not a broken entry. The card renders from the properties alone and makes no request per attachment, so it cannot fail because storage is down; the click on one comes back as a gateway error naming what happened, and the file browser reports the failure rather than answering 500.
- **Stage 7 (block B) — Markdown carries the links (§23.9):** an export writes the attachment links into the front matter and an import puts them back, filling in the file name from the reference and the type from its extension, so the substance of an attachment survives the round trip. What is not carried is stated rather than discovered: an attachment another client embedded as base64 has no link, is read-only anyway, and a note file with a megabyte of encoded image in its front matter is not a note file.
- **Stage 7 (block B) — import `.md` from WebDAV (§23.9):** a folder of notes already on the person's own storage previews and imports without being downloaded and uploaded again. Files are read one at a time and each is capped, so a folder somebody filled with a gigabyte of text costs the ceiling rather than the gigabyte; only `.md` directly in the named folder is read, subfolders are not walked, and nothing on the file server is moved or deleted.
- **Stage 7 — configuration:** `files.max_upload_bytes` (`CARREL_FILES_MAX_UPLOAD_BYTES`, default 256 MiB) and `files.max_entries` (`CARREL_FILES_MAX_ENTRIES`, default 2000). The upload ceiling is generous because nothing buffers the file — the cost of a large one is bandwidth and not memory — and the listing ceiling is not, because a listing is a page and a response.
- **Stage 7 — tests:** path resolution against traversal in both directions, a name that only looks like one, and the backslash and control bytes; listing separating folders from files and not reaching into a subfolder; a megabyte read out of a stream in two goes; a range returning the middle of a file; a refused conditional create leaving the original; a taken name yielding the next one without touching what was there; `EnsureDir` creating a chain once and being content the second time; a folder listing cached inside the TTL at no request and a write making it a miss; the listing ceiling truncating. `ATTACH` parsed with its parameters across a folded line, an inline attachment marked and left alone, the property modelled rather than listed as foreign while `X-JTX-COLOR` still is, a detach rewriting the set and preserving the inline one's parameters and an unrelated property, the last one removing the property rather than emptying it, a round trip reporting no loss under §8, and the Markdown links surviving export and import. Over HTTP against a server holding both a calendar and two file collections: the navigation entry appearing only when a plain collection exists, the listing and the breadcrumb, download headers and body, a traversal in a download URL answering 404, an upload refusing to overwrite, a read-only collection refusing writes and offering no forms, mkdir and delete, the whole of §23.10 in one pass (folder named once, file stored under a date-and-title name, `ATTACH` written as a URI with a file name and not as base64, the card showing it with its proxy), the proxy serving the bytes, a foreign link shown but refused, an inline attachment refused with a reason and no write, detaching leaving the file and saying so, an unreachable file server still rendering the card, a card with no folder configured pointing at the setting, and a folder of Markdown importing from WebDAV without disturbing it.

### Changed

- **DAV transport:** `REPORT` and a conditional `PUT` (media type, `If-Match`, `If-None-Match: *`) are available on the client as `Reporter` and `ConditionalPutter`, outside the `Transport` interface that §7 fixes at the plain DAV methods. `IsPreconditionFailed` and `StatusCode` name a 412 for the conflict path (§9). The session cache exposes the collection tag its ETag map was read at, so an unchanged tag can spare the deep `PROPFIND`.

- **Invitations:** two separate admin flows — copy a **link** (no mail) or **send by email** (SMTP required; the administrator never sees the link). The invitee chooses their own login on accept; email is fixed only for email invitations. Resend applies to email invitations only.
- **`/about`:** source link points to [https://github.com/mixeme/carrel](https://github.com/mixeme/carrel).
- **Account creation is three ready methods, not a mode.** The global "User creation mode" setting chose between an invitation and a temporary password and hid one of them. Both were needed, and self-registration sat in Settings as a checkbox with no form behind it. The three ways now live together on **Add users**: invitation (link or email), a temporary password handed over in person, and a switch that publishes `/register`. Settings keeps invitation lifetime and session timeouts; it no longer pretends to pick a single way people join.
- **User deletion is a button, not a form.** The user list no longer asks the administrator to retype the login before deleting an account. **Delete** sits with the other per-user actions; the browser asks once to confirm.
- **Files is always in the navigation.** The section used to appear only after discovery found a plain WebDAV collection on a connected account. It is now a permanent entry alongside Contacts and Calendar; the empty Files screen points at the profile page the way the other sections do.
- **Contact card collapses empty fields.** On an existing card, unfilled properties stay in the form (so filling one is still a patch, not a rebuild) but start hidden. **Show empty fields** reveals them in place. A new contact still shows every field.
- **Administration is split into subsection pages.** The panel was one sheet of unrelated forms — users, invitations, mail, escrow, a DAV probe and the audit log. It is now five pages behind the same `/admin/` guard: users (the landing screen), invitations, settings, key escrow, and the audit log, with a local nav between them. A form still posts to its own page, so a saved setting does not dump the administrator back onto the user list.
- **DAV validator is its own administration page.** The discovery probe lived at the bottom of Settings alongside mail configuration. It is now `/admin/dav` with its own tab, because it tests a remote server rather than changing instance settings.
- **Roadmap: full DAV server test.** The administration validator is discovery-only today. [docs/roadmap.md](docs/roadmap.md) now records a planned second, opt-in mutating stage — create, exercise the operations Carrel actually uses, read back, delete — for server developers and administrators who need more than «collections were listed».
- **Build output directory:** the local binary is written to `dist/` rather than the repository root; `.gitignore` ignores `/dist/` instead of `/carrel.exe` and `/carrel`.
- **`go test -race ./...` passes across all seventeen packages.** It had been the one automated gate left open, because the development machine did not have gcc on `PATH` for part of this work and `-race` refuses to build without a C compiler. Run with MSYS2's UCRT64 toolchain it is clean — no data race anywhere, including the gate §21 actually cares about, `internal/fanout`: concurrent snapshots taken against retries and subscribers, cancellation mid-poll, and a cancelled task opening no further connections. That one is the reason the flag matters at all; the rest of the suite passing under it is reassurance rather than news.
- **The integration tests were run against live servers for the first time, and found three bugs.** They had been written, tagged `integration` and left to skip themselves; every run of `go test -tags=integration ./...` in this work reported `ok` in a couple of seconds, which is what a suite that skips everything looks like. Pointed at a real Baikal and a real SFTPGo they failed immediately, and each failure was a defect in Carrel rather than in a server: discovery could not reach a principal under a base path, a download was truncated at the response ceiling, and a create trusted a precondition one of the servers ignores. All three are in **Fixed** below, each with a regression test that reproduces the real behaviour against a fake server, so the offline suite now covers what only a live one revealed. All four live tests pass.

  Worth recording as a lesson rather than a fix: a fake DAV server agrees with whatever the code assumes. Both the principal bug and the precondition bug were invisible for exactly that reason — the fake put DAV at the root and honoured every header — and the ceiling bug survived because the offline test used a file smaller than the ceiling. A test tier that skips silently when unconfigured is a tier nobody notices is not running.

- **§25 checked against the competitor analysis it was derived from, which is now in the repository and cited.** The source document sat beside the specification unnamed and unlinked; §25 said «источник — конкурентный анализ августа 2026» and left the reader to take that on faith. It is now linked, with §25 explicitly the summary and the source the place to go for the quotations and the full caveats. Reading them side by side confirmed every Carrel capability the analysis names is accounted for, and corrected four facts: the competitor table is back, because prose could not carry «AgenDAV requires a database» and «MMDL supports several accounts» at once; the alternativeto quotation behind the anti-Nextcloud argument; KOrganizer in the VJOURNAL ecosystem; and the DAVx5 pain — every account set up separately on every device — which is the reason §23.1 and §23.2 exist and was previously implied by their existence rather than stated.

  The one thing worth calling a correction rather than an addition: **multi-account on its own is not a differentiator, and §25 now says so.** MMDL's own README claims «supports multiple CalDAV accounts, and multiple user accounts». What separates Carrel is *what* is merged (contacts and notes, not only calendars and tasks), *how* (a live proxy with no local copy) and *what is then done with it* (duplicates across servers). Compressing §25.1 into prose had quietly dropped that column, and a positioning claim that a reader can check and find false is worse than no claim.

The specification was written to be built from, and once something is built the instructions for building it are worse than nothing: two descriptions of the same thing, of which one is always the stale one. - **[docs/visual/carrel-logotype.html](docs/visual/carrel-logotype.html) — the wordmark, variant 2, as a reference file.** [docs/visual/carrel-wordmarks.html](docs/visual/carrel-wordmarks.html) offered five approaches and the second is chosen: the word ends in an «l», which is already a vertical stem, so the lamp sits on it and the mark becomes a letter rather than standing next to one. What that file holds is a sketch and not a file — measured against Georgia's own metrics, «Carre» at that size ends at 135.54 and the left sidebearing of an «l» is 4.71, so the stem belongs at 140.25; it is drawn at 193.6, pushed out by nearly four times the whole width of the letter. Read at size it is not a word but «Carre» with an object beside it.

  **The letters are Literata converted to curves, and the lamp is fitted to the font — not the other way round.** Two earlier attempts drew the letters by hand, first as a transitional antiqua and then as a grotesque, and both were rejected. The reason is the same for both and is worth recording: the tool this mark is built with is a ring between two ellipses plus a rectangle, and that tool cannot express what a real typeface's letters are made of — a bracketed serif flowing into the stem, an inclined stress axis, a teardrop terminal, a fillet at a join. Drawing produced sticks abutted to stems and contrast landing mechanically at three and nine o'clock. Dropping serifs for the grotesque removed the most visible symptom but not the cause.

  So the principle is inverted, which is what the variant's own verdict asked for from the start — *«requires the height and thickness of the stem to be fitted by hand to the chosen face»*. The «l» stays a glyph of the font, entire: its stem, its sidebearings and its foot serif are the font's. The lamp replaces the **upper** serif, and that replacement is forced rather than chosen — the upper serif of an «l» is a wide horizontal at the very top of the letter while the dome of a shade is narrow at its apex, so leaving the serif under the dome produces two whiskers poking out either side. The base is the other part that does not carry over: its job in the icon is to stand the lamp on a surface, and here the «l»'s own foot serif already does that.

  **The lamp is transferred whole, by one coefficient, rather than fitted part by part.** The only size imposed from outside is the stalk, which is the font's stem, 8.41; the icon's stalk is 6, so the coefficient is 1.4014 and everything else follows it — shade 84.08, dome 42.04, skirt 8.41, collar 16.82 × 8.41. Seven of the icon's internal ratios then hold at once, checked by program against a tolerance of 0.002 rather than asserted: shade to stalk 10, dome to shade 0.5, skirt to stalk 1, collar width and height to stalk 2 and 1, collar to shade 0.2, and the collar's own 2 : 1.

  That took three tries, and the failures share one shape. The shade was first 30 — a number carried over from the hand-drawn versions, justified only by clearing the serif — then 46.38, the x-height, chosen inside a band settled by eye. Both were picked *for the shade alone*, and each broke ratios the icon holds between parts: at 30 the shade stood to the stalk as 3.6 against the icon's 10, at 46.38 as 5.5. The collar went the same way, sized at two stems because the icon's collar is two stems, which preserved the one ratio that was easy and broke the two that carry the look. **While one part is fitted, the rest drift; when the sign is scaled whole, there is nothing left to drift.**

  Vertical placement is the one thing the coefficient does not give, and it comes from the glyph: the skirt's underside sits below the lower edge of the «l»'s upper serif, whose depth is measured by scanning down the outline until the width returns to the stem's — 4.34 in Literata. The transferred skirt is 8.41 thick and 84.08 wide against a required minimum of 26.58, so both conditions clear with room to spare, which is a consequence of the lamp being larger than anything that had been fitted by hand.

  One consequence is stated rather than left to be noticed: the shade is symmetrical, so it reaches as far right as it does left, to 295.87, while the word ends at 268.16 — some 28 units of the box are shade over empty space. An asymmetrical shade leaning over the word was drawn and rejected, because it contradicts the icon and agreement with the icon is what this version is for.

  **Spacing is no longer invented.** The word is shaped by harfbuzz with kerning on, so the letters sit where they would in typeset text, and the lamp takes the position the shaper assigned to the «l». The two hand-drawn versions each needed a bespoke metric to space themselves — one by area of white, one by minimum clearance — and both of those problems disappear with the font's own tables. The measured result is reported in the file rather than designed: minimum clearance 5.27 … 14.79 across the five pairs, with «el» the roomiest, and the note says explicitly not to tighten it.

  **Checked against the font itself.** Each of the six glyphs is emitted to curves and its area compared with the same glyph's area in the font: worst disagreement 0.004 %, which is the residue of flattening curves into points, so the extraction pipeline distorts nothing. The serif coverage is verified by testing three points of the «l»'s upper serif — left edge, axis, right edge — for containment in the skirt. The dome is a semicircle, so the icon's «no kink at the skirt» invariant holds verbatim. One ordering constraint is now load-bearing and stated as such: ink first, shade second, because the covered serif is still in the path and surfaces if the order is reversed. The collar has a check of its own, and it exists because of a bug worth recording: a local variable shadowed the parameter that switched the collar on, so for one commit the shape was computed and never written into the path — while the report printed its width and height from the computation rather than from the geometry, and a visual read mistook the bare stem for the collar. The file's own output had said so, the SVG returning to its exact pre-collar byte count. The check is now positive: a point beside the stem inside the collar's band must be filled and a point past its edge must not be, and it was verified to fail with the collar switched off.

  **This closes the brand-guide conflict the previous version had to leave open.** The guide assigns the logotype to Literata or Source Serif 4; the grotesque version stood as a stated exception to it. The file now uses Literata 3.103 at wght 400, opsz 72 — the maximum optical size, because a logotype lives large — so guide and reference agree. The letters ship as outlines, so no font is needed to display the mark; the font is needed only to rebuild the file, and the version is recorded because a future release of the face could move the «l»'s metrics and would require re-measuring the serif.

  Left open and stated rather than discovered: the logotype exists for the word «Carrel» in latin and nothing else; the file is pinned to that font version; and §8 of [docs/visual/carrel-icon.html](docs/visual/carrel-icon.html), the clear-space rule for setting the mark beside the wordmark, is inapplicable here — variant 2 forbids that pairing, because the mark is already inside the word — and is left without a replacement rather than silently reinterpreted. [docs/visual/carrel-wordmarks.html](docs/visual/carrel-wordmarks.html) is kept as the record of the choice and says on its face that it is not a file to build from.

### Fixed

- **Multipart CSRF:** mutating multipart posts (photo upload, contact import) can carry the token in the form field; the middleware no longer requires the `X-CSRF-Token` header for those bodies alone.
- **`PROPFIND` and `REPORT` asked for nothing recognisable:** the requested property names were serialised as the name of the Go field holding them (`<Raw><Name></Name>…`), so every request handed the server a body naming no property it knew, and servers answered with whatever they chose instead of what was asked for. Stage 2 discovery happened to work through that leniency; `addressbook-multiget` does not, since it has to name both `getetag` and `address-data` to get anything back. Requested properties are now emitted as themselves, under their own namespaces, and the request bodies are asserted in tests.
- **Calendar agenda and search failed against Baikal with HTTP 400.** A `calendar-query` REPORT was sent with `Depth: 0`; SabreDAV requires `Depth: 1` (RFC 4791 §7.8) and answers the wrong depth with `BadRequest`. The agenda, component queries and cross-source calendar search now send the depth the spec names; `calendar-multiget` stays at `Depth: 0`, which is what that report requires. A regression test pins the header on the transport.

- **A dedicated WebDAV account could not be added.** Discovery required `current-user-principal`, which is a CalDAV/CardDAV property a files-only server — SFTPGo, Apache `mod_dav`, the Go `net/webdav` package — does not advertise. The trace the connection screen showed was exactly that: `.well-known` 404s, the entered URL answering 200, then `no current-user-principal at /`. A Multi-Status without the property is now treated as files-only and the entered URL becomes the file collection; a 401, or HTML where a Multi-Status should be, is still a failure. The existing files-only test still put a fake principal on the mock, so this was the same class of miss as the Baikal-under-a-path bug: the fake agreed with the code. Three tests now cover a server that does not name the property, the same server under a path with a web page at the site root, and a 401 that must not be mistaken for it.

- **Connecting to Baikal by its direct URL never worked, and no test could have caught it.** `findPrincipal` asked for `current-user-principal` at the hardcoded path `/`, and resolving a path that starts with a slash replaces the base path entirely — so an account entered as `https://host/dav.php/` had its principal looked for at `https://host/`, the web server's home page, which answers `200 OK` with HTML rather than `207` with a multistatus. §6 calls the entered URL **the main path** precisely because Baikal's `.well-known` usually is not configured, so this broke the ordinary case since stage 2. Every discovery test passed throughout, because a fake server puts DAV at its root and there was no site root to hit. The principal is now asked for at the base path first and the server root second, and every response is examined rather than only the first; two tests reproduce the real arrangement, one with a trailing slash and one without.
- **A file download was capped at 10 MiB.** `Get` wrapped every body in the `MaxResponseBytes` ceiling, which exists so that XML a provider parses into memory cannot grow without bound. Applied to a file it put an arbitrary limit — the default 10 MiB — on what a person may keep on their own server, which is the opposite of why §7 makes `Get` return a reader, and directly contradicts the §21 criterion that a 10 MB download work. There is now `GetStream` without the ceiling, used by the files provider alone; the contacts and calendar providers keep the capped `Get`, where the cap is a real protection.
- **A create could overwrite a file, on a server that accepts the precondition and ignores it.** An upload asked not to replace anything by sending `If-None-Match: *`, which is the correct way to ask and is not enough: SFTPGo 2.7.1 accepts the header and overwrites regardless. So "an upload never overwrites" was false on it without any sign, and attaching two screenshots to one note on one day — which generates the same name from the same date and title — silently replaced the first, leaving the earlier entry's `ATTACH` pointing at the second one's picture. A create now asks whether the path is free before writing **and** still sends the precondition; only a clear answer counts, so a server that will not say does not block the write. Tests cover both halves against a fake server that ignores the header exactly as that one does.

- **A multipart upload over 1 MiB was refused as a CSRF failure.** The body limit of §24.4 was applied before routing at a flat 1 MiB, and the CSRF check of §24.5 reads a multipart form to find the token a plain HTML form carries as a field. Past a megabyte the check was reading a body the limit had already truncated, so it found no token and answered 403 — for an import, a photo or an attachment whose token was perfectly good, and with a message that pointed at the wrong thing entirely. The ceiling is now chosen per request before anything touches the body, from the configured limit of whichever path it is, and each handler still applies its own; the smaller of the two wins and neither is load-bearing alone. An upload whose token arrived in a header — every htmx post, and the paste and drop of §23.10 — is still streamed rather than spooled.

### Added

- **Stage 0 — project scaffold:** Go module `gitea.mixdep.ru/mix/carrel`, `cmd/carrel/main.go` with version/commit ldflags, package layout per spec §3, `go:embed` for templates and static assets, vendored htmx 2.0.9 and htmx-sse extension, `LICENSE` (AGPL-3.0-or-later), `THIRD_PARTY.md`, SPDX headers in source files.

- **Stage 2 — crypto layer:** `internal/crypto` implementing the key schedule of spec §4. Argon2id with separate cost profiles for login verification, KEK derivation and the escrow master password (strengthened: 256 MiB / 6 passes), stored alongside each salt so costs can be raised later. Separate salts for the two uses of a password, constant-time digest comparison, `Equal` for invite-token digests.
- DEK handling: 32-byte random DEK, AES-256-GCM wrap/unwrap under the KEK, per-use AAD constants so a wrapped DEK cannot be replayed as sealed state. Changing a password re-wraps the DEK only and leaves data encrypted under it readable.
- Server key: generated on first run in the data directory (`server.key`, `O_EXCL`, mode 0600), never overwritten; a short or unreadable key file is reported as corrupt instead of being replaced. `SealState`/`OpenState` protect service data that must be readable before anyone logs in.
- Escrow (§5.4): X25519 key pair, private key sealed under the master password and never cached, DEK copies encrypted to the public key so depositing needs no secret. Master password change re-seals the private key only; minimum master password length enforced at 16 characters.
- `Key.Zero`/`Zero` for explicit wiping of key material (§24.6); uniform `ErrDecrypt` for every authentication failure.
- Unit tests: derivation and salt separation, wrap/unwrap round trips, password change, wrong password and tampered ciphertext, AAD domain separation, server key persistence and corruption, escrow round trip, cross-escrow isolation and master password rotation.

- **Stage 3 — persistence:** `internal/store` keeps the whole service state in one file on the volume (`state.enc`), sealed with the server key. An empty volume yields a store in bootstrap mode and nothing is written until the first change, so `docker run` on a fresh volume lands on the setup screen. Writes go through a temporary file and a rename, and a change becomes visible in memory only after it has reached the disk — a rejected or failed write leaves neither the record nor its audit entry behind. The format carries a version number and a migration hook; a file from a newer build is refused rather than guessed at.
- User records (§5.1): login verifier, KEK salt and Argon2id parameters, wrapped DEK, optional escrow copy, and a per-user blob for the DAV credentials of stage 2. The parameters travel with each record so costs can be raised later without locking anyone out. `Authenticate` verifies the password and returns the unwrapped DEK for the session keyring; an unknown login, a wrong password and an account that never set one all fail alike. Password change re-wraps the DEK and keeps the data readable; the administrator's reset replaces it and drops the blob, and is refused outright when the account is covered by escrow (§5.5). The last administrator cannot be deleted, demoted or disabled.
- Invites (§5.3): one-time tokens of 32 random bytes, stored as digests only, with expiry, revoke, extend and resend. Unknown, revoked, expired and already-accepted tokens return one indistinguishable error and every candidate digest is compared in constant time (§24.3). A pending invite reserves its login. Creating and accepting an invite works with SMTP completely unset; a failed delivery is recorded without invalidating the link (§21).
- Global settings with the defaults later stages consume: creation mode, self-registration off, invite TTL, session timeouts, SMTP with its password sealed under the server key, and escrow flags. Escrow is off on a fresh volume, applies only to users created after it is enabled, and disabling it leaves already-deposited copies alone.
- Append-only audit log written in the same atomic commit as the change it describes, filterable by action, actor, target and time, bounded so a long-lived instance cannot grow the state file without limit. Entries carry no passwords, tokens or object contents (§5.5).
- **Stage 4 — sessions and web security:** `internal/session` holds sessions and the DEK keyring in memory only, so a restart logs everyone out. Each login gets a fresh identifier and CSRF token (§24.5), with idle and absolute timeouts, `Rotate` for later privilege changes, and per-user teardown for "disable" and "kill sessions". Every path that ends a session — logout, expiry, sweep, `Close` — wipes the DEK explicitly rather than leaving it to the collector (§24.6); a periodic sweeper does the same on `SIGTERM`.
- `internal/ratelimit`: progressive per-key delay that doubles after a few free attempts and is capped, used with the client address and the submitted login together, so neither one attacker address nor one targeted account can be hammered.
- `internal/web/handler` middleware: security headers with a CSP that never allows inline scripts (htmx works through attributes), `X-Frame-Options`, `nosniff`, `Referrer-Policy`, `no-referrer` for pages whose URL holds a token, and HSTS only when the request demonstrably arrived over TLS. Session cookies are `HttpOnly`, `SameSite=Lax`, and `Secure` only then. Trusted-proxy handling walks `X-Forwarded-For` from the right and stops at the first untrusted hop, so a client cannot forge the address the rate limiter counts. CSRF is checked on every mutating request from the session token, or from a double-submit cookie for the setup, login and invite forms, and accepts both the hidden field and the htmx header. `RequireAuth`/`RequireAdmin` guard `/app` and `/admin`, answering htmx with `HX-Redirect` rather than a swapped-in login page, and the post-login `next` parameter is restricted to same-origin paths.
- Server wiring: store opened at startup with the bootstrap state logged, request body limit, panic recovery, `/healthz` that discloses neither version nor user count (§24.3) and issues no cookies, and a graceful shutdown that drains requests for 15s and then wipes the keyring.
- Tests: state encryption and reload, atomic write leaving no stray files, invite indistinguishability, last-admin guard, DEK preserved across a password change and replaced by a reset, escrow not applied retroactively, audit bounds and absence of secrets; session expiry, rotation, teardown and key wiping; rate limiter progression and key independence; header, cookie, CSRF, guard and proxy-trust behaviour over `httptest`.

- **Stage 5 — bootstrap and authentication:** an empty volume sends every visitor to `/setup`, where the first administrator is created; the screen redirects to the login form the moment an administrator exists, so it cannot be used to mint a second one (§5.1). Setup signs the new administrator in through a normal authentication rather than taking key material out of the create call, so the DEK still only ever reaches whoever proves the password (§4).
- `/login` and `/logout`: a successful login gets a fresh session and CSRF token, stamps the last-login time and writes an audit entry; logout ends the session, wipes its DEK and clears the cookie. An unknown login, a wrong password and a disabled account all come back as the same message on the same page — which of the three it was goes to the audit log only (§24.3). The login form is throttled by client address and by submitted login together, and a success clears the counters it was throttled under.
- «Forgot password» leads to a page that explains why there is nothing behind it: without the password there is no KEK, so no reset can return the data, and the two real options — a destructive reset or an escrow recovery — are named instead (§5.3).
- Post-login destinations: administrators land on the panel, everyone else on their own page; a `next` parameter is followed only when it is same-origin. `/app` and `/admin` are mounted as whole sections behind `RequireAuth` and `RequireAdmin`, so a route added inside them later cannot miss the guard.
- `internal/web/handler` page rendering: templates parsed once at startup against a shared frame — a broken template fails the process, not one request — and each page rendered into a buffer first so a failure halfway through cannot leave a truncated body behind a 200. Every page is `no-store`. Screens for setup, login, recovery, and placeholders for the profile and the panel that steps 9–11 replace; base stylesheet extended to match.
- Tests over the real middleware chain: the whole bootstrap → login → logout cycle, setup closing after first use, rejected forms leaving no account and not echoing the password, failed logins being byte-identical for unknown and wrong-password cases, throttling with `Retry-After` that holds even for a correct password, CSRF required on the login form, a plain user landing on `/app` and refused at `/admin`, and `next` honoured only for same-origin paths.

- **Stage 6 — invitations and registration:** administrators create invitations from the panel with login, optional email and role; the one-time link is always shown with a copy button and delivery status (`not configured`, `pending`, `sent`, `failed`) independent of whether mail goes out. `ResendInvite` rotates the token so a fresh link can be handed over when the digest is all that was kept; revoke and extend work on pending invites. `GET/POST /invite/<token>` lets the bearer choose a password — login and email come from the invite, not the form — and signs them in; invalid tokens are indistinguishable and the page carries `no-referrer`. When creation mode is `admin_password`, the panel creates users with a temporary password and a warning that the administrator can sign in as them until it is changed. Public invite and email-confirmation routes are rate-limited separately from login.
- **Stage 7 — SMTP (`internal/mail`):** relay settings in the admin panel — host, port, TLS mode (STARTTLS, implicit, none), username, sealed password, from address and name. «Send test email» runs synchronously and prints the full SMTP transcript. `Queue` delivers invite and email-change messages asynchronously with exponential backoff; failures are logged and recorded through `RecordInviteSend` without invalidating the link. Plain-text plus minimal HTML templates for invitations, address confirmation and escrow recovery notices — no external resources. Profile email change posts to `/app/email`, queues a confirmation message, and `GET /confirm-email/<token>` applies the new address after the bearer proves receipt.
- Unit and integration tests: invite resend rotates the digest, email-change round trip and expiry, template content, and bootstrap → admin → create invite → accept → login over the real handler chain.

- **Stage 8 — key escrow (§5.4):** off on a fresh volume and turned on from the panel, which states plainly what it is — not a key backup but a way in: an administrator holding the master password can decrypt a covered user's saved DAV credentials, and through them their contacts and calendars. Enabling generates the recovery key pair once and covers accounts created from then on; a second setup is refused rather than allowed to orphan the copies already taken. Deposit can be paused and resumed, and resuming asks for the master password so that a scheme nobody can still open is not switched back on. Changing the master password re-seals the private key alone, so no one has to deposit again.
- Recovery: the master password opens the deposited copy of the user's data key, which is re-wrapped under a temporary password the administrator hands over. The key itself never changes, so the account's connections survive — this is the alternative the destructive reset refuses in favour of, and the refusal now names it. Recovery ends the account's sessions, is written to the audit log, and mails the user a notice that the administrator cannot suppress; when the instance has no relay or no address on file, the panel says so and tells the administrator to deliver the message themselves. Guessing at the master password is rate-limited by client address, separately from the login form.
- Transparency, which §5.4 makes the condition for having the option at all: the profile always says whether a copy of the user's key is deposited, who could use it, when the account was last recovered, and whether withdrawal is allowed — including when the administrator has forbidden it. A covered user is shown an explicit notice at their first sign-in, once, and it is recorded as delivered.
- Voluntary participation for accounts that predate the scheme: a user joins from their own profile by entering their password, because their DEK cannot be opened without it — the same reason enabling escrow is never retroactive. Opting out deletes the copy and makes the account unrecoverable again, which is also what lets the destructive reset back in.

Graceful shutdown on SIGTERM drains requests for 15 seconds and wipes the session keyring; structured JSON logs to stdout never carry passwords or tokens.

- **Stage 14 — tests and acceptance (§21):** the acceptance criteria of stage 1 walked end to end over the real middleware chain — an empty volume, the first administrator, an invitation handed over by link alone with SMTP left unset, the account it creates, and that account signing in with the password it chose for itself. The checks that matter are made along the way: no credentials and no data key exist for an invited login until it is accepted, a spent link answers «gone» and only its digest was ever stored, and the new account is refused at the panel. Alongside it: an administrator's key cannot open another account's sealed data and the panel discloses none of it; disabling an account ends its live sessions and wipes their keys then and there, rather than at the next attempt to sign in; the last administrator survives deletion, demotion and disabling; and the destructive reset states what it destroys, and names escrow as the alternative, above the button that does it.
- Invite tokens: `NewToken` produces a full `TokenLen` of entropy in a form that needs no escaping in a URL path, and `HashToken` is deterministic, collision-free across tokens, and compared only through the constant-time `Equal` — including against a digest that differs in one bit, a truncated one and none at all.
- SMTP diagnostics (§5.3): the send path is exercised against a local relay that can be told to refuse. A missing configuration is reported without dialling, an unreachable relay names the address it tried, and a server's refusal is passed through in the server's own words — while the relay password stays out of the transcript that goes on screen.
- Fixed: a refused deletion — the last administrator, typically — signed the account out before the store rejected it, so the administrator lost their session to a change that never happened. The store now decides first.
- Трекер открытых пунктов этапа 1 — race-тесты, ручная приёмка A1–A9 в Docker, критерий полного закрытия; план и чеклист этапа 1 помечены к удалению как архивные.
