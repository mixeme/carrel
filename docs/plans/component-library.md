## 1. Контекст

Макеты описывают **87 именованных примитивов** с префиксом `.m-` и заканчиваются правилом: «классы из раздела 6 переносятся в `carrel.css` копированием, а не перерисовкой».

Копированием их не переносили ни разу. К началу работы в продакшене было **ноль** классов `.m-*` и **368** своих, потому что один и тот же примитив назывался заново на каждом экране:

| Примитив в макетах | Имён в `carrel.css` | Примеры |
|---|---|---|
| `.m-bar` — полоса действий | **16** | `.page-bar`, `.files-ops-bar`, `.dialog-acts`, `.dup-buttons`, `.note-read-bar`, `.src-bar`, `.form-actions`, `.conflict-actions` |
| `.m-head` + `.m-h1` + `.m-sub` — шапка | **28** в 11 семействах | `.page-head/-title/-sub`, `.detail-panel-head/-title/-sub`, `.note-read-head/-title/-sub`, `.dup-head`, `.person-head` |
| `.m-row` — строка списка | **25** в 13 семействах | `.contact-row`, `.task-row`, `.note-row`, `.find-row`, `.agenda-event-row`, `.src-row`, `.list-row` |

Это корень дефектов, которые разборы макетов находили поштучно: **размер и устройство знала соседняя разметка, а не компонент**. Отступ полосы брался у шапки сверху; у строки источника было четыре колонки, а разметка подавала пять; стрелку у выпадающего поля рисовали руками и забыли в 24 местах из 28. Пока у одной вещи шестнадцать имён, починка одного места ничего не говорит об остальных пятнадцати.

Волна 2.6 уже доказала, что лечится это ровно так: пять компонентов, типизированный вход вместо `map[string]any` и трое ворот, роняющих сборку. Задача — довести начатое до всей библиотеки.

## 2. Зафиксированные решения

| Тема | Решение |
|------|---------|
| Имена | **Из макетов, дословно** (`.m-bar`, `.m-head`, `.m-row`). Макет и экран становятся одной разметкой, и сверка на наборах превращается из слечения глазами в diff по узлам |
| Где живёт | **Отдельный каталог** `internal/web/component/`: разметка и стили рядом, плюс `README.md` — как пользоваться |
| Галерея в приложении | **Не делаем.** Каталог — сам каталог библиотеки и его README |
| Объём | Максимальный, разбит на этапы; этапы выполняются в разных сессиях |
| Порядок | Переезд и исправление — **никогда не один коммит**. Сначала примитив переезжает как есть, потом чинится |

## 3. Устройство

```
internal/web/component/
  README.md            документация: что есть, как звать, что нельзя
  tmpl/  m-*.html      по файлу на компонент
  css/   NN-*.css      по файлу на компонент, числовой префикс = порядок каскада
internal/web/handler/component.go   типы входа, сборка стилей
```

- `internal/web/embed.go` — `//go:embed component/*`.
- `LoadTemplates(pages, components)` парсит библиотеку в **каждую** страницу: вызов компонента, которого странице не досталось, роняет процесс на старте, а не запрос, который первым дойдёт до этой ветки.
- CSS склеивается **на старте** и отдаётся как `/static/component.css` первым `<link>` перед `carrel.css`. Собранный файл не коммитится: он расходится с исходниками, и этого никто не замечает — ровно та поломка, ради которой библиотека и заводится.
- `carrel.css` укорачивается каждым этапом: в нём должно остаться только то, что действительно принадлежит одному экрану.

Сборка экрана:

```gotemplate
{{template "m-head" (head "Title" "Combined calendar" "Subtitle" "5 of 7 calendars")}}
    <div class="m-acts">…действия экрана…</div>
{{template "m-headend"}}
```

### Что Э0 намеренно не сделал — закрыто в Э1, кроме

- **`datatable` и `importexportmenu` остались на месте.** У `datatable` класс приходит из места вызова (`Class "data"`, `"files-table"`), то есть примитив пока без единого имени; тащить это в библиотеку значит закрепить смысл, который надо развалить.
- **`.src-bar` и `.src-row` закрыты в Э5** (`.m-bar3` / `.m-src`).
- **`.dup-head` и `.note-read-title` не тронуты.** Рубрика группы дубликатов — Э6 (`.m-card` > `.m-rubric`); 27px заголовок заметки — `.m-title`, не шапка раздела.

## 5. Ворота

Трое существующих (`internal/web/handler/component_*_test.go`) расширены, добавлены новые:

| Ворота | Что держат |
|---|---|
| `TestComponentClassesStayInComponentFiles` | Класс компонента экран руками не пишет. Список классов **читается из стилей самой библиотеки**, поэтому новый компонент охраняется в день добавления. Исключения названы поимённо: `slotClasses` (слот вроде `.m-acts`) и `standaloneUse` (примитив отдельно от компонента, с указанием экрана) |
| `TestComponentLibraryIsComplete` | Компонент не может существовать в одной половине и отсутствовать в другой: разметка без стилей, любая половина без строки в README |
| `TestComponentStylesheetAssembles` | Склейка на старте работает и идёт в порядке имён |
| `TestEveryTemplateClassIsStyled` | У класса из шаблона есть правило — теперь и в библиотеке, и в `carrel.css` |
| `TestEveryShellScreenAssemblesInOrder` | Ровно одна шапка на экран, шапка раньше содержимого |
| Ворота типографической шкалы | `readStylesheet` отдаёт библиотеку **вместе** с `carrel.css` в порядке ссылок, иначе размер, попавший в компонент, окажется вне всех проверок |

## 7. Риски и что их снимает

| Риск | Чем снимается |
|---|---|
| Массовое переименование по 55 шаблонам | Ворота ловят и забытый класс, и класс без правила; `component_structure_test` рендерит **каждый** экран. В Э0 ворота сработали трижды по делу |
| Порядок каскада при склейке | Числовой префикс в имени файла |
| `carrel.js` завязан на классы | Почти всё на `data-*`; классовых селекторов: `.dots-menu`, `.m-row`, `.m-row.is-on`, `.m-row.is-task`, `.folder-tree-node.is-on` |
| Печать и узкий экран отвалятся | У `carrel.css` отдельные блоки для печати и узкого экрана; переносятся вместе со своим примитивом, а не отдельным этапом |
| Офлайн-оболочка не получит стилей | `offline-shell.html` подключает `component.css`, сервис-воркер держит его в precache |

## 8. Чего этот план не делает

- Не трогает `internal/desktop/` и davloom.
- Не меняет поведение экранов: это перекладка разметки и стилей, а не редизайн. Любое изменение вида — отдельное решение и отдельная строка в CHANGELOG.
- Не заводит препроцессор, сборщик и зависимости: склейка — двадцать строк на Go.
