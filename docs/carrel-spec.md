# Carrel — техническое задание

Версия документа: 1.1

---

## 1. Что это

Carrel — self-hosted веб-клиент для CalDAV, CardDAV и (на поздних этапах) WebDAV. Подключается к внешним DAV-серверам (Baikal, Davis, Radicale, Nextcloud), даёт полный CRUD над контактами, событиями, задачами и заметками. Многопользовательский, каждый пользователь подключает несколько DAV-аккаунтов одновременно и видит их содержимое в едином представлении.

**Ниша.** Прямых живых конкурентов почти нет: InfCloud заброшен с 2015, AgenDAV — только CalDAV и в maintenance mode, единственный активный аналог (MMDL) покрывает лишь календари и задачи и требует свою БД. Свободные сегменты — мультиаккаунтный unified view с дубликатами, веб-редактор VJOURNAL и read/write DAV-агрегатор. Ниша реальна, но узкая (self-hosted энтузиасты); подробный разбор рынка, акценты для README и риски — в §25.

**Название.** Carrel — индивидуальная кабинка в библиотеке, где работают с материалами, которые тебе не принадлежат. Это и есть точная метафора сервиса: своё рабочее место, чужие данные. В README указать именно библиотечное происхождение слова (и отграничить от ассоциации с Алексисом Каррелем).

## 2. Жёсткие ограничения

- **Go + htmx.** Никакого Node, npm, сборщиков, CDN. htmx и его SSE-расширение вендорятся в репозиторий.
- **Один бинарник.** Шаблоны, CSS, JS-вендоринг — через `go:embed`.
- **Один контейнер.** Ни базы данных, ни Redis, ни sidecar-процессов.
- **Источник истины — DAV-сервер.** Локальной персистентности контента нет. Кэш существует только в памяти сессии и не переживает рестарт.
- **Смотрит в интернет.** Работает за reverse-proxy, слушает HTTP, требует входа.
- **Не терять чужие данные.** Любое редактирование сохраняет неизвестные свойства vCard и iCal.
- **Изоляция пользователей.** Данные одного пользователя недоступны другому, включая администратора (кроме явно включённого депонирования ключа, см. §5.4).

Веб-фреймворки не использовать: достаточно `net/http` и `html/template`.

**Библиотеки:** `emersion/go-webdav`, `emersion/go-ical`, `emersion/go-vcard`, `teambition/rrule-go`, `golang.org/x/crypto/argon2`. Новые зависимости — только по согласованию.

## 4. Криптосхема

Пароль входа используется дважды, но по-разному. **Смешивать эти два применения нельзя.**

1. **Проверка логина.** `Argon2id(пароль, salt_auth)` → хэш. Сравнение constant-time.
2. **Ключ шифрования.** `Argon2id(пароль, salt_kek)` → KEK. KEK разворачивает DEK — случайные 32 байта, зашифрованные AES-256-GCM. DEK шифрует учётные данные DAV-аккаунтов и решения по дубликатам.

Соли разные, хранятся рядом с шифротекстом. Смена пароля перешифровывает только DEK, а не все подключения.

**DEK живёт только в памяти сессии.** Нет активной сессии — нет доступа к учёткам. Рестарт контейнера требует повторного входа. Это осознанное свойство, задокументировать в README.

Пароли DAV-серверов нужны в открытом виде для Basic-аутентификации при каждом запросе. Хэшировать их нельзя, только обратимо шифровать.

**Служебные данные** (список пользователей, роли, статусы, настройки SMTP) шифруются отдельным серверным ключом, лежащим на томе. Иначе список пользователей невозможно прочитать до входа кого-либо.

**Дополнительно:** rate limit на форму логина (по адресу и по учётной записи, с прогрессивной задержкой), CSRF-токены на всех мутирующих запросах, `Secure` на куках сессии при `X-Forwarded-Proto: https` от адреса из **явного списка доверенных прокси**, а не от любого источника.

## 5. Пользователи и администрирование

### 5.1 Модель

Две роли: администратор и пользователь. Каждый пользователь полностью изолирован: свои соли, свой DEK, свои подключения, свои решения по дубликатам, свой кэш сессии.

Администратор — обычный пользователь с дополнительными правами управления учётными записями. Своими DAV-аккаунтами пользуется так же, как все. **Доступа к данным других пользователей не имеет** — не по правилу в коде, а потому что у него нет их KEK. Исключение — явно включённое депонирование (§5.4).

**Первый запуск.** Пустой том ведёт на экран создания первого администратора. Никакого встроенного пароля по умолчанию.

### 5.2 Создание пользователей

Самостоятельная регистрация отсутствует. Опционально включается флагом в конфиге, по умолчанию выключена.

Два режима создания:

**Приглашение (по умолчанию).** Админ вводит логин и адрес почты. Генерируется одноразовый токен, отправляется письмо со ссылкой `https://host/invite/<token>`. Пользователь переходит, задаёт пароль, входит. Временный пароль не создаётся вообще: до первого входа у записи нет ни хэша пароля, ни солей, ни DEK. Админ пароль не знает ни на каком этапе.

**Пароль от админа.** Админ задаёт временный пароль, смена обязательна при первом входе. Проще при передаче из рук в руки, но до смены админ технически может войти под пользователем — вывести это предупреждением в интерфейсе.

### 5.3 Приглашения и почта

**Ссылка всегда доступна вручную.** Отправка по почте не должна быть единственным путём: SMTP может быть не настроен, письмо может не дойти. После создания приглашения панель показывает саму ссылку с кнопкой копирования независимо от статуса отправки. Статус отображается отдельно («отправлено», «ошибка отправки», «SMTP не настроен») и не блокирует работу с приглашением.

**Токен.** Не менее 32 байт из `crypto/rand`, base64url. В хранилище держится **только хэш токена**. Одноразовый, срок жизни по умолчанию 72 часа (настраивается). Сравнение constant-time, rate limit на эндпоинт. Действия админа: отправить повторно, отозвать, продлить.

**Настройка SMTP** в панели администратора: хост, порт, режим шифрования (STARTTLS, implicit TLS, без шифрования для локального релея), логин, пароль, адрес отправителя, отображаемое имя. Пароль SMTP шифруется серверным ключом. Обязательна кнопка «Отправить тестовое письмо» с показом полного ответа сервера.

Отправка асинхронная, с повторами и растущей задержкой. Провал доставки логируется, приглашение остаётся действительным.

В README упомянуть связку с SelfPost как рекомендуемый вариант локального релея.

**Содержание письма.** Простой текст плюс минимальный HTML, без картинок и внешних ресурсов. Кто пригласил, на какой сервис, ссылка, срок действия, строка «если вы не ожидали письма — проигнорируйте его». Никаких паролей и токенов вне самой ссылки.

**Почта в профиле.** Сохраняется в записи пользователя, меняется с подтверждением нового адреса письмом. Используется только для приглашений и служебных уведомлений.

**Восстановления пароля нет.** Без старого пароля DEK не развернуть. «Забыли пароль» на экране входа либо отсутствует, либо ведёт на страницу, честно объясняющую: восстановление невозможно, админ может лишь сбросить учётную запись с потерей подключений. Классический сброс по ссылке из письма реализовывать нельзя — он создаёт иллюзию восстановления, молча уничтожая данные.

### 5.4 Депонирование ключа (опция)

**По умолчанию выключено.** Включается администратором и **применяется только к пользователям, созданным после включения**: задним числом депонировать невозможно, чужой DEK без пароля владельца недоступен даже серверу. Существующие пользователи подключаются к схеме добровольно из своего профиля.

**Устройство.** При включении генерируется пара ключей. Публичный лежит открыто. Приватный шифруется мастер-паролем администратора, который **не совпадает** с его паролем входа и вводится только в момент восстановления. При создании пользователя его DEK дополнительно шифруется публичным ключом восстановления, копия кладётся рядом. Обычная работа схему не задействует.

**Восстановление.** Админ инициирует, вводит мастер-пароль, разворачивает приватный ключ, тот расшифровывает DEK пользователя, DEK перешифровывается под новый временный пароль. Пользователь входит и меняет пароль. Подключения целы.

**Обязательная прозрачность** — условие, без которого опцию делать не следует:

- Пользователь видит статус в профиле: депонирование включено или нет, кто может восстановить, когда это делалось в последний раз.
- При первом входе — явное уведомление, если схема активна.
- Каждое восстановление записывается в журнал и **уведомляет пользователя письмом** независимо от воли админа.
- Пользователь может отказаться от депонирования (его копия DEK удаляется). Админ может запретить отказ настройкой, но тогда пользователь видит и это.

**Формулировка в интерфейсе и README — честная.** Не «резервное копирование ключей», а прямо: администратор с мастер-паролем может получить доступ к сохранённым DAV-учётным данным пользователя, а значит к его контактам и календарям.

**Мастер-пароль.** Argon2id с усиленными параметрами относительно обычного входа, повышенная минимальная длина. Нигде не кэшируется: вводится, используется, стирается из памяти. Восстановление под rate limit и всегда в журнал. При утере мастер-пароля схема бесполезна — предупредить при включении, предложить сохранить его вне сервиса. Смена мастер-пароля перешифровывает только приватный ключ, копии DEK не трогает.

### 5.5 Панель администратора

- Список пользователей: логин, роль, дата создания, последний вход, число подключённых DAV-аккаунтов (именно число, не сами аккаунты), активные сессии
- Создать пользователя, выдать / отозвать / переотправить приглашение
- Отключить пользователя: вход запрещён, данные сохраняются, сессии завершаются немедленно
- Удалить пользователя: необратимо, стирает шифрованный стор, требует подтверждения вводом логина
- **Сбросить пароль — разрушительная операция.** Подключения пользователя становятся нечитаемыми и удаляются. Диалог обязан назвать последствия прямо, без эвфемизмов. Если для пользователя действует депонирование — вместо сброса предлагается восстановление.
- Завершить сессии пользователя
- Сменить роль (удаление последнего администратора запрещено)
- Глобальные настройки: режим создания пользователей, SMTP, депонирование, тайм-ауты сессий, лимиты кэша, тайм-ауты веерного опроса
- Журнал административных действий: вход, неудачные попытки, все действия админа, восстановления. Без паролей и содержимого записей.

**Смена пароля пользователем** — безопасная операция: перешифровывается только DEK, подключения остаются. Требует ввода текущего пароля.

## 6. Discovery

Пользователь вводит базовый URL, логин, пароль.

1. Попытка `.well-known/caldav` и `.well-known/carddav`, следовать редиректам.
2. При неудаче — введённый URL как есть. **Это основной путь.** У Baikal `.well-known` живёт в конфиге веб-сервера и часто не работает; надёжно подключение по `https://host/dav.php/`.
3. `PROPFIND` с `current-user-principal`.
4. Из принципала — `calendar-home-set` (ns CalDAV) и `addressbook-home-set` (ns CardDAV).
5. `PROPFIND Depth: 1` по обоим home-set.

Для каждой коллекции забирать: `displayname`, `resourcetype`, `calendar-color`, `supported-calendar-component-set`, `current-user-privilege-set`, `getctag`.

`current-user-privilege-set` определяет, показывать ли элементы редактирования. Коллекции только для чтения помечаются визуально.

**Один принципал отдаёт и календари, и адресные книги — аккаунт это одна такая связка**, а не отдельное подключение на протокол.

**Ограничение исходящих подключений (SSRF).** Пользователь задаёт произвольный URL, по которому Carrel идёт **с сервера**. Это SSRF по построению: без ограничений сервис становится инструментом сканирования внутренней сети хоста чужими руками. Требования обязательны для любого инстанса, а не только публичного (§24.2).

**Диагностика неудачи.** Discovery — самая частая точка отказа: не тот URL, `.well-known` не настроен веб-сервером, принципал не отдаётся, права урезаны. При неудаче экран подключения обязан показать, **на каком шаге сломалось и что ответил сервер**: что вернул `.well-known`, что вернул введённый URL, что ответил `PROPFIND current-user-principal`. Без этого пользователю нечего сообщить, кроме «не подключается».

Реализуется тем же кодом, что валидатор сервера в панели администратора, — применённым в момент первого подключения.

Файловые коллекции (`resourcetype: collection` без календарного и адресного маркера под корнем) определяются автоматически: есть — появляется раздел файлов, нет — не появляется. Отдельной настройки не заводить.

## 7. Транспорт

```go
type Transport interface {
    PropFind(ctx context.Context, path string, depth int, props []xml.Name) (*MultiStatus, error)
    Get(ctx context.Context, path string, rng *Range) (io.ReadCloser, string, error)
    Put(ctx context.Context, path string, body io.Reader, ifMatch string) (string, error)
    Delete(ctx context.Context, path, ifMatch string) error
    MkCol(ctx context.Context, path string) error
    Move(ctx context.Context, src, dst string, overwrite bool) error
}
```

`Get` возвращает `io.ReadCloser`, а не `[]byte` — **это принципиально**. Иначе файловый раздел потребует переписывать транспорт. Провайдеры контактов и календаря вычитывают поток целиком сразу, файловый пробрасывает его в браузер.

Транспорт ничего не знает про vCard и iCal.

## 8. Модель и сохранение чужих свойств

```go
type Object struct {
    Path string
    ETag string
    raw  *ical.Component // или *vcard.Card
}

func (o *Object) Apply(patch Patch) error
func (o *Object) Marshal() ([]byte, error)
```

`raw` **неэкспортируемый**. Наружу отдаётся только структура для отображения. Пересоздание объекта с нуля из полей формы должно быть физически невозможно — это защита от молчаливой потери `X-`полей, вложений, категорий и всего, что положили другие клиенты.

`Apply` трогает только свойства, явно указанные в патче.

**Контроль потерь при записи.** После успешного `PUT` перечитанный объект сравнивается с отправленным. Если сервер молча потерял свойства, пользователю показывается уведомление вида «сервер вернул объект без свойств X, Y» — не ошибка и не блокировка, решение принимает человек.

Это самая недооценённая проблема в CardDAV: потеря обнаруживается через месяцы, когда исходник уже не восстановить. Механизм сравнения всё равно нужен для тестов сохранения неизвестных свойств — не хватает только вывода результата наружу.

Повторяющиеся потери по одному серверу агрегируются: систематическая потеря `X-`полей — свойство сервера, а не случай, и сообщается один раз в свойствах аккаунта, а не при каждом сохранении.

## 9. Конфликты

Все мутации идут с `If-Match: <etag>`. При `412 Precondition Failed`:

1. Перечитать актуальную версию с сервера.
2. Показать построчный diff: версия сервера против правки пользователя.
3. Дать выбрать: оставить серверную, применить свою, отменить.

Никакой автоматической перезаписи.

## 10. Данные

**v1:** VEVENT, VTODO, VJOURNAL, vCard.

**RRULE.** Раскрытие повторов на своей стороне через `rrule-go`. Не полагаться на серверный `expand` — поддержка неровная. Редактирование **только серии целиком**. Отдельные экземпляры, `RECURRENCE-ID`, `EXDATE`, `THISANDFUTURE` — вне v1.

**Часовые пояса.** Один глобальный TZ из настроек, применяется ко всему отображению.

**Участники** (`ATTENDEE`, `PARTSTAT`) — только чтение, без iTIP-планирования.

**Замечание по VJOURNAL.** Клиенты существуют — jtx Board на Android, Evolution на десктопе, — но веб-звена в этой связке нет. Заметки не односторонние: совместимость с этими клиентами обязательна, сохранение неизвестных свойств действует полностью. Подробнее — §23.9.

## 11. Фотографии контактов

Показ и редактирование фотографий — обязательная часть v1.

**Хранение в vCard.** Формат зависит от версии. Писать надо **в той же версии, в какой объект пришёл**, не конвертировать:

- vCard 3.0: `PHOTO;ENCODING=b;TYPE=JPEG:<base64>`
- vCard 4.0: `PHOTO:data:image/jpeg;base64,<base64>`

`PHOTO` со ссылкой на внешний URI показывать как есть (проксируя запрос, а не отдавая браузеру чужой адрес). Редактирование для таких недоступно, пометить в интерфейсе.

**Отдача.** Отдельный эндпоинт, не инлайн в HTML:

```
GET /c/{account}/{collection}/{uid}/photo?size=thumb|full
```

`ETag` берётся от ETag объекта — при правке контакта фото инвалидируется автоматически. Заголовки: `Cache-Control: private, max-age=0, must-revalidate`, `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`. Отдавать только `image/jpeg`, `image/png`, `image/gif`, `image/webp`; остальное — 415, даже если сервер это принял.

**Заглушка.** При отсутствии фото — генерируемый на сервере SVG с инициалами и цветом, детерминированно выведенным из UID. Никаких внешних сервисов аватарок.

**Загрузка.**

1. Тело запроса писать потоком во временный файл, не в память. Жёсткого лимита на размер входного файла нет; опциональный потолок в конфиге, по умолчанию отключён.
2. `image.DecodeConfig` для чтения размеров **до** декодирования. Если ширина × высота превышает потолок в пикселях (по умолчанию 100 Мп, настраивается) — отказ с сообщением про разрешение. Байтовый лимит от декомпрессионных бомб не защищает: связь между размером файла и потреблением памяти отсутствует, декодер разворачивает изображение как ширина × высота × 4 байта.
3. Применить EXIF-ориентацию, затем **срезать все метаданные**. В EXIF бывают GPS-координаты и серийники камер — они не должны уехать на DAV-сервер и разойтись по всем клиентам, синхронизирующим книгу.
4. Привести к квадрату, сжать, перекодировать в JPEG.
5. Временный файл удалить в `defer`, в том числе при ошибке и при отмене кадрирования.

**Выходной размер — требует уточнения на практике.** Значения ниже стартовые, вынесены в конфиг и подлежат проверке на реальных данных до фиксации:

- максимальная сторона: 512 px
- качество JPEG: 85
- ориентир по весу в vCard: ~200 КБ

Что проверить перед фиксацией:

- Как выглядит в интерфейсе: 512 px может быть избыточно для списка и мало для крупного просмотра на HiDPI. Возможно, нужны два размера.
- Что переваривают серверы: у некоторых DAV-серверов есть потолок на размер объекта, base64 добавляет треть сверху. Проверить на Baikal, Radicale, Nextcloud.
- Как ведут себя чужие клиенты: DAVx5, Thunderbird, iOS, Android — корректность отображения и скорость синхронизации.
- Влияние на коллекцию целиком: книга на 500 контактов с фото по 200 КБ — это 100 МБ через `addressbook-multiget` при построении списка. Возможно, потолок придётся опустить именно из-за этого.

По результатам замеров зафиксировать значения в README как обоснованные. До этого они не входят в критерии приёмки.

**Кадрирование без JS.** Живого перетаскивания не будет — принятое ограничение стека. После загрузки показывается серверный предпросмотр квадрата с элементами управления: сдвиг по осям, масштаб, поворот на 90°. Каждое изменение — обычная htmx-отправка, возвращающая новый предпросмотр. Оригинал держится во временном буфере сессии до подтверждения. По умолчанию кадр по центру, чтобы пользователь мог ничего не трогать.

**Запись.** Только через `Object.Apply` с патчем на единственное свойство `PHOTO`. `PUT` с `If-Match`, конфликты по §9.

**Удаление.** Отдельное действие, удаляющее свойство `PHOTO` целиком, а не записывающее пустое значение.

**Права.** В коллекции только для чтения элементы загрузки и удаления не отображаются.

## 12. Кэш сессии

**Принцип.** Источник истины — DAV-сервер. Кэш живёт в памяти процесса, привязан к сессии, целиком уничтожается при выходе, истечении сессии и рестарте контейнера. **На диск не пишется ничего.** Это не синхронизация: фоновых обновлений нет, кэш наполняется только тем, что пользователь уже запросил.

**Что кэшируется:**

- Список коллекций и их свойства после discovery
- Ответы `PROPFIND Depth: 1` — карта URL → ETag по коллекции
- Тела объектов, ключ — путь + ETag
- Миниатюры фото, ключ — ETag объекта
- Раскрытые повторы RRULE по диапазону

**Инвалидация.** Ключ включает ETag, поэтому устаревшее тело физически недостижимо — при изменившемся ETag это промах. Дополнительно:

- После любого успешного `PUT` или `DELETE` запись по пути выбрасывается, новый ETag из ответа сохраняется.
- Перед чтением коллекции сверять `getctag` (или `sync-token`, если сервер отдаёт): не изменился — карта ETag берётся из кэша без запроса; изменился — перечитать `PROPFIND`.
- Мягкий TTL на карту коллекции (по умолчанию 60 секунд) для серверов без `getctag`.
- Кнопка «обновить» на каждом экране, сбрасывающая кэш этой коллекции.

**Границы.** Потолок памяти на сессию (по умолчанию ~64 МБ, в конфиге), вытеснение LRU. Отдельный, более жёсткий потолок на миниатюры. Общий потолок на все сессии процесса — иначе десяток пользователей с большими книгами упрётся в память контейнера; при достижении вытеснение по LRU через всех пользователей. При переполнении в первую очередь вытесняются тела объектов, карты ETag держатся дольше: они мелкие и дают наибольший выигрыш.

**Безопасность.** Кэш в памяти сессии, а не глобальный: данные разных пользователей и аккаунтов не смешиваются в общем пространстве. При выходе — явное обнуление. В README отметить: содержимое календарей и контактов присутствует в RSS процесса, поэтому дампы памяти и swap на хосте нежелательны.

**Чего кэш не делает.** Не позволяет работать при недоступном сервере — при отказе источника показывается ошибка, а не устаревшие данные. Не переживает рестарт. Не заменяет `If-Match`.

## 13. Интерфейс

**Календарь — списочная агенда**, сгруппированная по дням, с выбором диапазона. Никакой сетки и drag&drop: это принятое решение, а не упущение. `REPORT` с `time-range` возвращает ровно то, что нужно списку.

**Экраны:** вход, приглашение, список аккаунтов и подключение нового, контакты, агенда, задачи, заметки, единый вид, поиск, дубликаты, профиль, панель администратора, настройки, «О сервисе» (§22).

**Раскладка.** Слева источники с цветовыми метками, сгруппированные по аккаунтам, с чекбоксами. Справа содержимое. Переключение коллекции, открытие карточки, сохранение — htmx-фрагментами, страница целиком не перезагружается.

**Большие коллекции.** `PROPFIND Depth: 1` даёт все URL с ETag одним ответом; сами карточки тянуть батчами через `addressbook-multiget` / `calendar-multiget` по мере прокрутки. При повторных заходах данные берутся из кэша сессии.

#### Узкий экран: вспомогательный режим

**Мобильная версия — спасательный круг, а не основной способ работы.** Целевой сценарий: зашёл с телефона, потому что больше нечем, и сделал дело. Конкурент здесь не мобильный веб-клиент, а связка DAVx5 + нативное приложение, и по скорости веб проиграет ей всегда — поэтому целиться в паритет бессмысленно.

**Что входит в спасательный круг** (чтение и короткий ввод):

- посмотреть расписание,
- найти контакт и позвонить,
- быстро записать заметку (§23.9).

**Что сознательно не оптимизируется под узкий экран:** экран дубликатов с раскрытием групп, объединение записей, кадрирование фотографий, панель администратора, подключение и настройка аккаунтов. Не блокировать — но и не тратить силы на удобство; допустим упрощённый вид. **Функциональность можно урезать ради удобства оставшегося.**

**Требования:**

- Ниже 640 px — одна колонка, боковой рейл источников уезжает в выдвижную панель.
- Зоны нажатия не меньше 44 px. Чекбоксы источников по 9 px и цветные полоски по 3 px — размеры для мыши, на пальце их не взять.
- Шрифт полей ввода не меньше 16 px, иначе iOS зумит страницу при фокусе.
- Кнопка создания заметки остаётся доступной на узком экране: без неё требование «две секунды» на телефоне не работает.
- Прогресс веерного опроса: на мобильной сети SSE рвётся при переключении вышек, поэтому фолбэк с опросом статуса (§16) здесь не запасной вариант, а обычный сценарий.
- Кадрирование фото на узком экране — только кадр по центру, без ручной подгонки.

**В README сказать прямо:** тому, кто хочет удобно работать с телефона, правильный ответ — DAVx5 и jtx Board, а не мобильная вёрстка Carrel. Это снимает запросы на функции, которых там сознательно не будет.

#### Установка как приложение (PWA)

Интерфейс поставляется с манифестом и иконками, чтобы устанавливаться как приложение: своя иконка в доке, отдельное окно без вкладок и адресной строки, переключение по Alt+Tab.

**Зачем.** Инструмент, которым пользуются ежедневно, выигрывает от того, что отделён от тысячи вкладок в браузере. Плюс это закрывает десктопную нишу: Evolution существует только под Linux, а у Thunderbird календарь и контакты — придаток к почте без многоаккаунтного сведения. Кроссплатформенного клиента, сводящего несколько DAV-серверов, сегодня нет.

**Стоимость — один манифест и набор иконок,** без сборки, подписи и отдельного релизного цикла. Работает на всех платформах сразу.

**Следствия для вёрстки, которые надо соблюдать с самого начала:**

- Интерфейс не полагается на адресную строку и браузерные кнопки «назад» и «обновить»: в окне без хрома их нет. Навигация и обновление данных — собственными элементами.
- Манифест и иконки входят в `go:embed` вместе с остальной статикой.
- Service worker — минимальный: оболочка и статика. **Кэшировать содержимое коллекций он не должен** — это нарушило бы §2 (нет локальной персистентности контента) и дало бы устаревшие данные при недоступном сервере вопреки §12.

#### Язык интерфейса

**Английский, единственный.** Локализация не делается и рассматривается только при появлении аудитории, которой она нужна.

Практическое следствие для шаблонов: строки пишутся прямо в них, без слоя перевода, файлов сообщений и заготовок под будущие языки. Инфраструктура локализации «на всякий случай» — это лишний слой во всех шаблонах, который в отсутствие переводов не даёт ничего.

Если аудитория появится, вынесение строк — механическая работа, и делать её лучше по факту, зная реальный объём.

## 14. Единый вид

Сводный экран, показывающий записи из нескольких коллекций одновременно, независимо от того, на каких серверах они лежат. Работает для всех типов: контакты, события, задачи, заметки. Это главная причина существования сервиса.

**Выбор источников.** У каждой коллекции чекбокс в боковой панели. Выбор сохраняется в настройках (не в сессии) и переживает перезапуск. Наборы независимы по типам: календари для агенды и адресные книги для контактов выбираются отдельно.

**Слияние и сортировка.** Записи сводятся в один список и сортируются по естественному ключу типа: события и задачи по времени, контакты по отображаемому имени, заметки по дате. Группировка по источникам не применяется — смысл экрана в перемешанном порядке.

**Пометка происхождения.** Каждая строка несёт цветовую метку коллекции и подпись «аккаунт · коллекция». Это обязательно: одинаковые имена и совпадающие встречи в разных аккаунтах — нормальная ситуация, и пользователь должен видеть источник, не открывая запись.

**Редактирование.** Открытая из сводного вида запись правится в своей исходной коллекции, `PUT` уходит на её сервер. При создании новой записи целевая коллекция **выбирается явно** — контекста для угадывания нет.

**Стоимость.** Веерный запрос, требования те же, что у поиска: тайм-аут на источник, прогрессивная догрузка, пометка недоступных без падения остального (§16, §17).

## 15. Дубликаты

**Обнаружение.** На лету по уже загруженным записям, без дополнительных запросов к серверам.

Контакты — скоринг по признакам:

- совпадение нормализованного email (регистр, точки в gmail-адресах) — сильный
- совпадение телефона, приведённого к E.164 — сильный
- совпадение `UID` — сильный, но между серверами редкий
- близость `FN` (расстояние Левенштейна с нормализацией регистра и порядка слов) — слабый
- совпадение `BDAY` — слабый, усиливающий

События — совпадение `UID` (частый случай: одно приглашение попало в два аккаунта) либо совпадение `DTSTART` и `SUMMARY` при разных `UID`.

Порог настраиваемый, по умолчанию консервативный: ложное срабатывание должно быть заметно реже пропуска.

**Пометка.** Группа-кандидат сворачивается в одну строку с бейджем «2 источника», раскрывается по клику в подстроки с метками коллекций. Никаких автоматических действий. Отдельный экран «Дубликаты» показывает все найденные группы по типам.

**Решения пользователя** — три, все сохраняются локально:

- *Связать* (по умолчанию) — записи считаются одной сущностью, в сводном виде показываются одной строкой с объединёнными полями. **На серверах ничего не меняется.** Связь разрывается в любой момент.
- *Не дубликаты* — группа больше не предлагается. Отменяется на экране «Дубликаты».
- *Объединить на сервере* — разрушительная операция, см. ниже.

**Слияние полей при связывании.** Поле есть только в одной записи — берётся оно. Значения расходятся — показывается выбор, предпочтение запоминается. Многозначные поля (телефоны, адреса, email) объединяются в объединение множеств с удалением точных дублей, а не заменяются.

**Объединение на сервере.** Явное действие с подтверждением, перечисляющим, что будет удалено и откуда.

1. Пользователь выбирает целевую коллекцию.
2. Формируется объединённая vCard: за основу берётся `raw` целевой записи, из остальных добавляются недостающие свойства. Все `X-`поля всех участников сохраняются; при конфликте одноимённых — из целевой.
3. `PUT` в целевую коллекцию с `If-Match`.
4. **Только после подтверждённого успеха** — `DELETE` остальных, каждый со своим `If-Match`.
5. Если хоть один `DELETE` не прошёл, операция останавливается, пользователю показывается, что уже удалено, а что нет. Автоматический откат не выполняется.

В коллекциях без права записи объединение недоступно, вариант помечен как таковой.

**Хранение решений.** Это единственные данные о содержимом, которые Carrel держит на диске. Хранятся только метаданные, не содержимое записей:

```
account_id + collection_path + object_uid  →  группа | игнор
```

Плюс предпочтения полей для связанных групп. Шифруется тем же DEK, что и учётки.

Идентификатор нестабилен: объект могут удалить или перенести сторонним клиентом. Пропавший участник группы удаляется из неё молча, группа из одного участника распускается. Ошибок пользователю по этому поводу не показывать.

## 16. Поиск и прогресс веерного опроса

**Поиск** сквозной по всем выбранным источникам: `calendar-query` с `text-match` по календарным коллекциям, `addressbook-query` по адресным книгам.

Веерный запрос — самое дорогое место архитектуры, к нему относятся требования ниже. Они распространяются и на единый вид (§14).

**Модель задачи.** Веерный запрос — задача с идентификатором, живущая в сессии. Хендлер не блокируется до конца опроса: сразу отдаёт каркас со списком источников в состоянии «ожидание» и подключает обновления. Каждый источник опрашивается в своей горутине и меняет состояние независимо.

**Состояния источника:** ожидание → опрашивается → готово (N записей) / пусто / ошибка / тайм-аут / отменено.

**Сводная строка** над результатами: «Опрошено 4 из 7 источников · 23 записи · 1 недоступен». По завершении меняется на итог с временем выполнения. Пока опрос идёт — индикатор активности; когда закончился, он исчезает. Пользователь всегда должен понимать, закончился опрос или нет.

**Панель источников** раскрывается по клику: построчно аккаунт, коллекция, состояние, число найденного, длительность. Для ошибок — краткая причина (отказ соединения, 401, тайм-аут) и кнопка повтора **только этого источника**, без перезапуска всего опроса.

**Доставка обновлений.** Через SSE-расширение htmx: одно соединение на задачу, сервер шлёт фрагменты по мере готовности источников. Расширение вендорится вместе с htmx.

Фолбэк на случай, если SSE не проходит через reverse-proxy: опрос статуса через `hx-trigger="every 700ms"` с остановкой по завершении. Режим в конфиге, по умолчанию SSE с автоматическим переключением после неудачи.

**Порядок выдачи.** Записи вставляются в общий список сразу по приходу с сохранением сортировки, не в конец. Иначе список прыгает и читать его во время опроса невозможно.

**Тайм-ауты.** На источник — по умолчанию 10 секунд. Общий потолок на задачу — 30 секунд, после чего неответившие помечаются как тайм-аут, а задача считается завершённой. Пользователь никогда не остаётся с бесконечным индикатором.

**Отмена.** Уход со страницы, новый запрос или явная кнопка отменяют задачу: контексты горутин отменяются, соединения закрываются, частичные результаты остаются на экране с пометкой «опрос прерван».

**Кэш.** Источники, ответившие из кэша сессии, помечаются мгновенно и визуально отличаются от опрошенных заново — видно, что именно потребовало похода в сеть.

## 17. Деградация

Недоступность одного сервера **никогда** не роняет интерфейс. Коллекции такого аккаунта помечаются, работа с остальными продолжается. Ответ 500 на отказ источника — баг.

## 18. Поставка

**Один контейнер, ничего рядом.** Всё состояние — либо в памяти процесса (сессии, кэш), либо в одном файле настроек на томе.

**Образ.** Многостадийная сборка: `golang:alpine` для компиляции, `gcr.io/distroless/static` для финального слоя. `CGO_ENABLED=0`, статическая линковка, `-ldflags="-s -w"`, версия и коммит через `-X`. Шаблоны, CSS, htmx и SSE-расширение внутри бинарника через `go:embed`.

Мультиплатформенная сборка `linux/amd64` и `linux/arm64`. Теги: `latest`, мажорный (`1`), точный (`1.4.2`).

**Хостинг и CI.** Основной репозиторий — собственный Gitea, зеркало на GitHub. Всё публичное (issues, релизы, ссылки в интерфейсе и README) указывает на GitHub. Образы публикуются в `ghcr.io`, привязанный к зеркалу. CI собирается на GitHub Actions, поскольку сборка мультиплатформенных образов и публикация в GHCR происходят там же. Секреты не дублировать в Gitea; runner на своей стороне при необходимости добавляется позже, отдельной задачей.

**Запуск от непривилегированного пользователя,** файловая система контейнера только для чтения, единственный том — каталог настроек, все capabilities сброшены.

**Том.** По умолчанию `/var/lib/carrel`. Внутри: зашифрованные подключения, соли, обёрнутые DEK, записи пользователей, решения по дубликатам, ключ депонирования. Больше ничего на диск не пишется; временные файлы при загрузке фото создаются в `tmpfs` и удаляются в `defer`.

**Конфигурация** переменными окружения (приоритет) поверх опционального файла. Минимум для старта: порт, путь к каталогу данных, список доверенных адресов reverse-proxy. Первый запуск с пустым томом ведёт на экран создания администратора, а не падает.

**Десктопная обёртка возможна** (на будущее, не раньше живых пользователей и явного запроса). Тонкий клиент — окно с системным webview (Wails или Fyne). Стек этому не мешает: HTTP-слой отделён от способа запуска (§3), абсолютных путей и предположения об обязательном reverse-proxy в коде нет. Два режима подключения в одной обёртке:

1. **Удалённый.** Пользователь указывает адрес уже работающего инстанса (контейнер или сервер). Сервер остаётся отдельным процессом/контейнером; обёртка только открывает его UI.
2. **Локальный (standalone).** Carrel работает как обычная программа на машине пользователя: скачанный бинарник (тот же артефакт, что и для контейнера, либо платформенные сборки `windows`/`darwin`/`linux`) слушает `localhost`, данные — в каталоге пользователя. В обёртке вместо адреса вводят **путь к бинарнику**: приложение само запускает процесс, дожидается готовности (`/healthz`), подключается к `http://127.0.0.1:<port>` и при закрытии корректно останавливает дочерний процесс (SIGTERM / аналог на Windows, потолок ожидания 15 с — как при штатном завершении ниже). Каталог данных и порт — из настроек обёртки или рядом с бинарником; наружу порт не публикуется.

Обёртка добавляет отдельный релизный артефакт, подпись сертификатами под macOS и Windows и проверку интерфейса в WebKitGTK. До её появления ту же «отдельную иконку» закрывает установка как PWA (§13); локальный standalone без обёртки уже возможен вручную: скачать бинарник, запустить, открыть браузер на `localhost`.

**Healthcheck** `/healthz` — отвечает, что процесс жив. Состояние DAV-серверов не проверяет, иначе чужая недоступность будет ронять контейнер.

**Логи** в stdout, структурированные, уровень из конфига. Учётные данные, пароли, содержимое карточек, токены сессий и приглашений в логи не попадают никогда, включая режим отладки.

**Корректное завершение.** По SIGTERM: перестать принимать соединения, дождаться активных запросов, отменить веерные задачи, обнулить ключи и кэш в памяти, выйти. Потолок ожидания 15 секунд.

**В README явно:** обновление образа означает рестарт, рестарт означает повторный вход для всех пользователей, поскольку ключи живут только в памяти. Это осознанное свойство, а не недоработка.

### 18.1 Reverse-proxy: Apache (основной вариант)

```apache
<VirtualHost *:443>
    ServerName carrel.example.com

    SSLEngine on
    SSLCertificateFile      /etc/letsencrypt/live/carrel.example.com/fullchain.pem
    SSLCertificateKeyFile   /etc/letsencrypt/live/carrel.example.com/privkey.pem

    ProxyPreserveHost On
    RequestHeader set X-Forwarded-Proto "https"

    # Прогресс веерного опроса: SSE не должен буферизоваться
    <Location /events/>
        ProxyPass        http://127.0.0.1:8080/events/ flushpackets=on
        ProxyPassReverse http://127.0.0.1:8080/events/
        SetEnv proxy-sendchunked 1
        SetEnv proxy-nokeepalive 0
    </Location>

    ProxyPass        / http://127.0.0.1:8080/
    ProxyPassReverse / http://127.0.0.1:8080/

    # Загрузка фото без потолка на стороне прокси
    LimitRequestBody 0
    ProxyTimeout 120
</VirtualHost>
```

Модули: `proxy`, `proxy_http`, `headers`, `ssl`; при HTTP/2 дополнительно `http2`.

Существенные детали для README:

- **`flushpackets=on` на SSE-эндпоинте обязателен.** Без него Apache копит ответ в буфере, и прогресс опроса доедет одним куском в самом конце, то есть не заработает. Это самая частая причина «индикатор висит и ничего не происходит».
- `RequestHeader set X-Forwarded-Proto "https"` именно `set`, а не `setifempty`: заголовок от клиента должен затираться, иначе его можно подделать снаружи.
- `LimitRequestBody 0` снимает ограничение на размер загружаемого фото (по умолчанию у Apache 1 ГБ).
- `ProxyTimeout` должен превышать общий потолок веерной задачи (30 с), иначе Apache оборвёт соединение раньше, чем приложение завершит опрос.
- В конфиге Carrel в список доверенных прокси вносится `127.0.0.1` — только тогда приложение поверит `X-Forwarded-Proto` и выставит `Secure` на куках.
- Порт приложения не публиковать наружу: в `compose.yaml` привязка `127.0.0.1:8080:8080`.
- При работе в подкаталоге (`/carrel/`) приложению нужен базовый путь из конфига, иначе htmx-запросы и ссылки на статику уйдут не туда. Отдельный вариант конфига Apache для этого случая — в README.

Конфигурации для Caddy и nginx приводятся дополнительно, с той же оговоркой про буферизацию SSE (`proxy_buffering off` для nginx).

## 21. Критерии приёмки

**Подключение и данные**

- Подключение к Baikal по прямому URL работает; коллекции обоих типов обнаружены автоматически.
- Контакт с `X-`полями от стороннего клиента после правки имени сохраняет все исходные свойства. Проверяется побайтовым сравнением всего, кроме изменённого.
- Контакт в vCard 3.0 после замены фото остаётся 3.0.
- Правка того же объекта из второго клиента приводит к экрану выбора, а не к тихой перезаписи.

**Фотографии**

- Фото, загруженное в EXIF-ориентации 6, отображается вертикально и не содержит EXIF после сохранения.
- Снимок с GPS-метками сохраняется без координат.
- Снимок 4000×3000 приводится к настроенному потолку.
- Контакт с `PHOTO` в виде ссылки отображается, но помечен как нередактируемый.

**Единый вид и дубликаты**

- Три выбранных календаря из двух аккаунтов дают агенду за неделю, отсортированную по времени, каждое событие с меткой источника.
- Снятие галочки с коллекции убирает её записи и сохраняется после перезапуска контейнера.
- Создание события из сводного вида требует явного выбора целевого календаря.
- Один человек в двух книгах разных аккаунтов помечается кандидатом; после связывания показывается одной строкой с объединёнными телефонами обоих.
- Отметка «не дубликаты» переживает перезапуск.
- Объединение на сервере не удаляет исходники, если `PUT` объединённой записи не прошёл.
- Удаление одной из связанных записей сторонним клиентом не вызывает ошибок.

**Опрос и деградация**

- Во время сводного запроса видно, сколько источников ответило; после завершения индикатор активности исчезает.
- Недоступный источник помечен ошибкой с повтором только его; остальные результаты остаются.
- Записи медленного источника встают на правильные позиции по сортировке, а не в конец.
- Уход со страницы во время опроса не оставляет висящих горутин.
- Отказ одного из трёх аккаунтов не ломает интерфейс, единый вид и поиск.

**Кэш**

- Повторное открытие той же коллекции без изменений на сервере не порождает новых `multiget`-запросов.
- Правка объекта сторонним клиентом становится видна после обновления, а не отдаёт старое из кэша.
- Выход из сессии освобождает память кэша.

**Пользователи и безопасность**

- Администратор не видит подключений и данных других пользователей ни в интерфейсе, ни в API (при выключенном депонировании).
- Приглашённый пользователь заводит пароль сам; до его первого входа в хранилище нет ни хэша пароля, ни DEK.
- Ссылка приглашения работает при полностью ненастроенном SMTP.
- Токен приглашения после использования недействителен; в хранилище только его хэш.
- Тестовое письмо показывает диагностику при неверных настройках SMTP.
- Сброс пароля админом делает подключения недоступными, о чём он предупреждён до подтверждения.
- Смена пароля самим пользователем сохраняет все подключения.
- Отключение пользователя немедленно завершает его активные сессии.
- Удаление последнего администратора невозможно.
- На экране входа нет функции восстановления пароля, вводящей в заблуждение.

**Депонирование**

- При выключенной схеме (по умолчанию) в хранилище нет ни одной копии DEK, доступной кому-либо кроме владельца.
- Включение схемы не даёт доступа к учётным записям, созданным до включения.
- Восстановление невозможно без мастер-пароля, отличного от пароля входа админа.
- Каждое восстановление отражено в журнале и в письме пользователю.
- Профиль пользователя показывает, действует ли для него депонирование.

**Развёртывание**

- `docker run` с пустым томом приводит к экрану создания администратора.
- Контейнер работает при `read_only: true` и непривилегированном пользователе.
- SIGTERM завершает процесс без обрыва активных запросов.
- В логах на уровне debug отсутствуют пароли, токены и содержимое карточек.
- Прогресс веерного опроса работает через Apache с приведённым конфигом.

**Лицензия**

- Страница «О сервисе» доступна без входа и показывает версию, коммит и ссылку на исходники.
- Версия и коммит на этой странице совпадают с зашитыми при сборке.
- `THIRD_PARTY.md` содержит тексты лицензий всех зависимостей и вендоренного htmx.

## 23. Дополнительный функционал

Две идеи, решающие одну задачу: Carrel уже знает рабочие адреса, пути коллекций и учётные данные всех подключённых серверов, и это знание можно использовать за пределами собственного веб-интерфейса. **Ни то, ни другое не входит в v1** и не должно влиять на архитектуру первых шести этапов.

### 23.1 Экран «Новое устройство»

Помощник настройки сторонних клиентов. Устройства после настройки ходят к DAV-серверам **напрямую**: Carrel не становится посредником в синхронизации и не превращается в точку отказа. Данные для настройки достаются один раз, при живой сессии, когда DEK и так развёрнут, — криптосхема §4 не меняется.

**Что Carrel отдаёт.** После discovery известно всё, на что уходит время при ручной настройке: рабочий базовый URL (для Baikal это `/dav.php/`, который `.well-known` часто не отдаёт), URL принципала и home-set, точные пути и имена коллекций, логин и пароль.

**Android — DAVx5.** У DAVx5 есть документированная точка интеграции: ссылка вида `davx5://user@server.example.com/path/`, превращённая в QR-код, открывает DAVx5 с подставленными URL и именем пользователя. Пароль так передать нельзя — документация DAVx5 прямо запрещает кодировать учётные данные в URL, для них предусмотрены extras интента, выставить которые может только Android-приложение, а не веб-страница. Пароль остаётся ввести вручную, но два самых ошибкоёмких поля закрыты. Дополнительно поддерживаются универсальные схемы `caldavs://` и `carddavs://`, которые открывает любое совместимое приложение, не только DAVx5.

**Apple — конфигурационный профиль.** iOS и macOS принимают `.mobileconfig` — XML-plist с payload'ами CalDAV и CardDAV (хост, путь принципала, логин, пароль). Carrel собирает **один профиль сразу на все подключённые аккаунты**: пользователь открывает файл, подтверждает установку, все календари и адресные книги появляются разом. Самая большая экономия из всего раздела, при этом по коду — генерация XML. Профиль либо подписывается, либо интерфейс честно предупреждает о том, что iOS покажет его как неподписанный.

**Thunderbird.** Механизма импорта нет, достаточно готовых URL: экран с кнопками копирования по каждой коллекции снимает основную возню.

**Состав экрана.** Список аккаунтов; у каждого — QR с `davx5://`, кнопка скачивания `.mobileconfig`, раскрывающийся блок с точными URL коллекций и логином для ручного ввода.

**Безопасность.** Профиль Apple содержит пароли открытым текстом — это файл, который утекает через мессенджеры и оседает в «Загрузках». Поэтому:

- Генерация только после **повторного ввода пароля от Carrel**.
- Отдача по одноразовой ссылке с коротким TTL.
- Явное предупреждение о содержимом файла до скачивания.
- Профиль **не сохраняется на диск сервера**: собирается в памяти и отдаётся потоком.
- Скачивание профиля записывается в журнал.

**Оценка объёма:** примерно один этап работы.

### 23.2 davloom — режим DAV-прокси

Carrel выступает единственной точкой подключения для сторонних клиентов: пользователь вводит в DAVx5 или Thunderbird одну учётную запись и получает все настроенные аккаунты сразу. Режим называется **davloom** и в этом качестве упоминается в интерфейсе и документации.

#### Форма поставки

**Одна сборка, прокси — режим запуска.** Не отдельный бинарник и не отдельный продукт. Команды: `carrel serve` (только веб), `carrel proxy` (только прокси), либо оба слушателя сразу. Разные слушатели на разных портах: веб можно повесить на `127.0.0.1`, прокси опубликовать наружу.

Обоснование выбора:

| | Один процесс | Два процесса из одного образа | Два бинарника |
|---|---|---|---|
| Сборка и CI | одна | одна | две матрицы, два набора тегов |
| Разнести по хостам | нет | да | да |
| Изоляция памяти | нет | да | да |
| Падение прокси роняет веб | да | нет | нет |
| Код прокси у того, кто его не ставил | есть | есть | отсутствует |

Первые два столбца — **одна и та же сборка**, выбор между ними делает тот, кто разворачивает, а не архитектура. Третий покупает ровно одну вещь: физическое отсутствие серверной поверхности у тех, кто прокси не использует. Разделение на два таргета в `cmd/` при общих пакетах — работа на день, и делается в любой момент позже, когда станет ясно, нужен ли прокси людям отдельно. Обратного пути нет только у бренда: имя, разошедшееся по чужим compose-файлам, назад не сворачивается.

**Рекомендуемый способ запуска — два отдельных процесса.** Один процесс допустим и работоспособен, но рекомендацией по умолчанию — и в README, и в примере `compose.yaml` — является раздельный запуск. Причины:

- **Изоляция памяти.** Прокси принимает запросы от машин, разбирает недоверенные тела и правит их на лету. В одном процессе паника или утечка в этом коде оказываются в том же адресном пространстве, где сессии веб-интерфейса и развёрнутые DEK.
- **Независимый рестарт.** Падение или обновление прокси не выбрасывает работающих в вебе людей, и наоборот.
- **Раздельное завершение.** SIGTERM одному процессу не обрывает синхронизацию, идущую в другом.

Запуск одним процессом остаётся приемлемым там, где нагрузка низкая, а лишняя эксплуатационная сложность не оправдана: домашний инстанс на одного-двух человек, где второй контейнер, второй healthz и второй лог дают больше возни, чем пользы. Доступность из интернета критерием здесь не является — она задана в §2 как базовое условие и одинакова для обоих вариантов.

**Раздельные лимиты и логи.** Независимо от числа процессов:

- Потолок памяти под кэш сессий веб-интерфейса и потолок под прокси задаются **отдельно**. Иначе большая синхронизация вытеснит по LRU кэш работающего человека.
- Логи размечаются по компонентам (`web`, `proxy`) и фильтруются по ним. DAVx5 генерирует запросы круглосуточно, и без разметки полезные записи веб-части тонут в фоновом трафике.
- `/healthz` у прокси отдельный от веб-интерфейса даже при запуске одним процессом.

#### Правила употребления имени

Имя должно указывать на конкретную включаемую вещь, а не быть украшением:

- Название режима в интерфейсе, документации и логах; отдельный раздел в доках; собственный `/healthz`.
- **Не заводить** под него отдельный репозиторий, отдельные теги образа, отдельные релизные заметки и отдельную страницу проекта — иначе получится второй продукт без его выгод.
- davloom остаётся **единственным** поименованным модулем. Словарь из нескольких внутренних имён превращается в нагрузку на пользователя.
- Пишется всегда строчными.

**Знак модуля** — нити, сходящиеся в полотно через вертикальный вал станка (три стадии: разрозненное, механизм, результат). Палитра и антиква общие с Carrel. Это пиктограмма уровня иконки раздела, а не второй логотип: рядом с лампой не конкурирует, а обозначает подсистему.

#### Корневая страница

Человек, открывший адрес прокси в браузере вместо DAVx5, должен получить не 401 и не пустой ответ, а страницу с названием модуля, версией, коммитом и ссылкой на исходники. Это **требование AGPL §13**: davloom смотрит в сеть, значит обязан предлагать исходники своим пользователям. Единственная пользовательская поверхность модуля.

#### Криптосхема прокси

Схема с app-паролями снимает необходимость что-либо хранить отдельно и не требует держать ключи развёрнутыми между запросами.

**Обёртки DEK.** Carrel создаёт их, когда пользователь залогинен и DEK развёрнут: одна обёртка на один app-пароль, то есть на одно устройство. App-пароль генерируется Carrel, показывается один раз, в хранилище лежит только обёртка.

**Обработка запроса:**

1. Клиент присылает запрос с app-паролем в Basic-аутентификации.
2. `Argon2id(app_password, salt)` → KEK, KEK разворачивает DEK.
3. DEK расшифровывает учётные данные нужного апстрима.
4. Запрос проксируется.
5. Ключи и расшифрованные учётки затираются.

**Между запросами ничего расшифрованного в памяти не остаётся.** Утверждение «пока подключён синк-клиент, учётки лежат открытыми» неверно: они открыты только на время обработки запроса.

**Кэш KEK.** Плановый интервал синхронизации DAVx5 типично велик (в наблюдаемой конфигурации — 240 минут), поэтому расписание нагрузки не создаёт. Кэш нужен под другой сценарий: DAVx5 синхронизируется **немедленно при локальных изменениях**, и правка пяти контактов подряд даёт пять отдельных синков со своими наборами запросов. TTL порядка 30–60 секунд (в конфиге) накрывает серию ручных правок и истекает задолго до следующего планового захода. Ключ присутствует в памяти доли процента времени.

**Параметры Argon2id для прокси** могут быть легче, чем для интерактивного входа: там человек ждёт однократно, здесь машина стучится постоянно. Значения не назначать умозрительно — измерить на реальном цикле DAVx5 и зафиксировать в README с обоснованием.

**Отзыв устройства** — удаление его обёртки. Остальные не затронуты, перенастраивать ничего не нужно.

**Смена основного пароля Carrel** перешифровывает только его собственную обёртку DEK; app-пароли продолжают работать. Интерфейс обязан сказать об этом явно, иначе пользователь решит, что сменой пароля отключил все устройства.

**Мониторинг.** При интервале в несколько часов упавший прокси остаётся незамеченным очень долго — о проблеме узнаёшь по отсутствию встречи в календаре. `/healthz` следует заводить во внешний мониторинг.

**Что остаётся неустранимым.** Пароли DAV-серверов нужны в открытом виде для Basic-аутентификации наверх, поэтому в момент проксирования они всегда в памяти — свойство протокола, а не схемы. App-пароль хранится на устройстве в хранилище DAVx5, но там же сегодня лежит пароль от Baikal.

#### Проксирование

**Реализовывать серверную семантику CalDAV не нужно.** Большая часть трафика проксируется вслепую — `REPORT`, `sync-collection`, `calendar-query`, `PROPPATCH`, `MKCALENDAR`, `GET`, `PUT`, `DELETE`. Клиент шлёт запрос, прокси подменяет заголовок авторизации и отдаёт ответ апстрима как есть. Семантику реализует Baikal или Radicale.

Вслепую не проходят две вещи.

**Первое — hrefs в телах.** Multistatus содержит абсолютные пути апстрима. Отданные клиенту без изменений, они приведут к тому, что следующий запрос уйдёт мимо прокси. Обратно тоже: `calendar-multiget` присылает ранее полученные hrefs, их надо разворачивать в апстримовые.

Решается зеркальной схемой путей:

```
/dav/{account_id}/dav.php/calendars/mix/personal/
        →  https://cloud.example.org/dav.php/calendars/mix/personal/
```

Правка — подмена префикса строковой заменой в обе стороны, без XML-парсинга, потоково, без буферизации тела целиком. Отдельно ловить абсолютные URL со схемой и хостом: некоторые серверы отдают их вместо путей.

**Второе — корень.** Апстрима, владеющего `/`, не существует. `.well-known`, `current-user-principal`, principal и home-set — синтетические уровни, которые прокси генерирует сам: именно они склеивают несколько серверов в один аккаунт. `PROPFIND Depth: 1` по синтетическому home-set — веерный опрос всех подключённых аккаунтов со слиянием ответов, с тайм-аутами и деградацией по §16 и §17. Плюс `OPTIONS` на корне с корректным заголовком `DAV:`. Синтетических уровней ровно три; ниже начинается тупое проксирование.

**Стабильность идентификаторов.** Клиенты запоминают href'ы, поэтому `account_id` персистентен на диске и не выводится из порядка подключения. Имена коллекций между аккаунтами совпадают («Личный» есть везде) — различает их `account_id` в пути.

**Риск интеропа.** Реализация по RFC и реализация, которую переваривают DAVx5, Thunderbird и Apple Calendar, различаются заметно. Отладка этого хвоста нередко занимает больше, чем сам код. Начинать с read-only прототипа под один DAVx5.

**Оценка объёма:** маршрутизация по префиксу, подмена авторизации, потоковая замена путей в обе стороны, три синтетических уровня, обёртки app-паролей, персистентные идентификаторы.

### 23.3 Резервное копирование на WebDAV

Carrel собирает архив коллекций и кладёт его на WebDAV-сервер, указанный пользователем. **Принцип §2 не нарушается:** у себя Carrel по-прежнему ничего не хранит — он читает у одного сервера и пишет на другой. Файл живёт там, где уже лежат данные пользователя, и попадает в его собственные бэкапы. WebDAV-транспорт для этого уже есть, нужен только потоковый `PUT`.

Целевой WebDAV может быть как одним из подключённых аккаунтов, так и отдельным адресом с собственными учётными данными. **Целевой WebDAV необязателен:** архив можно забрать через API (см. ниже) — для тех, у кого писать некуда.

#### Формат архива

Сырые `.ics` и `.vcf` **как есть**, без собственной упаковки, разложенные по каталогам «аккаунт / коллекция». Архив должен читаться любым инструментом и не зависеть от того, жив ли Carrel: копия, которую можно восстановить только своей же программой, — плохая копия.

Рядом с данными — манифест: дата, версия Carrel, список аккаунтов и коллекций, число объектов, ETag'и на момент снятия.

#### Требования

- **Шифрование архива** отдельным паролем на стороне Carrel. Целевой WebDAV может быть на чужом хостинге; без шифрования туда лягут все контакты и календари открытым текстом. Пароль архива не совпадает с паролем входа.
- **Ротация:** файл с датой в имени, не перезапись предыдущего; хранить N последних, N настраивается.
- **Проверка после записи:** прочитать записанное обратно и сверить размер и контрольную сумму. Молча провалившийся бэкап хуже отсутствующего.
- **Восстановление обязательно.** Копия без проверенной процедуры восстановления — иллюзия защиты, а не защита. Восстановление идёт через выбор целевой коллекции и обычный `PUT` с сохранением неизвестных свойств по §8; перед записью показывается, что и куда будет положено.
- Ошибка на одной коллекции не отменяет копирование остальных: она помечается в манифесте, процесс продолжается.
- Все операции с целевым WebDAV — потоком, без сборки архива целиком в памяти и без временных файлов на диске сервера.

#### Копия по требованию

Пользователь залогинен, DEK развёрнут, Carrel собирает архив и кладёт на выбранный WebDAV. **Новых уступок в модели безопасности не требуется вообще.** Реализуется первой.

#### Расписание: внешний триггер (основной способ)

**Carrel не планирует ничего сам.** Он отдаёт эндпоинт, который дёргают снаружи: обычным `cron`, GoSentry, заданием в Gitea — чем угодно. Секрет живёт на машине с планировщиком, а не на инстансе Carrel, поэтому **схема §4 остаётся нетронутой: сервер не хранит паролей**.

По коду это дешевле собственного планировщика: один хендлер вместо расписаний, повторов и состояния заданий.

**Устройство:**

- `POST /api/backup/run` с app-паролем в заголовке. Механизм обёрток DEK — тот же, что у прокси (§23.2), новых понятий не вводится.
- **Область действия пароля — ровно одна: запуск резервного копирования.** Ни чтения коллекций, ни доступа к настройкам, ни к чему-либо ещё. Скомпрометированный триггер-пароль не должен давать читать контакты.
- Ответ **асинхронный**: снятие копии займёт минуты и упрётся в тайм-аут reverse-proxy. Запуск возвращает идентификатор задачи; рядом `GET /api/backup/status` для опроса. Для `cron` достаточно кода возврата на запуске — приняли задачу или нет.
- Rate limit на эндпоинт.
- Каждый запуск в журнал с указанием, каким паролем инициирован.
- Параллельный запуск при незавершённой копии — отказ, а не вторая задача.

**Честная оговорка.** Пароль всё равно где-то хранится — просто на машине с планировщиком. Если это тот же хост, где крутится Carrel, выигрыш в основном формальный: и то и другое доступно тому же администратору. Реальная разница появляется, когда планировщик на другой машине.

**Побочная выгода:** связка с GoSentry (собственный планировщик с GUI) — живой сценарий совместного использования, который стоит описать в README обоих проектов.

#### Скачивание архива через API

Не у всех есть WebDAV, куда можно писать. Альтернатива — забрать архив тем же процессом, который его запустил.

- `GET /api/backup/{id}/download` с тем же app-паролем, что запускал задачу. Отдаётся только после успешного завершения; пока задача идёт — `409`.
- Архив **не сохраняется на диск сервера**: собирается потоком и отдаётся в ответ. Если целевой WebDAV не задан, копия существует только как этот поток — не забрали, значит её нет, и это должно быть сказано в описании эндпоинта.
- Ссылка одноразовая либо действует ограниченное время, идентификатор задачи не угадывается (не последовательный).
- Шифрование архива и все прочие требования — без изменений: то, что файл уходит по HTTP, а не на WebDAV, не отменяет пароля архива.
- Скачивание пишется в журнал отдельной записью.

Тогда `cron` или GoSentry делают два вызова: запуск, затем скачивание по готовности, — и файл ложится туда, где стоит планировщик. Для многих это будет проще, чем поднимать WebDAV ради одних бэкапов.

#### Копия при входе

Carrel смотрит, когда снималась последняя копия, и если прошло больше N дней — предлагает или запускает её в текущей сессии, где DEK и так развёрнут. **Секретов не хранит вообще.** Покрывает не всё, но закрывает основной сценарий: человек, заходящий раз в неделю, получает еженедельные копии бесплатно.

#### Собственный планировщик с хранимым паролем (запасной вариант)

Делать только если трёх способов выше оказалось недостаточно.

Планировщик работает без активной сессии, значит DEK нужно развернуть без человека, а пароль взять неоткуда — он должен лежать на сервере, зашифрованный серверным ключом с тома. Это та схема, от которой §4 сознательно уходит.

**Argon2id здесь ничего не защищает:** на томе лежит и пароль, и обёртка, поэтому владелец хоста разворачивает DEK за одну команду. Это обфускация, а не защита. Реальная ценность схемы другая — отсек и отзыв: скомпрометированное задание не открывает остальные устройства, удаление задания стирает его обёртку. **От оператора хоста она не защищает никак, и в интерфейсе это должно быть написано прямо.**

Условия, при которых допустимо:

- Схема применяется **только** к резервному копированию и ни к чему больше.
- Обёртка DEK своя на каждое задание, отзывается независимо.
- В интерфейсе сказано без эвфемизмов: этот пароль сервер держит сам, поэтому владелец хоста технически может получить доступ к данным задания.
- Задание отключается и удаляется в любой момент; удаление стирает обёртку.
- Каждый запуск в журнал; провал уведомляет пользователя.

#### Очерёдность

1. Копия по требованию — без уступок.
2. Копия при входе — без уступок.
3. Внешний триггер через API — без уступок, основной способ расписания.
4. Собственный планировщик — только если предыдущего не хватило, и осознанно.

### 23.4 Общий доступ: публикация и подписка

Закрывает дыру, которой у части серверов нет вовсе: у Baikal человеческого механизма поделиться календарём наружу не существует. Три разные по цене вещи, которые важно не смешивать.

#### Публикация read-only

Коллекция отдаётся наружу по секретной ссылке в виде `.ics` или `.vcf`, собранных из живого чтения апстрима.

**Состояния нет и хранить ничего не нужно:** пришёл запрос — Carrel сходил на сервер — отдал. Самая дешёвая часть раздела, не требует уступок ни в §2, ни в §4.

Требования:

- Токен не короче 32 байт из `crypto/rand`, в хранилище — только хэш.
- Отзыв в один клик; настраиваемый срок жизни; список активных ссылок в профиле с датой последнего обращения.
- Отдавать с `Cache-Control: private` и без индексации (`X-Robots-Tag: noindex`).
- Rate limit на эндпоинт: ссылка публичная, и её будут перебирать.
- Ссылка даёт доступ **только** к одной коллекции, никогда к аккаунту целиком.

#### Ссылка с правом записи

Тот же механизм, но внешний адресат может писать. Работает через учётную запись владельца на апстриме.

**Обязательная оговорка, которую нельзя прятать:** все правки на сервере будут выглядеть как сделанные владельцем. В журнале апстрима не различить, кто именно внёс изменение. Это не полноценный совместный доступ, и называть его так в интерфейсе нельзя.

Настоящий совместный доступ — это ACL на стороне сервера: право выдаёт тот, кто владеет данными, а Carrel учётных записей на Baikal не заводит и подменить это не может. Формулировка в интерфейсе должна честно говорить, что даёт ссылка, и не создавать впечатления управления правами.

#### Подписка на внешний календарь

Здесь цена принципиально другая, и она зависит от режима.

**В веб-интерфейсе** честно реализуется только просмотр фида по требованию: открыл — Carrel сходил и показал. Фонового обновления нет, потому что подписке негде жить между сессиями, а кэш фида на диске означал бы локальную персистентность контента вопреки §2.

**В режиме прокси (§23.2) подписка становится почти бесплатной.** Внешний фид отдаётся клиенту как ещё одна read-only коллекция, тянется по запросу, ничего не хранится. Клиент сам решает, когда обновляться. Это естественное место для подписки — она принадлежит davloom, а не веб-интерфейсу.

Требования: фид тянуть с тайм-аутом и лимитом размера; недоступность внешнего источника не роняет остальные коллекции (§17); коллекция помечается как внешняя и только для чтения.

### 23.5 Мультитенантность: Carrel как услуга

Сценарий: кто-то поднимает Carrel и раздаёт доступ другим людям — сообществу, небольшой компании, клубу. Пользователи подключают **свои** DAV-аккаунты на любых серверах; хостер даёт только веб-клиент, а не хранилище данных.

**Кода почти не требуется.** Механика §5 уже даёт всё нужное: изоляция пользователей (у каждого свои соли, свой DEK, свои подключения), приглашения по почте, панель администратора, отсутствие у администратора доступа к чужим данным. Отличие от текущей модели не техническое, а в позиционировании и в нескольких эксплуатационных деталях.

#### Что делает нишу пустой

Существующие варианты — это хостинг **данных**: Nextcloud, Fastmail, Google. Клиент там неотделим от хранилища, и переезд означает миграцию данных. Carrel как услуга разделяет эти вещи: данные остаются на сервере пользователя, хостер даёт интерфейс. Уйти можно в любой момент, ничего не перенося.

**AGPL здесь работает на проект, а не против.** Хостер обязан отдавать исходники своим пользователям (§22, требование §13 лицензии) — то есть коммерческое использование автоматически возвращает изменения в экосистему.

#### Чего не хватает поверх §5

- **Квоты:** предел числа подключённых аккаунтов и коллекций на пользователя, потолок памяти сессии на пользователя (§12 задаёт общий потолок процесса — при мультитенантности нужен ещё и персональный, иначе один пользователь с огромной книгой вытеснит остальных).
- **Ограничение исходящих подключений.** Пользователь задаёт произвольный URL, к которому Carrel сходит с сервера, — это SSRF по построению. Нужны запрет приватных диапазонов и loopback, список разрешённых или запрещённых хостов, лимит на редиректы. **Для однопользовательского инстанса это второстепенно, для публичного — обязательно.**
- **Самостоятельная регистрация** с подтверждением почты — сейчас §5.2 её по умолчанию запрещает.
- **Условия использования и контакты оператора** на странице «О сервисе» рядом со ссылкой на исходники.
- **Прозрачность депонирования.** §5.4 требует показывать пользователю, действует ли для него схема восстановления. В публичном хостинге это перестаёт быть формальностью: пользователь должен видеть, может ли оператор добраться до его учётных данных, **до** того как заводить подключения.

#### Ограничения, которые нужно назвать честно

- Пароли DAV-серверов пользователей находятся на инстансе хостера в зашифрованном виде и расшифровываются в его памяти при каждом запросе — иначе Basic-аутентификация невозможна (§4). Оператор с доступом к процессу технически может их получить. Это свойство архитектуры, а не недоработка, и в условиях использования оно должно быть написано прямо.
- Рестарт инстанса разлогинивает всех: ключи живут в памяти. Для публичного сервиса это заметнее, чем для личного, и должно быть в описании услуги.

**Приоритет.** Отдельного этапа не требует: это README, несколько настроек и ограничение исходящих подключений. Последнее стоит сделать раньше остальных независимо от мультитенантности — SSRF актуален для любого инстанса, доступного не только владельцу.

### 23.6 Печать

Печатная версия списков: повестка за период, список контактов, отдельная карточка. Делается печатной таблицей стилей (`@media print`), а не генерацией PDF на сервере — сохранение в файл выполняет сам браузер. Ни новых зависимостей, ни серверного рендеринга.

**Почему это уместно именно здесь.** Визуальный стиль построен на картотечной эстетике: волосяная линовка вместо теней, тёплый фон, рубрикаторы с разрядкой. Такая вёрстка на бумаге выглядит естественнее, чем интерфейсы со стеклянными карточками, — печать здесь не чужеродная функция, а логичное продолжение материала.

**Что печатается:**

- Повестка за выбранный диапазон, сгруппированная по дням, с пометкой источника.
- Список контактов выбранных книг: имя, телефоны, email, при желании адреса.
- Отдельная карточка контакта или события.
- Печатается **то, что отобрано на экране** — выбранные коллекции и период, а не всё подряд.

**Требования к печатной таблице стилей:**

- Убрать навигацию, боковой рейл, поиск, кнопки, элементы управления.
- Цветные метки коллекций сохранить, но продублировать текстом («аккаунт · коллекция»): печать бывает чёрно-белой, и цвет как единственный носитель информации на бумаге не работает.
- Фон не печатать (пустой расход тонера), текст — чёрным по белому; тёплый фон интерфейса на бумаге не воспроизводится.
- Разрывы страниц не внутри записи (`break-inside: avoid`), заголовок дня не отрывать от первой записи под ним.
- Колонтитул: название, диапазон, дата снятия. Без этого распечатка через неделю неотличима от свежей.
- Фотографии контактов — по выбору: с ними и без, печать фото заметно дороже.

**Ограничение:** печать отражает состояние на момент открытия страницы. Это бумага, а не живой документ, и колонтитул с датой существует именно для того, чтобы это было очевидно.

### 23.7 Кандидаты без решения

Две идеи, записанные для обдумывания. Ни одна не принята: у обеих есть цена, которую надо взвесить отдельно.

#### Импорт из выгрузок сервисов

Не просто приём `.vcf` и `.ics` (это входит в базовый CRUD), а именно разбор того, что отдают Google Takeout, iCloud и выгрузки телефонов. Там свои особенности: нестандартные `X-`поля групп, фотографии в разных представлениях, склейка нескольких карточек в один файл, кодировки, экранирование, вложенность архива.

**Зачем.** Эта работа определяет приток пользователей: человек переезжает один раз, и если импорт спотыкается, он не возвращается. Скучная, но результативная.

**Цена.** Работа не заканчивается: форматы выгрузок меняются без предупреждения, и каждый источник — отдельный набор частных случаев. Требует реальных выгрузок для тестов.

**Что решить:** делать ли вообще, или ограничиться честным приёмом стандартных `.vcf`/`.ics` и рекомендацией конвертеров.

#### Корзина: восстановление удалённого

DAV-серверы корзины не имеют: удалённый контакт исчезает безвозвратно. Carrel мог бы удерживать удалённые объекты N дней и возвращать их обратно.

**Зачем.** Этого нет нигде в экосистеме, и это ровно та функция, которая однажды спасает человеку данные.

**Цена — прямое нарушение §2.** Хранить придётся **содержимое** объекта, а не метаданные: восстанавливать нечего, если тела нет. Это первая уступка принципу «локальной персистентности контента нет», и она настоящая, а не формальная.

Смягчающие обстоятельства: уступка узкая (только удалённое, только временно, автоочистка по сроку), тело можно шифровать тем же DEK, объём ограничен.

**Чего корзина не даст.** Удаление из стороннего клиента Carrel не увидит — он узнает о нём только как об исчезновении объекта при следующем чтении, уже без тела. То есть корзина работает **только для удалений, сделанных через Carrel**. Это надо назвать прямо, иначе она создаст ложное чувство защищённости.

**Что решить:** оправдывает ли частичная корзина (только свои удаления) отказ от одного из базовых принципов, или правильнее закрывать этот сценарий резервным копированием (§23.3), которое уступок не требует.

### 23.8 Прозрачность: показать то, что и так известно

*Контроль потерь при записи перенесён в §8, диагностика подключения — в §6: оба стали требованиями основной части.*

Два пункта, объединённые общим свойством: **нового кода почти не требуется**. Всё перечисленное Carrel уже вычисляет для собственных нужд — не хватает только вывода наружу. Это дешевле любой новой функции и заметно отличает сервис от клиентов, которые молчат.

#### Состояние синхронизации по коллекциям

У человека DAVx5 на телефоне, Thunderbird на работе, Carrel в браузере — и когда данные расходятся, причину не установить.

Carrel видит `getctag` и ETag'и, то есть знает, когда коллекция менялась в последний раз. Достаточно строки состояния у каждой коллекции: когда последний раз читалась, когда менялась на сервере, сколько объектов.

Это **не** журнал изменений (он требует хранить содержимое, см. §23.7) — только метаданные, которые уже проходят через кэш §12.

#### Исходный часовой пояс события

§10 фиксирует один глобальный TZ — правильное упрощение для v1. Но встреча, созданная в другом поясе, показывается не в то время, и человек не понимает, ошибка это или так задумано.

Минимальное лекарство — **не** поддержка нескольких поясов, а показ исходного пояса там, где он отличается от текущего: рядом со временем пометка вроде «создано в Europe/Berlin». Данные уже есть в `DTSTART` с `TZID`, ничего вычислять не нужно.

### 23.9 Заметки (VJOURNAL): совместимость и связи

#### Позиция

VJOURNAL — не пустое поле: на Android есть jtx Board, на десктопе Evolution. Чего в связке нет — **веб-звена**. Заметку, созданную в jtx на телефоне, не посмотреть с рабочего компьютера иначе как поставив Evolution. Carrel закрывает именно эту дыру, а не создаёт формат с нуля.

**Следствие, определяющее всё остальное:** сторонние клиенты существуют, значит заметки обязаны уживаться с чужими правками ровно так же, как контакты. Сохранение неизвестных свойств (§8), `If-Match` и разрешение конфликтов (§9) действуют полностью. jtx Board пишет в VJOURNAL собственные `X-`поля — терять их нельзя.

#### Ориентир — Google Keep, а не системы знаний

Сравнивать VJOURNAL с Obsidian или Notion бессмысленно: ни вложений, ни истории версий, ни обратных ссылок он не даёт и не даст. Но массовый сценарий — не вики, а «записал, чтобы не забыть», и по нему ориентир именно Keep.

Против Keep формат покрывает практически всё нужное: заголовок (`SUMMARY`), текст (`DESCRIPTION`), метки (`CATEGORIES`), дата (`DTSTART`). Не хватает цветовых пометок и картинок. Зато даёт то, чего у Keep нет вовсе: данные на своём сервере, синхронизация уже настроена, ничего не пропадёт при закрытии сервиса, и запись можно привязать к человеку или встрече.

**Единственное, в чём Keep выигрывает по-настоящему, — скорость входа.** Заметка создаётся за две секунды с любого экрана. Отсюда главное требование к этой функции: **не богатство полей, а быстрое создание.**

- Кнопка создания заметки — **в навигационной панели, на виду**, доступна с любого экрана, а не спрятана внутри раздела заметок.
- Открывается одно поле ввода. Ввёл — сохранил. Заголовок, метки, связи, дата — потом и по желанию, а не в форме на восемь полей.
- Целевая коллекция берётся по умолчанию (последняя использованная), меняется по желанию, но не спрашивается каждый раз.

Если создание заметки стоит трёх кликов и формы, никакая переносимость данных этого не компенсирует.

**Разделение с jtx Board.** На телефоне быстрый ввод за две секунды даёт jtx, а не веб-интерфейс. Это не конкуренция, а разделение ролей: jtx — быстрый ввод на ходу, Carrel — десктоп, просмотр, связи, поиск по всем источникам. Тем важнее, что совместимость с jtx заявлена как проверяемое свойство.

#### Модель

Строится на стандартных свойствах, а не на изобретённых:

- **`RELATED-TO`** — связи заметки с контактом, событием или задачей. «Поговорил с Анной, договорились о…» живёт рядом с карточкой Анны, но лежит обычным объектом на DAV-сервере, а не в проприетарной базе. Это то, за чем обычно идут в CRM.
- **`CATEGORIES`** — теги.
- **`DTSTART`** — хронология: заметки за период как лента.

Это не изобретение Carrel: `RELATED-TO` — то, чем jtx Board связывает заметки с задачами. Правильная постановка задачи — **не** «придумать модель заметок», а «писать так, чтобы понял jtx, и читать так, чтобы понять его».

#### Связи между объектами

**Принцип: только то, что выражает стандарт.** Собственные `X-`поля для связей не вводятся, каким бы соблазнительным это ни было. Такие данные прочтёт только Carrel, а весь смысл проекта в обратном — объекты должны оставаться понятными сторонним клиентам. Если стандарт связь не выражает, честнее её не делать.

**`RELATED-TO` — связи внутри iCal.** Заметка с событием, заметка с задачей, задача с задачей. Стандартный механизм, понятный jtx Board.

Основной сценарий: **заметка, созданная из события** — итоги встречи. `RELATED-TO` на UID события, дата та же. В агенде рядом с прошедшей встречей видно, что по ней есть запись. Полностью в рамках стандарта, ничего изобретать не нужно.

**Мост между iCal и vCard — только email.** Штатно связать заметку или событие с карточкой контакта нельзя: форматы живут в разных мирах. Единственное, что есть, — `ATTENDEE` с `mailto:` в событии.

Carrel сопоставляет адрес с карточкой в адресной книге. Нормализация адресов уже написана для скоринга дубликатов (§15) и переиспользуется целиком. На сервер при этом ничего нестандартного не пишется — сопоставление происходит на стороне Carrel при отображении.

**Подавать это следует как «упоминания», а не как жёсткую привязку:** у контакта может не быть адреса, у события — `ATTENDEE`, и тогда связь не установится. Интерфейс не должен создавать впечатление, что связь гарантирована.

**Хронология контакта.** На карточке — все события с его участием и все заметки с его упоминанием, отсортированные по времени. Фактически карточка клиента, то, за чем обычно идут в CRM.

Вычисляется на лету из уже загруженных данных: **хранить ничего не нужно**, состояния не добавляется. Стоимость — та же, что у единого вида (§14): веерный запрос с тайм-аутами и деградацией по §16 и §17.

#### Экспорт заметок в Markdown

Заметка в VJOURNAL — это заголовок, текст, дата и метки, то есть ровно то, из чего состоит `.md`-файл с front matter. Экспорт превращает журнал в набор файлов, читаемых Obsidian, Logseq, любым редактором и `grep`.

**Зачем.** Снимает главное возражение против того, чтобы вести заметки в календарном формате: данные не заперты. Даже если Carrel исчезнет, а VJOURNAL никто не поддержит, заметки остаются обычным текстом.

**Режимы:**

- **Одна заметка** — кнопка на карточке, скачивание файла.
- **Пачкой** — выбранные коллекции и период, архив с файлами.
- **Назначение:** скачать на устройство либо положить на WebDAV (тот же механизм, что у §23.3, включая необязательность WebDAV).

**Формат файла:** YAML front matter с полями из объекта (`title`, `date`, `tags` из `CATEGORIES`, `uid`, `related` из `RELATED-TO`, источник — аккаунт и коллекция), дальше `DESCRIPTION` как тело.

**Требования:**

- Имя файла из даты и заголовка, транслитерация и замена символов, недопустимых в файловых системах; при совпадении — суффикс из UID, а не молчаливая перезапись.
- Свойства, не попавшие в front matter, сохранять там же как есть: экспорт не должен терять то, что §8 бережно сохраняет при записи.
- Сборка потоком, без временных файлов на сервере.
#### Импорт заметок из Markdown

Однократная миграция: перенести существующие заметки из Obsidian, Logseq, папки с файлами или выгрузки другого сервиса.

**Это не синхронизация, и граница проходит здесь:** импорт **всегда создаёт новые объекты и никогда не трогает существующие**. Конфликтов не возникает по построению, поэтому ни версий, ни разрешения расхождений не требуется.

**Требования:**

- Совпал UID из front matter — **не перезаписывать**, а создать с новым UID и отметить в отчёте. Иначе повторный запуск начнёт затирать правки, сделанные после первого импорта.
- Front matter читается, если есть, но **не требуется**. Без него: заголовок — из имени файла или первого `#`, дата — из имени файла или mtime, тело целиком в `DESCRIPTION`. Импорт, работающий только с собственной выгрузкой Carrel, для миграции бесполезен.
- **Предпросмотр до записи:** сколько файлов найдено, что не разобралось, в какую коллекцию ляжет. Импорт двух сотен файлов вслепую — верный способ засорить коллекцию.
- **Отчёт после:** что создано, что пропущено и по какой причине.
- Целевая коллекция выбирается **явно** — единственный случай без умолчания, поскольку операция массовая и штатными средствами необратимая.
- Источники: архив с `.md`, отдельные файлы, каталог на WebDAV.

**Экспорт и импорт не образуют пары для регулярного обмена.** Выгрузил, поправил в редакторе, залил обратно — это уже синхронизация со всеми её конфликтами, и она не предусматривается.

#### Обязательный шаг до реализации

**Снять реальные объекты из jtx Board и Evolution и разобрать, что они пишут на самом деле.** Формат допускает многое, а на практике используется узкое подмножество — попадать надо в него, а не в RFC вообще. Без этой сверки любая модель окажется умозрительной.

Проверить: какие свойства заполняются, как оформляются связи, какие `X-`поля добавляются, как ведёт себя `CATEGORIES` при правке с двух сторон.

#### Совместимость как заявленное свойство

Совместимость с jtx Board и Evolution указывается в README и входит в критерии приёмки: заметка, созданная в Carrel, корректно открывается в обоих; заметка из jtx после правки в Carrel сохраняет все исходные свойства (проверяется побайтовым сравнением всего, кроме изменённого).

Это проверяемое обещание, а не декларация, — и оно же определяет ценность: Carrel становится веб-частью существующей экосистемы, а не ещё одним хранилищем заметок.

### 23.10 Вложения через WebDAV

Файл лежит на WebDAV пользователя, а событие или заметка несут ссылку на него в штатном свойстве `ATTACH`. Никакого base64 внутри объекта, никаких раздутых `.ics`.

**Почему это органично.** Carrel видит календарный и файловый серверы одновременно — соединить их может только он. Механизм при этом стандартный: `ATTACH` с URI существует в iCal, ничего изобретать не нужно, и принцип §23.9 «только то, что выражает стандарт» соблюдён.

**Требования:**

- Прикрепление: файл кладётся на выбранный WebDAV, в объект добавляется `ATTACH` с URI. Загрузка потоком, без временных файлов на сервере.
- Отображение: имя файла, размер и тип; открытие проксируется через Carrel, а не отдаётся браузеру как чужой адрес (тот же подход, что у внешних `PHOTO` в §11).
- Существующие `ATTACH`, поставленные другими клиентами, показываются как есть; `ATTACH` с inline-данными (base64) — только на чтение, не переписывать в ссылку.
- Удаление вложения из объекта **не удаляет файл** с WebDAV: на него могут ссылаться другие объекты. Интерфейс говорит об этом прямо.
- Недоступность файлового сервера не ломает открытие события: вложение помечается недоступным (§17).

#### Вложения в заметках

Для заметок вложения закрывают единственный существенный пробел против Google Keep (§23.9) — картинки и скриншоты. При этом файл идёт ссылкой, а не в тело объекта, поэтому синхронизация не раздувается.

**Скорость вставки здесь критична.** У Keep скриншот вставляется одним движением. Если в Carrel это «выбрать файл, выбрать место на WebDAV, дождаться, прикрепить» — функция окажется мёртвой.

- Вставка из буфера обмена (Ctrl+V прямо в форму заметки) и перетаскивание файла.
- **Каталог для вложений задаётся один раз в настройках и больше не спрашивается** — тем же способом, что коллекция по умолчанию в §23.9. Иначе требование «заметка за две секунды» ломается.
- Имена файлов генерировать осмысленно: дата и заголовок заметки, а не `image-1.png`. Каталог должен оставаться разбираемым вне Carrel.

**Управление содержимым каталога — не задача Carrel.** Это диск пользователя: Carrel выступает посредником, который кладёт файл и ставит ссылку. Ни чистки, ни квот, ни сборки мусора он не делает и брать на себя ответственность за содержимое чужого хранилища не должен.

**Честное ограничение.** Сторонние клиенты ссылку покажут, но откроют не всегда, а если файл за авторизацией — не откроют вовсе. Это свойство подхода, а не недоработка, и его надо назвать в интерфейсе при прикреплении.

**Зависимость.** Требует файлового раздела (§19, этап 7), который сам по себе ещё не подтверждён. Отдельно от него не реализуется.

**Границы.** Роль файловой части — обслуживать вложения, а не быть самостоятельным файловым менеджером. Превью, редактирование, управление правами — отдельный продукт с другими конкурентами, не имеющий отношения к задаче сведения нескольких DAV-аккаунтов.

## 24. Безопасность: сводный раздел

Требования разбросаны по §4, §5, §11, §23 — здесь они собраны воедино и дополнены тем, что появилось вместе с ростом поверхности. **Это чеклист для реализации, а не пересказ:** пункты, отсутствующие в других разделах, помечены как новые.

### 24.1 Модель угроз

От кого защищаемся и от кого нет — определить до реализации, иначе требования выглядят произвольными.

**Защищаемся:**

- Внешний злоумышленник без учётных данных: перебор паролей и токенов, доступ к чужим данным, SSRF, XSS.
- Скомпрометированное устройство пользователя: один app-пароль не должен открывать остальные.
- Другой пользователь того же инстанса: полная изоляция данных.
- Кража тома с данными: без пароля пользователя учётные данные DAV не расшифровываются.

**Не защищаемся (назвать честно в README):**

- Оператор хоста с доступом к процессу. Пароли DAV нужны открытым текстом для Basic-аутентификации (§4), значит в момент запроса они в памяти. Дамп памяти их выдаёт.
- Оператор при включённом депонировании ключа (§5.4) или при собственном планировщике бэкапа (§23.3) — там пароль хранится на сервере.
- Компрометация самого DAV-сервера.

### 24.2 SSRF: ограничение исходящих подключений

**Новое требование.** Самая недооценённая дыра: пользователь задаёт URL, Carrel ходит по нему с сервера. Касается discovery (§6), подписок (§23.4), вложений (§23.10), целевого WebDAV для бэкапа (§23.3).

- Резолвить имя и **проверять полученный IP** до подключения. Запрещены: loopback (`127.0.0.0/8`, `::1`), приватные диапазоны (`10/8`, `172.16/12`, `192.168/16`, `fc00::/7`), link-local (`169.254/16` — метаданные облачных провайдеров), multicast, `0.0.0.0`.
- **Проверка после каждого редиректа**, а не только исходного URL. Разрешающий исходный адрес с редиректом в локалку — типовой обход.
- Лимит числа редиректов (3–5).
- Защита от DNS rebinding: подключаться к уже проверенному IP, а не резолвить имя повторно.
- Список исключений в конфиге — для тех, у кого DAV-сервер действительно в локальной сети. **По умолчанию пуст**, добавление осознанное.
- Тайм-аут на соединение и на весь запрос; лимит размера ответа.

### 24.3 Эндпоинты без аутентификации

**Новое требование.** Поверхность выросла: публичные ссылки (§23.4), `/api/backup/run` и скачивание архива (§23.3), корневая страница прокси (§23.2), приглашения (§5.3), `/healthz`, страница «О сервисе» (§22).

- Сравнение всех токенов — **constant-time**. Обычное сравнение утекает информацию по времени.
- Ответ **не различается** для «не существует», «отозвано» и «истекло» — иначе перебор становится осмысленным. Одинаковый код, одинаковый текст, одинаковое время ответа.
- Rate limit на каждый такой эндпоинт, независимо от лимита на логин.
- Токены не меньше 32 байт из `crypto/rand`; в хранилище только хэш.
- Токены не попадают в логи, в `Referer` и в аналитику. Публичные страницы — с `Referrer-Policy: no-referrer`.
- `/healthz` не раскрывает версию, состояние апстримов и число пользователей.

### 24.4 Загрузка и разбор файлов

По фотографиям защита описана в §11. **Новое — то же самое для остальных точек загрузки:** вложения (§23.10), импорт `.md` (§23.9), восстановление из архива (§23.3).

- Лимит размера тела запроса **по умолчанию для всех эндпоинтов**, отдельно расширяемый там, где нужно.
- Архивы: лимит на распакованный размер и на число файлов (zip-бомбы), проверка коэффициента сжатия.
- **Пути внутри архива:** отвергать `../`, абсолютные пути и символические ссылки. Классический path traversal при распаковке.
- Разбор — потоково, во временный файл, не в память; удаление в `defer` при любом исходе.
- Тип содержимого определять по сигнатуре, а не по расширению и не по заголовку от клиента.
- Отдача любых пользовательских файлов — с `X-Content-Type-Options: nosniff` и `Content-Disposition`, задающим имя явно.

### 24.5 Веб-уровень

**Новое требование** — в ТЗ упомянут только CSRF.

- **CSP.** Основная защита от XSS. htmx требует аккуратности: `unsafe-inline` для скриптов не использовать, обработчики выносить в атрибуты htmx, а не в inline-`<script>`. Директивы: `default-src 'self'`, `img-src 'self' data:`, `frame-ancestors 'none'`, `form-action 'self'`.
- `X-Frame-Options: DENY` (или `frame-ancestors` в CSP), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`.
- HSTS — только когда известно, что инстанс за HTTPS.
- **Экранирование.** `html/template` экранирует по контексту автоматически, но `template.HTML` отключает защиту. Пользовательские данные через него не передаются никогда. Особая осторожность с `DESCRIPTION` заметок: там произвольный текст, который выводится крупным блоком.
- Куки сессии: `HttpOnly`, `SameSite=Lax`, `Secure` при HTTPS (по доверенному прокси из явного списка, §4).
- Ротация идентификатора сессии при входе.
- CSRF-токены на всех мутирующих запросах, включая htmx-фрагменты.

### 24.6 Работа с памятью и ключами

- **Явное затирание** ключевого материала после использования, а не надежда на сборщик мусора. Касается KEK, DEK, паролей DAV и app-паролей.
- Кэш KEK (§23.2) — единственное место, где ключ живёт дольше запроса: TTL обязателен, очистка при завершении процесса тоже.
- Отключение swap и дампов памяти рекомендовать в README: содержимое календарей и контактов присутствует в RSS процесса (§12).
- Ключи и учётные данные не попадают в логи ни на каком уровне, включая debug и трассировки ошибок.

### 24.7 Прокси (§23.2)

- Прокси разбирает **недоверенный ввод** от сетевых клиентов и правит тела ответов — отсюда рекомендация запускать отдельным процессом.
- Подмена префиксов в телах: не допустить, чтобы клиент, подсунув специально составленный href, заставил прокси обратиться к произвольному адресу. Проверять принадлежность пути известному `account_id`.
- Лимит размера тела запроса и ответа при проксировании.
- App-пароль прокси даёт доступ только к аккаунтам своего пользователя — проверка на каждом запросе, а не только при выводе ключа.

### 24.8 Что проверять тестами

- Пользователь A не может получить объект пользователя B ни одним эндпоинтом, включая прямой запрос по угаданному пути.
- Отозванный app-пароль перестаёт работать немедленно.
- Отозванная публичная ссылка отвечает так же, как несуществующая.
- URL с редиректом на `127.0.0.1` и на `169.254.169.254` отклоняется.
- Архив с путём `../../etc/passwd` внутри отклоняется.
- Заметка с `<script>` в `DESCRIPTION` выводится как текст.
- В логах на уровне debug нет паролей, токенов и содержимого объектов.

## 25. Позиционирование и конкурентная среда

Раздел не содержит требований к коду. Он нужен, чтобы README, описание репозитория, порядок работ и акценты запуска опирались на проверенную картину рынка, а не на предположения.

Источник: конкурентный анализ августа 2026. Перед публичным запуском цифры и статусы конкурентов перепроверить.

### 25.0 Краткие выводы

- **Прямых живых конкурентов почти нет.** Единственный активно развивающийся веб-клиент к чужому DAV — MMDL, но только календари и задачи, со своей БД, desktop-first. InfCloud/CalDavZAP/CardDavMATE заброшены с 2015; AgenDAV официально в maintenance mode.
- **Ниша реальна, но узкая.** Self-hosted CalDAV/CardDAV устойчив (Radicale, Baïkal, DAVx5), у пользователей три подтверждённые боли: нет хорошего лёгкого веб-клиента, нельзя править VJOURNAL с большого экрана, нет единого представления нескольких аккаунтов.
- **Самые свободные сегменты** — мультиаккаунтный unified view с дубликатами, веб-редактор VJOURNAL, режим DAV-прокси/агрегатора (davloom).
- **Главный риск** — суммарная аудитория мала и «размазана»; часть уже закрыта Nextcloud «заодно» с другими сервисами.

### 25.1 Прямые конкуренты

Веб-клиенты к **чужим** DAV-серверам — та же категория, что Carrel.

| Проект | Стек | Лицензия | Состояние | CalDAV | CardDAV | Мультиаккаунт | Своя БД |
|---|---|---|---|---|---|---|---|
| InfCloud / CalDavZAP / CardDavMATE | JS + jQuery | AGPL-3.0 | v0.13.1 от 22.09.2015, заброшен | да | да | ограниченно (коллекции) | нет |
| AgenDAV | PHP + JS | GPL-3.0 | maintenance mode, активность ~авг. 2024 | да | нет | ограниченно | требует |
| Manage My Damn Life (MMDL) | Next.js / Node | GPL-3.0 | v0.9.2 от 10.06.2026, активен, бета (~590★) | да (события и задачи) | нет | да (аккаунты и юзеры) | требует (Sequelize) |
| **Carrel** | Go + htmx | AGPL-3.0-or-later | в разработке | да (+ VJOURNAL) | да | да, unified view + дубликаты | нет (живой прокси) |

**Детали по конкурентам:**

- **InfCloud** — ближайший функциональный аналог по охвату (CalDAV + CardDAV), та же AGPL, но jQuery-код 2015 года без стабильных релизов ~11 лет. Официальная страница по-прежнему указывает 0.13.1 как latest stable.
- **AgenDAV** — README дословно: prioritize stability over new features, «no active development & new major features are not planned». Интерфейс в духе Google Calendar grid; только CalDAV.
- **MMDL** — единственный живой конкурент. Протестирован с Nextcloud, Radicale, Baïkal; использует tsdav. Сам себя описывает как «self hosted front end for managing your CalDAV tasks and calendars» и как desktop-first («multiple clients like JTX Boards, OpenTasks exist for mobile»). Без CardDAV и без веб-редактора заметок; локальная персистентность через свою БД — противоположность модели Carrel (§2).

**Выводы по отстройке:**

- От InfCloud — современный стек (Go + htmx, один бинарник) и поддержка.
- От AgenDAV — контакты, заметки, отсутствие внешней БД.
- От MMDL — CardDAV, VJOURNAL, живой прокси без своей БД, unified view нескольких аккаунтов с обнаружением дубликатов.

**Веб-клиента такого рода на Go или Rust в публичном поле нет.** На этих языках — серверы и библиотеки (`emersion/go-webdav`, Fennel и прочие), но не полноценный веб-клиент-прокси. В этой технологической нише Carrel был бы первым.

### 25.2 Косвенные конкуренты и «вместо»

- **Nextcloud (Calendar / Contacts)** — де-факто основной веб-клиент для многих. Характерный отзыв: ownCloud/Nextcloud «слишком тяжёлый», если нужны только CalDAV/CardDAV. Главный источник аудитории «уставших от комбайна».
- **Baïkal, Davis, Radicale** — серверы с админками / управлением коллекциями, не пользовательские клиенты. Среда обитания Carrel, не конкуренты.
- **SOGo, Kolab, Roundcube** — groupware целиком либо почтовик с плагинами; не клиент к чужим серверам.
- **Thunderbird, Evolution, GNOME Calendar, KDE Kontact / Merkuro** — Thunderbird не поддерживает VJOURNAL (крупный запрос на Mozilla Connect); Evolution поддерживает, но только Linux. Кроссплатформенного десктопа с мультиаккаунтностью и заметками нет — ниша PWA (§13).
- **Android: DAVx5 + jtx Board + Fossify / Simple Calendar** — зрелый мобильный стек. **Не конкурент, а союзник:** §23.9 заявляет совместимость, §23.1 помогает настраивать; в README прямо сказать, что удобная мобильная работа — это DAVx5/jtx, а не мобильная вёрстка Carrel (§13).
- **Коммерческие (Fastmail, mailbox.org, Posteo, Apple)** — веб-клиент только к собственному серверу, не агрегатор чужих DAV.

### 25.3 Свободные сегменты и подтверждённые боли

Три ниши без прямых аналогов:

1. **Мультиаккаунтный единый вид** с обнаружением дубликатов между серверами (§14, §15). У живых конкурентов нет; у MMDL есть несколько аккаунтов, но без CardDAV/заметок и без заявленного сведения с дубликатами.
2. **Веб-редактор VJOURNAL** (§23.9). Экосистема: jtx Board (Android, почти полный RFC-5545 со связями `RELATED-TO`), Evolution (Linux), KOrganizer, синк через DAVx5, хранение на Radicale/Nextcloud/Baïkal. Веб-звена нет. Спрос: тема «Support VJOURNAL in Thunderbird» (Mozilla Connect); issue nextcloud/tasks #1955 — «people have no ability to edit or create syncable Journals and Notes on Nextcloud… it would be a lot easier to manage that on the big screen».
3. **Read/write DAV-прокси / агрегатор** (§23.2, davloom). Смежное: Linkal (Rust, публичные календари, read-only), calmerge / camerge (слияние `.ics`-фидов, read-only), запрос Radicale #1193 на слияние календарей. Полноценного read/write CalDAV+CardDAV-агрегатора за одной точкой для DAVx5/Thunderbird не найдено.

Отдельно: пользователи Radicale/Baïkal регулярно ищут лёгкий веб-фронтенд; серверы дают админку или управление коллекциями, не агенду/контакты/заметки. Масштаб спроса количественно не измерен (см. §25.8).

### 25.4 Размер ниши

Индикаторы инфраструктуры (прокси популярности, не число пользователей клиентов):

- **Radicale** — порядка 4,8 тыс. звёзд GitHub (отдельные обзоры называют ~3k), живёт с 2008, активен в 2026, GPLv3.
- **Baïkal** — около 3 тыс. звёзд проекта; community-образ `ckulka/baikal` — **5M+** pulls на Docker Hub (неофициальный образ; сам `ckulka/baikal-docker` — ~644★).
- **DAVx5** — официальная градация Google Play «100 000+»; сторонние оценки выше, плюс F-Droid и Managed DAVx5.

**Аудитория нишевая:** self-hosted энтузиасты. Ожидания от запуска держать скромными.

### 25.5 Акценты для README

По убыванию приоритета — готовые формулировки ценности:

1. **Главный слоган (то, чего нет ни у кого):** «Единый веб-клиент к нескольким CalDAV/CardDAV-серверам сразу: календари, контакты и заметки в одном представлении, без своей базы данных.» Отстраивает от MMDL (только календари+задачи, своя БД) и от InfCloud/AgenDAV (мертвы / только календарь).
2. **«Анти-Nextcloud» / лёгкость:** один бинарник, один контейнер, Go + htmx, без Node/npm/сборщиков, живой прокси без локального хранения контента. Целевая фраза: «если вам нужен только календарь, контакты и заметки — а не весь комбайн.»
3. **VJOURNAL в вебе:** «редактируйте заметки jtx Board с большого экрана»; совместимость с jtx Board и Evolution; экспорт/импорт Markdown; ориентир Google Keep (§23.9). Крючок для аудитории jtx/DAVx5.
4. **davloom:** «одна учётка в DAVx5/Thunderbird вместо пяти» — killer-feature для тех, кто устал настраивать каждый аккаунт отдельно (§23.2).
5. **Помощник устройств** (`.mobileconfig`, `davx5://` QR) и **многопользовательский режим с изоляцией ключей** — аргументы для семейного / малого-командного self-hosting (§23.1, §5).

Обязательно в README (не маркетинг, а честность и ясность):

- происхождение названия (библиотечная кабинка) и отграничение от Алексиса Карреля;
- мобильная роль — спасательный круг; удобный телефон = DAVx5 + jtx (§13);
- рестарт = повторный вход (ключи только в памяти);
- модель угроз: от чего защищаемся и от чего нет (§24.1);
- что означает AGPL для того, кто хостит для других (§22).

### 25.8 Риски, оговорки и пороги стратегии

**Оговорки по данным анализа:**

- Звёзды GitHub и Docker pulls — прокси, не число живых инсталляций.
- «5M+ pulls» у Baïkal относится к community-образу `ckulka/baikal`, не к самому проекту.
- Оценка DAVx5 сверх «100 000+» со сторонних агрегаторов менее надёжна.
- Исчерпывающего количественного замера спроса не было; цитаты (Mozilla Connect, nextcloud/tasks #1955, Radicale #1193, AlternativeTo) репрезентативны, но не статистика.
- **Прямого масштабного треда «нужен мультиаккаунтный веб-клиент» не найдено** — спрос на мультиаккаунтность выведен косвенно (мультиаккаунт в MMDL, запросы на слияние в Radicale, описания в awesome-selfhosted). Это гипотеза; первый публичный отклик её проверит.
- Carrel в сети на момент анализа отсутствовал (не искался); нельзя полностью исключить свежий малоизвестный веб-клиент 2025–2026, не попавший в каталоги.

**Структурные риски:**

- Ниша мала и разрозненна; часть аудитории закрыта Nextcloud «заодно».
- Главный риск запуска — что «чистая» ниша веб-клиента слишком мала.

**Пороги, меняющие акценты в README и roadmap:**

- Если после запуска на r/selfhosted и HN за первые месяцы нет хотя бы нескольких сотен звёзд — усиливать VJOURNAL и davloom как самостоятельные value-props, а не только «ещё один веб-клиент».
- Если основной отклик на заметки — разворачивать продукт в сторону «open-source Google Keep поверх CalDAV».
- Если основной отклик на агрегатор — акцент на «одна точка подключения для всех устройств» (davloom).

Решение принимать по реакции аудитории, а не заранее.
