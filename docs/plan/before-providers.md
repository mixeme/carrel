## 1. Депонирование — довести черновик

Слой набросан (`internal/crypt/escrow.go`, `store`, `user`, `web/handlers_escrow.go`),
чеклист [users-tail.md](users-tail.md) отмечен. К провайдерам это не готово:
восстановление выпускает временный пароль и сразу его теряет, а смена пароля
входа — заглушка, без которой `MustChangePassword` после восстановления не
снимается.

- [ ] **Восстановление не теряет временный пароль.** Сейчас `RecoverEscrow`
  перешифровывает, `sendEscrowRecoveryMail` всегда `false`, обработчик делает
  redirect — пароль ни человеку, ни администратору. До S-26: как приглашение
  (S-10.3) — показать временный пароль на `AdminEscrowPage` с копированием,
  отдельно сказать, что письма нет. После S-26 письмо человеку уходит всегда,
  независимо от воли администратора; показ на панели от этого не зависит.
  Проверка, которая краснеет сейчас: после `action=recover` войти временным
  паролем нельзя, потому что его негде прочитать
- [ ] **`RecoverEscrow` сжигает wipe-токены (Ф2-4).** Любой путь, ставящий
  пароль, зовёт `burnWipeTokens`. Иначе старая ссылка `/forgot/{token}`
  опустошит учётку после восстановления. Проверка: живой wipe-токен, recover,
  тот же токен — `ErrNotFound`, блоб цел
- [ ] **Смена мастер-пароля на экране.** `ChangeEscrowMaster` есть, на
  `/admin/escrow` при включённой схеме формы нет — только policy и recover
- [ ] **Консоль не становится восстановлением (S-10.4).** `IssueConsoleWipeLink`
  по-прежнему очищает, даже если человек в депонировании. `/forgot` для
  депонированного — «спросите администратора», не wipe. Экраны wipe называют
  уничтожение, не «сброс». Держится; не ломать, пока пишется панель

Не пересматривать: не задним числом; мастер нигде не кэшируется; отказ удаляет
копию в том же `Mutate`; уведомление при первом входе; формулировка S-10.5, не
«резервное копирование ключей»; депозит только через лист S-10.7.

## 2. Смена пароля входа

Без этого восстановление из депонирования и флаг `MustChangePassword` — тупик:
вход редиректит на `/app/password`, POST перерисовывает GET.

- [x] **`POST /app/password` — `RewrapDataKey`, не `ApplyPassword`.** Новый ключ
  данных сделает блоб нечитаемым. Снять `MustChangePassword`, `burnWipeTokens`,
  завершить **остальные** сессии этого человека (текущую оставить, SID не
  менять без нужды). Старый пароль — тем же ведром, что вход. Проверка: после
  смены старый пароль не входит, DAV-блоб открывается новым, чужая сессия
  того же логина мертва, старый wipe-токен мёртв

## 3. Панель администратора (S-10.6)

`GET` рисует страницы людей, приглашений и журнала; `POST /admin/settings`,
`/admin/dav`, `/admin/install` и проба письма — заглушки (S-26 / S-28).

Люди и приглашения — да. Настройки SMTP, проба письма, allowlist DAV, экран
установки — нет (S-26 / S-28).

- [x] **Список людей.** Логин, роль, дата создания, последний вход, **число**
  подключений (не сами подключения), живые сессии, disabled, escrowed
- [x] **Приглашения.** Завести; отозвать; продлить (= now + 7 суток, секрет
  тот же); отправить повторно (= новый секрет и новый срок). Актор в `Who`.
  Ссылка на панели видна всегда, состояние отправки отдельно: до S-26 —
  «SMTP не настроен», не «отправлено»
- [x] **Отключить / удалить / сменить роль / завершить сессии.** Удаление —
  набор логина. Последнего администратора нельзя удалить, понизить, отключить
  (`ErrLastAdmin` на всех трёх операциях)
- [x] **«Сбросить пароль».** Без депонирования — тот же wipe-токен, что
  `/forgot`, с актором. Адрес подтверждён — в очередь письма (до S-26 экран
  честный); адреса нет — одноразовая ссылка администратору, как консоль.
  Пароль за человека не задаётся. При действующем депонировании **вместо
  сброса** предлагается восстановление (S-10.6), не wipe
- [x] **Журнал `/admin/audit`.** Строки из тома: кто / что / с кем; не пароль,
  не токен, не тело записи. `Detail` — по правилу из [reviews.md](reviews.md)

## 4. Обнаружение: дефекты закрытого слоя

Первый прогон S-30.2 (05.09.2026) нашёл это в `dav.ResolveWellKnown` /
`discover.Run`. Провайдеры будут ходить в коллекции, которые вернул этот код.
Чинить здесь, тестами пакета, без живого сервера в воротах.

- [ ] **Цель well-known принимать только после `current-user-principal`.**
  Сейчас любой `2xx` становится адресом службы. Radicale ведёт `/.well-known/caldav`
  на веб-интерфейс (`200`) — обнаружение подменяет рабочий `/test/` и получает
  `403`. На Baikal не стреляет: цель отвечает `401`, есть откат. Проверка: фикстура
  well-known → `200` HTML без принципала → `Run` остаётся на введённом URL
- [ ] **well-known от корня origin, не от введённого пути (RFC 6764).** Сейчас
  `/test/.well-known/caldav`. Radicale и Baikal редиректят что угодно; сервер,
  отдающий well-known только на корне, обнаружение не найдёт
- [ ] **Понижение `https` → `http` при обнаружении — отказ, не предупреждение.**
  Baikal редиректит well-known на `http://…/dav.php`. Go копирует `Authorization`
  при редиректе в пределах хоста, схему не учитывая. Предупреждение Ф-13 висит
  на **введённом** адресе (`https://`) и промолчит. Вместе с пунктом про
  принципал: пока цель не принята как DAV, пароль туда не идёт

## 5. Linux-машина: не ломать SelfPost, не светить Radicale

Инфраструктура написана. Чекбокс S-30.2 в [server.md](server.md) снят: он стоял
по наличию файлов, не по зелёному прогону.

- [ ] **`docker-compose.linux.yml` слушает `127.0.0.1:5232`.** Сейчас
  `5232:5232` на все интерфейсы. Машина в интернете, на ней SelfPost, пароль
  `test:test` в `testdata/`. В репозиторий из `dev/` ничего не переносить
- [ ] **Интеграционные тесты — под CalDAV Radicale, не под «любой WebDAV».**
  Нетипизированный `MKCOL` → 403; не-iCalendar/vCard → 400, в том числе в доме
  пользователя. С валидным `.ics` внутри типизированной коллекции
  `TestRadicalePutIfMatch` и `TestRadicaleGetStreams` на машине уже проходили
  (412 / 204 в логе). Правка была на сервере, в репозитории её нет. После
  пунктов раздела 4 — прогнать три теста руками на Linux; зелёный прогон
  обнаружения, конфликта версий и потока **на Radicale** закрывает этот пункт.
  Файловый WebDAV — на SFTPGo, позже, вместе с `provider/file`

Учётные данные живых серверов — `dev/credentials.txt`. Не в git.
