# Хвост: фикстуры и проверка «вью-модель равна фикстуре»

Найдено ревью перед S-30 ([review-server.md](review-server.md), Р-13).

C-14.2 называет сервер готовым, когда:

- каждый маршрут C-5 отвечает;
- **на каждый обработчик есть проверка «вью-модель равна фикстуре» во всех её
  состояниях**;
- S-30 закрыт;
- ни одного шаблона в коде.

Второго пункта нет совсем. В `docs/spec/fixtures/` три файла:

- `app-contacts/normal.json`;
- `app-contacts/partial.json`;
- `app-conflict/normal.json`.

Сверяются они только с типами (`view/fixtures_test.go` разбирает JSON в
структуры). Ни один тест `internal/web` не строит экран и не сравнивает его с
фикстурой. План в [architecture.md](architecture.md) предписывает `cmp.Diff`
по анмаршаленному JSON, но этим способом ничего не проверено.

Последствия:

- **Клиент строится по фикстурам** (C-3.2). Для 60 с лишним экранов фикстур
  нет: клиенту нечего рисовать без сервера.
- **Расхождение сервера с кадром** ловится только глазами. Ревью нашло этим
  путём Р-4 (служебные поля видимыми строками) и Р-7 (формы без кнопок) — их
  поймала бы первая же фикстура с формой.

Это самый крупный незакрытый критерий готовности сервера. S-30 без него
объявлять закрытым нельзя: C-14.2 — рубеж, а не пожелание.

---

## Как сверять, чтобы данные совпали

Фикстура — данные кадра («Анна Ковалёва», «nextcloud · Контакты»).
Обработчик строит экран из того, что ответил DAV. Чтобы сравнение имело смысл,
на DAV должны лежать данные кадра:

- **`docs/visual/fixtures/`** уже содержит записи кадров в `.vcf` и `.ics`
  (`make-fixtures.py`) и раскладку «какой файл — какая коллекция — какой
  экран».
- Проверка поднимает `davtest` с двумя «серверами» (`nextcloud · home` и
  `radicale · vps`), кладёт туда эти файлы, заводит подключения с этими
  именами и снимает экран.
- Время заморожено на дне кадра (10.08.2026), пояс — Europe/Moscow.
- Идентификаторы (`a-…`, `t-…`), SID и CSRF заменяются перед сравнением —
  как `cmp.Diff` с опцией, а не правкой фикстуры.

## Порядок

1. **Инфраструктура**:
   - `web/fixture_test.go`: загрузка набора `docs/visual/fixtures` в `davtest`;
   - замороженные часы: `web.Server` уже берёт время из `timeFor`, часы
     нужно сделать внедряемыми;
   - сравнение с нормализацией идентификаторов;
   - первая пара — `app-contacts/normal.json` против
     `/app/contacts/{account}/{col}`.
   
   Ворота: проверка однажды показана красной (C-16).
2. **Фикстуры по C-14.3** — экран за экраном, в порядке кадров:
   - на каждый экран `normal`;
   - `empty` там, где список;
   - `readonly`, `source-error`, `partial`, `unavailable` там, где рейл или
     опрос;
   - `loss` у форм правки;
   - `conflict` у карточек;
   - `narrow` (U-9) — сервер не знает ширины. **Решение владельца
     19.09.2026:** узкий экран — забота клиента; в C-14.3 состояние уходит в
     U, серверных фикстур `narrow` нет.
   
   Фикстура пишется **с кадра**, не с ответа сервера. Иначе проверка
   подтверждает сама себя. Расхождение с сервером — находка, не повод
   переписать фикстуру.
3. **Расхождения, найденные сверкой**, — по C-3.4: данные не те → C-10 и `S`;
   данных нет → C-6 и `S`.

## Кто делает

Фикстуры — «определение задачи клиента» (C-3.2) и принадлежат обеим сторонам.
Писать их с кадров — работа того, кто держит кадры. Проверку на сервере пишет
Composer. **Решение владельца 19.09.2026:** JSON фикстур пишет Opus с кадров;
объём — порядка ста файлов.

- [x] Инфраструктура сверки и первая пара, показанная красной (`v0.0.159`,
      `web.TestFixtureCombinedContacts`). Набор кадров
      (`docs/visual/fixtures`) поднимается в двух `davtest`-серверах с
      подписями «nextcloud · home» и «radicale · vps», коллекции заводятся
      по таблице README с их цветами, записи раскладываются по одному
      объекту на адрес; ответ сравнивается с фикстурой через `cmp.Diff`
      после нормализации: `a-…`, `t-…`, CSRF. Сверка под флагом
      `CARREL_FIXTURE_DIFF=1` — она красная, и ворота от этого не должны
      падать, пока фикстуры не переписаны.

### Что показала первая сверка (20.09.2026)

- **Фикстура выдумала адреса.** `urn:uuid:9f2c` и `kontakty` — ни того, ни
  другого нет ни в кадре (там вообще нет ссылок), ни в наборе. Фикстура
  обязана нести настоящие UID набора и настоящий `{col}` — экранированный
  адрес коллекции на сервере, иначе клиент учится неправде.
- **Счётчики рейла.** 248, 51, 13 против пяти карточек набора. README
  набора говорит, что числа макета — иллюстрация; фикстура берёт числа
  набора.
- **Панель подробностей.** В фикстуре есть `details` с карточкой
  выделенного контакта; сервер на списках `Shell.Details` не заполняет
  вовсе. Это дыра сервера, а не фикстуры (C-3.3).
- **Панель списка.** Фикстура ждёт New/Import/Export **одной коллекции** и
  «Print»; сервер в сведённом виде отдаёт общие входы (`?pick=1`,
  `/import`, `/export`), а печать держит в `Shell.Print`. Здесь права
  фикстура только про печать — решить при переписывании.
- **Опрос.** В фикстуре три источника и 312 записей; у набора их четыре
  (`kontakty`, `arhiv`, `komanda`, `rassylki`).
- **`null` против `[]`.** Решено (владелец, 20.09.2026): пустой список —
  всегда `[]`. Правило в C-6.1, держится на выдаче (`web.withEmptyLists`),
  сторожится двумя тестами (`v0.0.160`).

### Сделано по находкам (20.09.2026, `v0.0.161`)

- **Панель подробностей.** Зона `details` (C-7.2) не отвечала ничем. Теперь
  адрес записи, запрошенный фрагментом с целью `details`, отдаёт `Details`:
  имя, поля карточки, источник и действия, первым — «Open the …». Панель на
  списке — это выбор строки клиентом, а не часть ответа списка, поэтому в
  фикстуре списка блока `details` быть не должно.
- **Адреса фикстур.** Короткие `a-nc-home/kontakty` законны как
  **нормализованные**: сверка подменяет выданные Carrel идентификаторы и
  адреса коллекций на имена набора. Прежняя запись «фикстура выдумала
  адреса» неверна — выдуманы только UID.
- **UID.** Фикстура берёт UID набора (`4f2b-9c31-a0e7` и прочие): их
  придумывать нельзя, они лежат в файлах.
- **Состояние набора.** «Команда» заводится только для чтения, «Рассылки»
  стоят в каталоге без галочки, два Артёма Белова связаны решением S-16 —
  всё это то, что показывает кадр, и всё это теперь делает загрузчик.
- **Значок связанной строки** назван, как в кадре: «linked ×2», а не
  «2 sources» — источники и так стоят рядом.
- **Выбранный порядок списка** помечается `On`.

### Находки карточки контакта, до её фикстуры

Сверено с `s-contacts-6`; каждая — расхождение сервера с кадром, не наоборот.

- **Организация и должность стоят в шапке, а не в списке полей.** Кадр
  пишет под именем «Издательство «Слово» · Выпускающий редактор», а поля
  начинает с телефонов. Сервер отдаёт `Organisation` и `Title` обычными
  строками полей. Нужна строка шапки в вью-модели: клиент не должен
  угадывать, какие два поля поднять наверх.
- **Порядок полей.** Кадр: телефоны, почты, адрес, день рождения,
  категории, заметка. Сервер: почта, телефоны, организация, должность,
  день рождения, заметка.
- **«Phone · mobile», не «Phone · cell».** `TYPE=CELL` — слово формата,
  а не слово продукта (C-10).
- **Категории — поле карточки**, как в кадре, и заодно `tags` рейла.
  Сейчас только `tags`.
- **Действия.** Кадр держит наверху Edit, Send, Print; сервер отдаёт
  Publish…, Edit contact, Move…, Copy…, Delete. Разобрать, что из этого
  первого ряда, что меню строки, и где место «Send» и «Print» после
  решения о печати.

### Что нашла первая зелёная пара (20.09.2026)

- **Свёрнутая строка была гонкой.** Два прогона одного и того же списка
  давали разного Артёма Белова: `foldLinked` оставлял того из связанных,
  кто пришёл первым, а первым приходит тот, чей сервер ответил раньше.
  Адрес, штамп, цвет и фотография строки менялись от прогона к прогону.
  Теперь строка — **первый член группы** (S-16), и остальные стоят за ней
  в порядке группы. Фикстура поймала то, что глазами не ловится (`v0.1.2`).
- **Порядок коллекций в рейле — сервера, не наш.** Carrel ничего не
  сортирует: какой порядок отдал DAV, такой и в рейле — и кадры рисуют
  именно это («Личный, Работа, Дни рождения» не по алфавиту). В наборе
  порядок даёт `davtest`, который сортирует по пути, поэтому в фикстуре
  «Архив, Контакты», а в кадре «Контакты, Архив». Проверка 8 `check.py`
  требовала совпадения порядка и чисел — то есть требовала от тестового
  сервера порядка боевого, а от набора — чисел иллюстрации. Теперь она
  сверяет состав коллекций, флажки и прочерк («—» в кадре — `null` в
  фикстуре, не ноль), а не порядок и не числа.
- **Что считает клиент сам.** Число у рубрики списка («А 3») и подпись
  под заголовком («3 of 4 books · 2 accounts · 312 cards») в вью-модели не
  стоят и стоять не должны: всё трое считается из того, что уже в ответе —
  строк группы, флажков рейла и `bar.total`. Это раскладка, а не данные
  (C-3.1).
- **Печать — контрол клиента.** Кнопка «Print» в шапке кадра действия
  сервера не требует: что печатать, уже лежит в `Shell.Print` — заголовок,
  диапазон и штамп снятия. В `bar.actions` её нет, как нет и «Columns».
- **День кадра и день опроса — разные мгновения.** Кадр снят через две
  минуты после опроса — кнопка обновления говорит «2 min ago». Харнесс
  переводит часы на эти две минуты перед снятием экрана.

- [x] **Штамп источника: в кадрах две формы одного штампа.**
      Подпись подключения в наборе — `nextcloud · home`, и так же она
      стоит рубрикой рейла во всех кадрах (72 раза). Но в столбце
      источника и под именем в панели кадр пишет коротко —
      «nextcloud · Контакты», без `home`. Точный счёт по всем кадрам:
      столбец источника — 48 строк, все урезаны; подпись под заголовком
      — 16 урезанных против 7 полных («nextcloud · home · Дела», «sftpgo · vps ·
      Documents», «radicale · vps · the server granted no write access» и прочие).
      Сервер
      везде держит одно правило — подпись плюс коллекция
      (`origin.stamp`), то есть совпадает с тремя и расходится с остальными.

      Ни README набора, ни сервер `home` не выдумывали: это подпись
      подключения из кадра. 20.09.2026 этот пункт был закрыт по ошибке
      (подключения переименовали в `nextcloud` и `radicale`) и открыт обратно:
      та правка ломала рубрику рейла, чтобы починить столбец источника.

      Предложение: полная подпись везде (сервер не трогаем, кадры
      правит Typecase). Короткую форму сервер честно собрать не может:
      подпись — одна строка слов человека, делить её по «·» нечем; а два
      аккаунта на одном сервере — ровно тот случай, ради которого штамп
      и существует.

      **Решение владельца 20.09.2026:** правим макеты, приводя их
      к единообразию. Сервер не трогаем: подпись подключения плюс
      имя коллекции везде. Задача на 64 урезанных места записана в
      [server.md](server.md) к остальным правкам владельца в Typecase.
      Фикстуры пишутся сразу с полной формой, не дожидаясь правки кадров.
