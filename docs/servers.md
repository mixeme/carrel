# Особенности серверов

Здесь записано, где настоящие DAV-серверы и библиотеки ведут себя не так, как
написано в стандарте, или не так, как ожидает Carrel, и что Carrel с этим делает.
Это поведение меняется от версии к версии, поэтому у каждой записи есть версия,
на которой оно проверено, и тест, который заметит перемену.

Спека ([docs/spec/](spec/)) говорит, что должно быть, и версий серверов не знает.
План ([docs/plan/server.md](plan/server.md)) говорит, что сделано. Этот файл —
что встретилось по дороге.

## Как вести

- **Нашли особенность — запись здесь в том же коммите**, что и обход в коде.
  Номер `SV-n` не переиспользуется; снятую запись не удаляют, а помечают снятой.
- **В комментарии к обходу в коде — номер записи** (`docs/servers.md, SV-n`),
  чтобы от кода можно было дойти сюда.
- **У записи есть сторож** — тест, который упадёт, если поведение сервера
  изменится. Запись без сторожа помечена «сторожа нет»: такую перемену никто
  не заметит.
- **Упал сторож — сначала сюда.** Поведение поменялось: обновить версию и
  описание, решить, нужен ли ещё обход, и только потом чинить тест.
- Проверено на серверах из раздела «Линейка» ниже; «вживую не проверено» —
  значит, вывод сделан по коду сервера.

## sabre/dav (Baikal, Nextcloud)

### SV-1. vCard отдаётся в 3.0 и теряет свойства 4.0

- **Стандарт.** RFC 6352 §10.4.2: клиент может указать версию в `address-data`;
  без неё сервер отдаёт в своём формате. Хранить карточку сервер обязан как есть.
- **Сервер.** Хранит как прислано, но и GET без `Accept`, и REPORT без
  `version` отдаёт **vCard 3.0**, конвертируя на лету. Свойства, которых в 3.0
  нет, при этом пропадают (`KIND`), зато добавляется `PRODID:-//Sabre//…`. Версию
  без конверсии отдаёт только на запрос той же версии. Незнакомую версию
  отвергает предусловием `supported-address-data`.
- **Чем грозило.** Carrel читал 3.0 и при правке записывал 3.0 обратно: карточка
  4.0 теряла `KIND` насовсем. Отчёт о потере этого не видел — потеря была при
  чтении.
- **Carrel.** Все чтения карточек (список, карточка, поиск, поиск по UID) просят
  `text/vcard; version=4.0` (`dav.CardQuerier`). Отказ — повтор без версии.
  Карточка 3.0 на таком сервере после правки хранится в 4.0: меняется формат, не
  данные (решение 15.09.2026).
- **Найдено.** 15.09.2026, живая проверка S-13 на Baikal. `v0.0.60`.
- **Сторож.** `TestBaikalVCard4Edit`; без сети — `TestCardReadsAskForVCard4`.
- **Nextcloud** вживую не проверен.

### SV-2. text-match в CalDAV: регистр только у латиницы

- **Стандарт.** RFC 4791 §9.7.5: collation по умолчанию `i;ascii-casemap` —
  регистр не учитывается только у ASCII. Это по стандарту, но для кириллицы
  поиск становится регистрозависимым. У CardDAV умолчание `i;unicode-casemap`
  (RFC 6352 §8.3), там этой беды нет.
- **Сервер.** Поддерживает `i;octet`, `i;ascii-casemap`, `i;unicode-casemap`;
  незнакомую collation отвергает 400.
- **Carrel.** Поиск по календарям шлёт `collation="i;unicode-casemap"` своим
  REPORT (`dav.CalSearcher`). Отказ 400/403/412/415/422/501 — повтор с умолчанием и
  заметка источника «регистр только у латиницы» (`cal.ErrLatinCaseOnly`).
- **Найдено.** `v0.0.47` (замечено), решено 14.09.2026, `v0.0.57`.
- **Сторож.** `TestBaikalSearch` требует, чтобы «ковал» находил «Встреча с
  Ковалёвой».

## Radicale

### SV-3. text-match по составному свойству — 500

- **Сервер.** До 3.7.7 (вышел 19.07.2026) `text-match` по `N` (и `ADR`) падает:
  `'Name' object has no attribute 'lower'`, ответ 500. Debian stable — 3.5.3,
  oldstable — 3.1.8.
- **Carrel.** Поиск контактов не ищет по `N`: `FN, NICKNAME, EMAIL, TEL, ORG`.
  `FN` обязателен в 3.0 и 4.0 и несёт то же имя (решение 14.09.2026, `v0.0.59`).
- **Когда пересмотреть.** Когда распространённые дистрибутивы дойдут до 3.7.7.
- **Сторож.** `TestRadicaleSearch` на 3.5.4 (падал без обхода);
  `TestSearchSendsNoTextMatchOnN` держит сам запрос.

### SV-4. Фото vCard 4.0 обрезается

- **Стандарт.** RFC 6350: фото в 4.0 — URI, `PHOTO:data:image/jpeg;base64,…`,
  без экранирования запятой.
- **Сервер.** Через vobject режет значение на первой запятой и экранирует `;`:
  хранит `data:image/jpeg\;base64`, картинки нет. С `VALUE=URI` — так же.
  Экранированная запятая спасает данные, но добавляется `\;`. Целиком держится
  только форма 3.0 `PHOTO;ENCODING=b;TYPE=JPEG` внутри карточки 4.0. Проверено на
  3.5.4 и 3.8.0. Задачи Radicale #1795 и #1863 закрыты без исправления.
- **Carrel.** Пишет по RFC; после записи отчёт о потере `PHOTO`, уведомление с
  названным риском и действие «сохранить фото в старом формате» — по одной
  карточке (решение 15.09.2026, `v0.0.61`, `v0.0.62`). Карточка 3.0 фото
  сохраняет.
- **Сторож.** `TestRadicalePhoto` ждёт потерю и упадёт, когда Radicale станет
  хранить фото; без сети — `davtest.CutPhotoDataURI`.

### SV-5. PUT без Content-Length — 400

- **Стандарт.** HTTP/1.1 разрешает chunked-тело.
- **Сервер.** Отвечает 400 на PUT без длины. Baikal и go-webdav принимают.
- **Carrel.** PUT всегда с `Content-Length`: обёртки `dav.Typed` и `dav.Sized`
  не доходят до `http.NewRequest` (`v0.0.44`). Там же: PROPPATCH и MKCOL с
  обрезанным телом давали 400 `no element found` (`v0.0.40`).
- **Сторож.** `TestRadicaleRecords`; без сети — `TestSizedBodyIsNotChunked`.

### SV-6. Права `owner_only` и отказы

- **Сервер** (настройки по умолчанию, как в `testdata/radicale/config`):
  - календари и книги — только прямо в домашней коллекции, промежуточной папки
    нет; один дом на оба рода — имена не должны совпадать;
  - нетипизированный `MKCOL` — 403;
  - тело не iCalendar / vCard — 400;
  - несколько VEVENT с разными UID в одном ресурсе — 400;
  - `MOVE` коллекции — 405;
  - путь с ведущим `/` от корня хоста видит чужого принципала — 403.
- **Carrel.** Коллекции создаются типизированно прямо в доме; адрес коллекции
  не меняется (S-12.2), `MOVE` коллекций нет.
- **Сторож.** `TestRadicaleCollections`, `TestRadicaleAddressBookCRUD`,
  `TestRadicaleCalendarCRUD`.

### SV-7. well-known уводит в веб-интерфейс

- **Стандарт.** RFC 6764: `/.well-known/caldav` ведёт к контексту DAV.
- **Сервер.** `/.well-known/carddav` → 301 → `/` → 302 → `/.web` → 200 HTML,
  без принципала.
- **Carrel.** Обнаружение принимает цель well-known, только если там найден
  `current-user-principal`; иначе остаётся на введённом адресе.
- **Сторож.** `TestRadicaleDiscoveryFindsBothKinds`; без сети —
  `TestWellKnownHTMLWithoutPrincipalStaysOnEnteredURL`.

Помимо особенностей: Radicale игнорирует `collation` и `version` и отдаёт
карточки как хранит, сравнивает текст через `lower()` — для Carrel это удобно.

## SFTPGo (x/net/webdav)

### SV-8. If-None-Match на PUT не соблюдается

- **Стандарт.** RFC 9110 §13.1.2: `If-None-Match: *` — не создавать поверх
  существующего, 412.
- **Сервер.** Заголовок игнорирует и перезаписывает (golang/go#44492).
- **Carrel.** Перед условным PUT, копией и переносом имя проверяется `file.Stat`
  (`v0.0.53`). Окно между проверкой и записью остаётся: имя, занятое в него,
  перезапишется.
- **Сторож нет.** `TestSFTPGoUploadOccupiedName` пропускается (`t.Skip`), а не
  проверяет, что заголовок по-прежнему игнорируется: исправление в SFTPGo никто
  не заметит.

## Baikal: окружение

### SV-9. Apache закрывает простаивающее соединение через 5 с

- **Сервер.** Apache 2.4 (`KeepAliveTimeout` 5 с по умолчанию) закрывает
  соединение, простоявшее дольше. PUT в уже закрытое соединение получает `EOF`, а
  Go такой PUT повторно не шлёт.
- **Carrel.** Не задело: `web` создаёт `dav.Client` на каждый запрос.
  Живые тесты берут новый клиент на засев и очистку (`v0.0.60`).
- **Сторож нет.** Держать соединение дольше 5 с между PUT — вернуть `EOF`.

### SV-10. well-known уводил с https на http

- **Сервер.** Перенаправление при обнаружении понижало схему (записано в плане
  при первом подключении Baikal; подробности ответа не сохранились).
- **Carrel.** По перенаправлению с https на http не идёт — ни при обнаружении,
  ни в страже (`dav.Guard`): пароль не уходит открытым текстом.
- **Сторож нет.** Перепроверить на текущем Baikal и записать ответ.

## Библиотеки

### SV-11. go-webdav, клиент

- `caldav.TextMatch` без поля collation, хотя внутренний элемент его знает
  (проверено и в master, 15.09.2026).
- `carddav.AddressDataRequest` не передаёт `content-type` и `version`.
- **Carrel.** Свои REPORT в `internal/dav`: `CalSearcher` (`v0.0.57`),
  `CardQuerier` (`v0.0.60`). `Transport` не расширялся.
- **Сторож.** `TestSearchCalendarNamesItsCollation`,
  `TestQueryCardsNamesTheVersion`. Когда поля появятся в go-webdav, свои REPORT
  можно снять.

### SV-12. go-webdav, сервер (под `davtest`)

- text-match сравнивает с регистром и игнорирует collation
  (`TODO: handle text-match collation attribute`).
- `carddav.Filter` без prop-filter не находит ничего; RFC 6352 §10.5 — находит
  всё.
- **Carrel.** `davtest` сворачивает регистр под `i;unicode-casemap` и отдаёт все
  карточки на пустой фильтр. Иначе тесты проверяли бы go-webdav, а не серверы.

### SV-13. go-vcard экранирует запятую в data: URI

- **Библиотека.** Пишет `PHOTO:data:image/jpeg;base64\,…`.
- **Carrel.** `card.Encode` возвращает запятую у `PHOTO`, `LOGO`, `SOUND`, `KEY`;
  иначе ломалось и чужое фото на любой правке карточки (`v0.0.52`).
- **Сторож.** Тесты фото в `internal/provider/card` и `internal/web`.
